# deploy identity, AWS

What lets one repository's pipeline deploy one ECS service, with no access key anywhere: an IAM role the forge's token can assume, and a policy that names one service and one image repository.

- **Creates:** an `aws_iam_openid_connect_provider` for the forge's issuer (or looks up the one that exists, see below), an `aws_iam_role` named `<environment>-<name>-deploy` with a one-hour session, and one inline policy.
- **Trusts one thing.** The trust is `sts:AssumeRoleWithWebIdentity` from that provider, with `StringEquals` on `aud` (`sts.amazonaws.com`) and on `sub`. There is no `StringLike` and no wildcard. The subject is `repo:<owner>/<repo>:environment:<environment>` on GitHub (the deploy job names its environment), the id form `repo:<owner>@<id>/<repo>@<id>:environment:<environment>` when `immutable_subject` is on, and `project_path:<group>/<project>:ref_type:branch:ref:<branch>` on GitLab, whose subject carries no environment. On GitLab the trust also matches `project_id` and `namespace_id`, which gitlab.com's provider offers as condition keys.
- **GitHub's numeric ids are pinned only through the immutable subject.** AWS documents only `aud` and `sub` as condition keys for GitHub's provider. On a repository whose subject has no ids, a deleted and recreated repository with the same name matches; turn `immutable_subject` on where the repository has it.
- **What the policy allows:** the registry login (`ecr:GetAuthorizationToken`); six ECR actions on the one repository (`BatchCheckLayerAvailability`, `CompleteLayerUpload`, `DescribeImages`, `InitiateLayerUpload`, `PutImage`, `UploadLayerPart`); `ecs:DescribeServices` and `ecs:UpdateService` on the one service; `ecs:RegisterTaskDefinition` and `ecs:DescribeTaskDefinition`; and `iam:PassRole` on the service's `-exec` and `-task` roles, only to `ecs-tasks.amazonaws.com`. **No action has a star.** Two statements name `*` as the resource, because AWS gives those calls nothing narrower: the registry login, and the two task definition calls. A test pins that list.
- **One provider per issuer per account.** The first identity in an account makes the provider; set `existing_oidc_provider` on every later one, and it is looked up instead. **Destroying the identity that made it removes the provider the others use.**
- **Names come from the service.** `service` is the name of a service resource in the environment; its cluster, service, repository and roles are derived exactly as the `service` module derives them, and a test fails if either side is renamed.
- **The first apply is by hand.** An identity cannot create itself: someone with IAM rights applies this stack once, from a workstation or a bootstrap pipeline. This is a human step (CLD-15).
- **gitlab.com only.** A self-managed GitLab issuer is untested.
- **Not checked against a real account:** the GitHub issuer's trailing slash, whether `RegisterTaskDefinition` needs tag permissions, whether `ecs:TagResource` is needed, and the ECS action table's resource types. The spike's reading was `ecr:DescribeImages` for the existing-tag check, not `BatchGetImage`. See `docs/cloud-deploy-spike.md`.
- **Needs from the runner's role:** `iam:CreateOpenIDConnectProvider` (and `GetOpenIDConnectProvider` to look one up), `iam:CreateRole`, `PutRolePolicy` and their delete counterparts, and `sts:GetCallerIdentity`.
- **Idle cost:** none. The role, its policy and the OIDC trust entry are free.
- **Outputs:** `console_url`, `role_name` (the template's `role` value), `role_arn`.
