# 19 worker-pools - done 2026-10-19

## What was built
- **POOL-1** Organization-wide worker pools: `worker_pools` (migration 0042, additive; unique name per org, at most one default, a default must be enabled, name/tag/image shape checked by the table), `createPool`/`updatePool`/`deletePool` under an org-row lock so the count and the default swap are atomic, and `GET/POST/PATCH/DELETE /organizations/:orgId/pools`. Org viewer reads, org admin manages, every change audited. The name is immutable; the default cannot be deleted or disabled.
- **POOL-2** `pool:` in `stack.yml`, kept as a declared name on the scan `Stack` (no column, no migration), resolved when a pipeline is generated by `resolvePool`: the named pool, else the org default, else none (today's behaviour).
- **POOL-3** The generator writes the pool's tags on a stack's `plan`, `estimate`, `summary` and `apply` jobs (a copy per job: a shared array would be written as a YAML anchor) and the pool's image on the tool job only. An unknown or disabled pool fails generation and never falls back to shared runners. Wired into merge request plans, drift checks and applies.
- **POOL-4** `GET /organizations/:orgId/projects/:projectId/pools/:poolId/status` (org admin, uses the org's GitLab connection): counts of runners with every tag of the pool that are online, `healthy | degraded | offline | unknown`, with a reason when unknown. Only `id`, status, paused and runner type are decoded; no address, description or token. `packages/gitlab` gained `runners.list`.
- **POOL-5** `orch pool ls|add|rm|default` (with `--status` per project) and a read-only **Worker pools** section on the settings page with an on-request **Check health**.
- **POOL-6** One structural test that every job of every kind a plan pipeline can carry has its stack's pool tags (proven by two mutations).
- **POOL-7** ADR-0015: tags only, no platform worker agent. D1 and invariant 3 are unchanged.
- Docs: `docs/worker-pools.md`, `docs/adr/0015-worker-pool-agent.md`, `docs/iac.md`.

## Invariants
Nothing secret is stored or shown: a pool holds names, tags and an image reference that cannot carry credentials (an `@` that is not `@sha256:` is refused, so `user:password@host/image` is never kept in the audit trail). The control plane still holds no cloud credentials: the runner does. GitLab traffic goes through `packages/gitlab`; tests use the mock. Pool routes are guarded and audited; the status route reads and is not audited.

## Auth-model decisions (taken on the standing authorization; say so in the report)
- Org viewer reads pools; org admin creates, changes and deletes them.
- Pools are org-wide, with no per-project allowlist. Tags route, they do not isolate.
- The default swap is atomic; the default cannot be disabled or deleted; a disabled pool cannot be the default; the name is immutable.
- `pool.status` is org admin, per project, because it reaches GitLab with the org's connection; it is not audited.
- ADR-0015 (tags only, no agent) is accepted. Reverse it in the ADR.

## Deviations
- POOL-4 asked for runner executors. GitLab's runner API has no executor field, so none is read and the SCAN-5 warning still says the executors are "not known".
- POOL-6 did not give the SCAN-5 `secret_detection` job the pool's tags: that job belongs to the project's own pipeline, and tagging it would make the rendered project pipeline depend on the org default pool (drift). A pool that takes tagged jobs only will not pick up that job.

## Not verified / human gates
- **Nothing ran against a real runner or GitLab.** Assumed: `tag_list` requires every tag; a real GitLab answers 403 below Maintainer; the runner list is read to the end with no cap; an unrecognised runner status is left out of the count.
- The API cannot say which stacks name a pool. An apply is generated from the pools as they are when it starts, so a retag between plan and apply moves the apply. A merge request can choose among the org's pools with `pool:`; that gives it no runner GitLab would not already offer the project.
- The settings page's Check health uses the org's first GitLab connection and is read-only for pools (CLI or API to change them). There is no Playwright coverage of the new section.

## Review results (once for the whole feature, not per task)
- **`/security-review`:** no vulnerability at confidence 8 or above. Below the bar: a merge request chooses its pool through `pool:` (adds no capability, since GitLab decides which runners a project may use; the route comment overstated it and is corrected, with a limit added to the docs); apply reads the pools as they are at apply time (an org admin's change, documented).
- **`/code-review`:** 12 findings. Fixed: a stack that cannot be generated (a pool deleted or disabled) stopped the drift check of the whole project, and sorted first at every later tick (now left out before the batch is cut, logged, and not recorded; the other stacks are still checked; test first, and two earlier tests that pinned "nothing is planned" now say the others are); `planRequest` took its policy sets, limits and pools as optional, so a caller that left them out ran every stack on shared runners (now required); `orch pool add --image ""` was dropped silently (now sent, and the API refuses it); the comment that said a merge request "cannot point a stack at a runner nobody approved" (corrected). Declined on purpose: the pool image replacing a stack's declared `version` (documented: the pool's image holds the tool by the pool's own say-so); apply using current pools (documented, ADR); "offline" for a pool no runner matches (the page says "0 of 0 runners online", and a test pins it); the status route's order of checks, unbounded runner paging, and its `Promise.all` over up to 50 pools (org admin only, small); mapping the two table constraints the API's own validation already prevents; a `pool.update` audit event on a same-value change (it records who asked); the duplicated regexes and reason text; test hygiene (audit rows are read per pool).
