# 29 job nodes - done 2026-10-21 (not seen green end to end, see the gate)

The Jobs panel on Status draws a pipeline as step-by-step nodes, like n8n: a node for each job, a column for each stage, arrowed lines from stage to stage, a failed node saying why. A job that starts another pipeline is a node of its own; a child pipeline of the same project and a pipeline of another project (when the viewer can see that project) are drawn as lanes to the right. Nothing is committed.

## What was built
- **A, the nodes (NOD-1..4).** `apps/web/src/job-flow-layout.ts` (pure layout: columns by stage, junctions, curved edges, lanes), `job-flow.tsx` (a `ul` of `li` nodes for each stage under its heading; the lines are an `aria-hidden` SVG), the Jobs panel in `runs.tsx` draws them. The box scrolls inside the card; the demo shots check its reach at 1280 and 390, both themes.
- **B, the chain inside one project (NOD-5..8).** `packages/gitlab` keeps a bridge's `id`, `stage`, `webUrl` and `downstream` (pipeline, project, state). `GET .../pipeline-runs/:runId/jobs` also answers `triggers` and `children` (jobs of each same-project child, in the same ten-key shape). Caps: 200 jobs in all, 20 triggers, 5 children, one level. The demo's `main` has a `release` trigger into a child of two jobs.
- **C, across projects (NOD-9..12).** A trigger into another project answers that pipeline's state and the two GitLab numbers, no name, path or address, and the project's pipeline is never read by this route. `GET .../pipeline-runs` takes `pipelineId`. The web matches GitLab's project number against the viewer's own project list; on a match it reads that project's run and jobs (its own guard, checked again by the server) and draws the lane headed with the project's name; otherwise the node says why in words. The demo's `main` also triggers `deploy-api` into `acme/api`, recorded as a run of that project.
- **Delivery (NOD-13).** `docs/demo.md` "Flow views" and the Status bullet; `docs/openapi.json` current; this file; ROADMAP row 29.
- No migration, no new dependency, no new route (one query parameter on a guarded one).

## Reviews
- **Security (by hand, cut C):** nothing at 8/10 or above. Every read of another project goes through a route that checks `pipeline.read` there; the run lookup is scoped by organization and project; the lane title is the project's name from the viewer's own list, never from an answer; another project's error text is not shown. **The one accepted exposure:** a reader of project A (`pipeline.read` on A only, calling the API directly) learns the state and GitLab numbers of a downstream pipeline of project B that they may not be able to read. If that is not acceptable, the route should leave the state out when the reader cannot read B on the platform.
- **Code review:** 13 findings; one fixed (a trigger with no project number matched a project made by hand, which has none either; test first), one refuted by measuring in a browser (vertical text clipping), the rest below or reasoned away in LOG.md (NOD-13 entry).

## Follow-ups for your decision
1. **One failing child hides the parent's jobs** (a 5xx or timeout reading a child fails the whole answer; before this feature only the parent was read). Fix needs a "could not read" state beside `gone` in the answer.
2. **Stage order** after a retry can put a stage in the wrong column (jobs sorted by id; GitLab gives no stage order). Needs the stages from `.gitlab-ci.yml`.
3. **The chain stops at one level silently**: no node or note says a child or another project's pipeline started more. A "not shown" note would do.
4. **Fan-out across projects is uncapped on the web**: 20 triggers into 20 projects is about 40 requests and 20 lanes, and each cross-project call makes the API read bridges and children the web discards. A lane cap and a jobs-only flag would bound it.
5. **F-NOD-1:** with real webhooks, a child pipeline sharing a ref with its parent may replace the parent as the Status row of that branch (the recorder keeps the newest per ref). Unverified live; not fixed.
6. The failing identities web test and the two failing root tests above.
