## Decisions to review (REVIEW-tagged in the LOG)

- **Auth model (CLI-5):** an environment's CI token now carries `secret.reveal` and a maintainer role derived from that scope, held to three actions on its own environment. Every environment token can therefore reveal that environment's secrets; protection rests on the exchange's protected-ref rule plus GitLab's protected-environment setting (GOV should require both for production).
- **Resolved-variables route (CLI-3):** org-level secrets are visible to a project maintainer through `resolved-variables/values`.
- **CLI-2:** `cli_logins.user_id` -> users CASCADE (migration additive); the loopback consent page threat is closed only by the web UI (feature 08).
- **Test-only API exports (CLI-6):** `./sync-apply`, `./worker`, and `@orch/gitlab`/`@orch/pipelines` dev dependencies in the CLI.
- **Release trust (CLI-7):** `SHA256SUMS` is fetched from the same place as the binary; it catches corruption or a swapped file, not a replaced release. Signing the list is the upgrade. Binaries are not code-signed or notarised.

## Remaining risks and open follow-ups

- **CLI-1:** mode/owner checks are POSIX-only; the parent directory of an existing config is not checked; the token is stored in clear in a 0600 file; `orch --json` with no command prints text help; unexpected errors print only the error kind; `.orch.json` search climbs to the filesystem root outside a git repo.
- **CLI-3:** dotenv `$` is not escaped; `file` kind is exported as content; `push` handles limited kinds; `--ignore-issues` exits 0; `--force` can leave a stale `.tmp`; `push -` cannot prompt; audit inserts are sequential; the size check is UTF-16; a UUID-looking ref is taken as an id; project list needs `organization.read`.
- **CLI-4:** `ORCH_TOKEN` is withheld from the child, but variable writers control the child's environment including `PATH`/`LD_PRELOAD`/`NODE_OPTIONS`; values are readable in `/proc/<pid>/environ` by the same user; SIGKILL on orch leaves the child running; a double Ctrl-C reaches the child twice; child exit codes 2, 126, 127 look like orch's own.
- **CLI-5:** the token is printed on stdout and reaches the job log if not captured; `eval "$login"` in two steps replaces the SPEC's `&&` form; `orch run` withholds only the default `ORCH_ID_TOKEN` name; ambient `ORCH_*` ids can mix with flag/file names.
- **CLI-6:** `overrides` are not exposed by `pipeline setup`; the apply wait is bounded to 10 minutes and the apply goes on server-side after it (no worker means "still applying"); `--param` values show in the process list (they are not secrets); `--yes` on a hand-written `.gitlab-ci.yml` skips the confirmation by design (it is a merge request).
- **CLI-7:** re-running the release job for an uploaded tag adds duplicate files to the package; the job installs `curl` with apt when the image lacks it; a private registry cannot be installed from anonymously; the atomic rename onto `orch` has no test.
