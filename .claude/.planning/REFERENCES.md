# References - what we borrow, and where it lands

Rows marked * were read from the upstream README while planning. The rest are from prior knowledge - re-check upstream docs before copying behaviour.

| Reference | What it is | Borrow | Lands in |
|---|---|---|---|
| [Spacelift](https://spacelift.io/) | Managed IaC CI/CD | Stack as the unit of work; shared "contexts" (vars attached to many stacks); policy-as-code (OPA) at plan/approval/trigger; drift detection; run states + approvals; stack dependencies | IAC, POL, VAR scopes |
| [Terragrunt](https://github.com/gruntwork-io/terragrunt) | Thin Terraform wrapper | DRY config via include/inherit; `dependency` ordering; `run-all` parallel waves; auto remote-state config | IAC-2, IAC-8, PIPE-3 |
| [Terramate](https://github.com/terramate-io/terramate) | Stacks + orchestration | Stack = directory + metadata + tags; git-based change detection (`--changed`); ordered execution; generating CI pipelines | IAC-1..4 (core model) |
| [Atmos](https://github.com/cloudposse/atmos) | Stack config framework | YAML manifests with imports + deep-merge inheritance; component catalog; "describe affected" | PIPE-3 layering, IAC-1 config |
| [Terraspace](https://github.com/boltops-tools/terraspace) | Terraform framework | Convention-over-config layout; env/region layering; before/after hooks; ordered `all up` | PIPE-3 conventions, IAC-4 hooks |
| [Atlantis](https://github.com/runatlantis/atlantis) | PR automation | Autoplan on changed files; `plan`/`apply` as MR comments; apply the *saved* plan; per-dir locks; apply requirements (approved, mergeable); in-repo config | IAC-3, 6, 7 |
| [Stategraph](https://github.com/stategraph/stategraph) * | Graph state + orchestration | Creds stay with the runner (server never runs Terraform); every plan/apply a recorded transaction; resource-level locks; state queryable by SQL; CODEOWNERS approvals, policy and cost gates | D1/D9, IAC trust boundary, backlog |
| [envolve](https://github.com/erdemkosk/envolve) * | Go CLI centralising `.env` files | One canonical store; bulk key search/edit across projects; table view; sync one vs sync-all; encrypted backup | VAR-6, VAR-7, CLI-3 |
| [EnvSync](https://github.com/EnvSync-Cloud/envsync) * | Bun + Hono env/secrets platform | Point-in-time rollback; approval workflow for prod changes; OIDC for CI; audit + log forwarding; many sync targets; `pull/push/export/run` CLI; typed SDKs | VAR-5, AUTH-6, CLI-4/5, GOV, SYNC, EXT |
| [Infisical](https://github.com/Infisical/infisical) | Secrets platform | Project > environment > folder model; secret versioning; references/imports; integrations incl. GitLab; `run` injection; dynamic secrets + rotation; secret scanning; audit; the secrets screen (environment select, search, masked list, row details, reveal all, .env download, change feed) | VAR, SYNC, CLI-4, EXT-6, VWS, FLD, backlog, VUI (the secrets screen as seen in nine more screens: toolbar, All Environments matrix, create drawer, row menu, version history drawer; the share-secret page is not taken) |
| [DNSControl](https://github.com/DNSControl/dnscontrol) * | DNS as code, `dnsconfig.js` | `preview` / `push` against 76 providers, `creds.json`, config in git with MR review. `check`, `print-ir`, `get-zones`, `NO_PURGE`/`IGNORE`, the `BIND` provider are prior knowledge: DNS-2 verifies them | DNS (the engine, runner-side) |
| [octoDNS](https://github.com/octodns/octodns) | DNS as code, YAML | Landing page only was read. Update/delete thresholds that refuse a plan changing too much (prior knowledge). Alternative engine, not built | DNS-7 gates; SPEC open question 1 |
| [external-dns](https://github.com/kubernetes-sigs/external-dns) * | Kubernetes resources to DNS records | `upsert-only` vs `sync` policy, TXT ownership registry, `--domain-filter`, `--dry-run`. Not rebuilt; coexists | DNS-6/7, docs |
| [gardener external-dns-management](https://github.com/gardener/external-dns-management) * | DNSProvider / DNSEntry controllers | A provider only touches the domains it includes; blocked zones; RFC 1123 name validation. Owner IDs were removed upstream | DNS-6 (claims) |
| [dns-orchestrator](https://github.com/AptS-1547/dns-orchestrator) * | Desktop/Android multi-provider DNS manager | Provider-API record CRUD with credentials in the OS keychain (the model we do not copy: invariant 3); network toolbox (propagation, DNSSEC) | backlog: post-apply checks |
| [GitHub REST: Actions secrets](https://docs.github.com/en/rest/actions/secrets) * | Secrets API | `PUT` with `encrypted_value` and `key_id` at repository, environment and organization scope; write-only, so drift is names and `updated_at` only; sealed box with libsodium | FRG-19, FRG-20 |
| [GitHub REST: Actions variables](https://docs.github.com/en/rest/actions/variables) * | Variables API | Same three scopes, readable, so drift by value | FRG-20 |
| [GitHub Actions OIDC](https://docs.github.com/en/actions/security-for-github-actions/security-hardening-your-deployments/about-security-hardening-with-openid-connect) * | Identity token for a job | Issuer, `id-token: write`, custom audience, claims `repository`, `repository_id`, `ref`, `environment`, `job_workflow_ref`; no protected-ref claim. JWKS URL and the Enterprise Cloud issuer still to confirm | FRG-23 |
| [GitHub webhooks: validating deliveries](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries) * | Webhook signature | `X-Hub-Signature-256` HMAC-SHA256 of the body, constant-time compare; needs the secret itself, not a hash | FRG-10, FRG-21 |
| [GitHub REST: environments and deployments](https://docs.github.com/en/rest/deployments/environments) * | Environments | Required reviewers are the manual approval; free on public repositories only, a paid plan for private ones (per-rule availability to confirm); pending-deployments approval call to confirm | FRG-18, FRG-22 |
| [GitHub Apps: installation tokens](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-an-installation-access-token-for-a-github-app) * | App credential | A token lasts one hour, not tied to a person. Not built first (SPEC question 3) | FRG-2 |
| n8n (workflow editor, seen in six screenshots from you, not read upstream) | Workflow automation | A flow drawn as boxes with a status mark and curved lines with a count on them; a step list with durations beside it. Not taken: drag, zoom, the chat dock | FLW, NOD |
| [GitLab Deployments API](https://docs.gitlab.com/api/deployments/) * | Deployment records | A job with `environment:` makes a deployment; list and get on every tier; statuses created, running, success, failed, canceled, blocked; `deployable` gives the job and pipeline. Not taken: the user and commit objects, GitLab's approvals (Premium) | DEP-2, DEP-3 |
| [GitLab Environments API](https://docs.gitlab.com/api/environments/) * | Environment records | List by name; stopping and deleting are writes we do not make. Protected environments and deployment approvals are Premium | DEP-2, DEP-6 |
| [GitLab webhook events: Deployment](https://docs.gitlab.com/user/project/integrations/webhook_events/) * | `Deployment Hook` | Fires on a deployment's status change; body has `deployment_id`, `status`, `environment`; allow-list three fields and ask GitLab for the rest | DEP-4 |
| [GitLab deployments and rollback](https://docs.gitlab.com/ci/environments/deployments/) * | GitLab's own rollback | Rollback is retrying an old deploy job: needs its artifacts, and "prevent outdated deployment jobs" can hide the button. Not taken: we start a new pipeline for the build instead | DEP-11 to DEP-13 |
| [GitLab CI `resource_group`](https://docs.gitlab.com/ci/resource_groups/) | Serialise jobs | One deploy at a time per environment (from prior knowledge, page not read). Whether a variable is allowed in the group name is to be proved on a real GitLab | DEP-9 |
| [Kargo](https://github.com/akuity/kargo) * | Promotion between stages | Stages in order, promote a verified build onward, one view of every stage. Not taken: Freight bundles, Warehouses, anything Kubernetes or Argo CD (core concepts page read; verification and auto-promotion pages not read). Licence not checked: ideas only | DEP-11, DEP-14 |
| [Argo Rollouts](https://argoproj.github.io/rollouts/) and [Flagger](https://flagger.app/) | Progressive delivery | Verify after a deploy and go back on failure (summaries only, upstream not read). Canary and blue-green traffic splitting are Kubernetes only: not taken | DEP-9 (health check, step back) |
| [Apache DevLake](https://github.com/apache/incubator-devlake) | Engineering metrics | DORA measures from deployments alone: frequency, failure rate, time to restore (summaries only, upstream not read). Lead time needs commit times: not taken | DEP-20 |
| [Kamal](https://kamal-deploy.org/), [Dokku](https://dokku.com/), [Coolify](https://coolify.io/) | Self-hosted deploy tools | The shape of a deploy script: pull the image, start it, check health, step back (summaries only, upstream not read). Not taken: running as a platform | DEP-9, DEP-10 |
| Argo CD, Flux, Spinnaker (from memory, not read) | GitOps and delivery platforms | Named only so the gap is clear: they hold cluster credentials, which the platform does not (invariant 3) | non-goal |

## Differentiator to protect
None of the above is "paste a GitLab project URL, get a working pipeline + its variables wired up". Keep onboarding (GL-7 -> PIPE-4 -> PIPE-6 -> SYNC) the shortest path in the product.
