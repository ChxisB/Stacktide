## 2026-10-19 COST-1
- Built: an optional `cost { monthlyDelta, monthlyTotal, currency, tool }` on `POST /runs/:runId/plan-summary`, stored on `run_stacks` (migration 0034, four nullable columns and `run_stacks_cost_check`, additive). Validation in the route (finite numbers via `z.number`, which refuses the `1e999` JSON writes as infinity; a delta of either sign up to a trillion, a total of 0 up to a trillion, a `^[A-Z]{3}$` currency, a `^[a-z0-9][a-z0-9._-]{0,39}$` tool, strict object) and again in the database (NaN and infinity compare above any limit in Postgres, so the bounds refuse them). The summary and its cost are one write: a later summary without a cost removes an earlier one, and a retried plan job (a new `planJobId`) forgets the estimate along with the policy verdict, so an old plan's number cannot gate a new plan. The audit event says `costed: true|false`, not the amounts. `docs/openapi.json` regenerated.
- Design: the cost is not its own endpoint (SPEC): it rides on the summary the summary job already posts under the same guard (`run.summary`) and the same "only the stack's summary job" check. Doubles, not numerics: an estimate has no use for decimal exactness, and the currency is never converted.

## 2026-10-19 COST-2
- Built: `cost_limits` (migration 0035, additive, with its `set_updated_at` trigger): one limit per scope, where the scope is an organization plus an optional stack tag (no tag is the organization's own limit), in a unique index on `coalesce(tag, '')`; `max_monthly_delta` 0..1e12, optional `warn_at` between 0 and the maximum, a `^[A-Z]{3}$` currency, all in a database check as well as in the route. `packages/db/src/cost-limits.ts`: `setCostLimit` (an upsert that keeps the id and returns what it replaced; setters of one organization take its row in turn, so the cap of `MAX_COST_LIMITS` = 100 and one-per-scope are not a race), `getCostLimit`, `listCostLimits`, `allCostLimits`, `deleteCostLimit`. `packages/core/src/cost.ts`: pure `limitFor(limits, tags)`. API (`apps/api/src/routes/cost-limits.ts`): `GET` (paged), `PUT` (201 when the scope is new, 200 when it replaces one) and `DELETE /:limitId` under `/organizations/:orgId/cost-limits`; rules `cost.limit.read` (org viewer), `cost.limit.set` and `cost.limit.delete` (org admin); audit `cost.limit.set` (with `previous`, or null) and `cost.limit.delete`, both carrying the figures, which are numbers, a code and a tag. `docs/openapi.json` regenerated; the pinned counts in `apps/api/src/authz.test.ts` (118 -> 121 routes) and `spec.test.ts` (116 -> 119 operations) moved by the three routes.
- Decision: **the strictest limit wins**, not the first or the most specific. A stack with several tags that each have a limit takes the one with the lowest `maxMonthlyDelta` (ties by tag name, so it is stable); the organization's own limit applies only when none of the stack's tags has one. "Most specific tag wins" in the task text has no order between two tags, and the safe reading for a gate is the lower number. Limits in different currencies are compared as bare numbers by `limitFor` (a `shortcut:` in the code): the verdict in COST-3 denies when the estimate's currency is not the limit's, so a mismatch never gets as far as a comparison.
- Moved, not dropped: the "currency different from the estimate" deny test is COST-3's (the TASKS line says so). COST-2 has no verdict to put it in.
- Tests: 6 in `core/cost.test.ts` (precedence, ties, no tag limit, no limits), 5 in `db/cost-limits.test.ts` (set and replace keep the id and report `previous`, organization isolation, paging, delete, the cap, the check refusing bad rows), 10 in `api/cost-limits.test.ts` (admin and owner set; member, viewer 403 on set and delete but read; no session 401; another organization's admin 404 on every verb; replace is 200 with the same id and an audit event that says what it replaced, the same numbers again still audited; null, omitted and a tag as scopes; 18 refused shapes with nothing stored and no submitted text in the answer; the 409 `too_many_cost_limits` at the cap, an existing scope still changeable, a delete makes room; delete is 204 then 404 and audits what it removed; paging).

## 2026-10-19 COST-3
- Built: in `packages/core/src/cost.ts`, `CostResult`, `COST_RULES` (`cost-over-limit`, `cost-near-limit`, `cost-unavailable`, `cost-currency-mismatch`), pure `costVerdict(limit, cost)` returning a `PolicyReport` (so the two are judged the same way) and `planVerdict(policy, limit, cost)`, which runs the policy report through `judge()` (an evaluator that did not run is still `evaluator-failed`) and joins the cost rules to it, every reason named, repeated rules once. A delta at the maximum is allowed, above it denied, from `warnAt` on warned. No limit: informational, never a deny, even with no estimate. A limit and no estimate, or a delta that is not finite: `cost-unavailable` (a crashed estimator blocks). A different currency: `cost-currency-mismatch`, checked before any comparison, never converted. `planCostOf(runStack)` in `packages/db/src/runs.ts` reads the estimate off a row (`PlanCost` is now `CostResult`, one type). In `apps/api/src/run-apply.ts`, `applyRun` reads the organization's limits once and, per selected stack after the policy checks, refuses with 409 `cost_denied` naming the stack and the rules. Both the command path and the merge path go through `applyRun`, so both refuse.
- Decision: the limits are those **in force at the apply**, not frozen at plan time (the policy verdict is stored; the cost verdict is computed). A lowered limit stops a plan that was inside the old one; a raised or removed one frees it. Both changes are audited (`cost.limit.set`/`delete`) and need an org admin.
- Decision: for one stack the policy's refusal comes first (`policy_denied`, then `cost_denied`); across stacks the first stack in name order that fails any check is the one named, as before.
- Tests: 34 more in `core/cost.test.ts` (17 limit x estimate cells for `costVerdict` including the boundaries, NaN and infinity, 16 limit x estimate x policy cells for `planVerdict`, a duplicate rule), 10 in `api/run-apply.test.ts` (no limit changes nothing, a plan under, at or only warned about by a limit applies, over is `cost_denied` naming stack and rule and starts nothing, a missing estimate and a different currency deny, a tag's limit judges its stacks and the organization's the rest, the limits in force at the apply, a retried plan job forgets the estimate, the policy refusal comes first, the merge path). The "currency different from the estimate" test that COST-2 handed over is here.
- Gate: `bun run check` green: 4280 pass (API and packages), 246 web. `/security-review` not run: no auth, token, crypto or secret handling changed. New dependency: none. `docs/iac.md` lists `cost_denied` beside the policy refusals.
- **Follow-ups:** `planVerdict` is not called by production code yet: the apply uses `costVerdict` because the policy checks there keep their own codes; COST-5 uses `planVerdict` for the MR note and the run page. A branch can drop a stack's tag and fall back to the organization's own limit (a `shortcut:` comment in `run-apply.ts`; stated in COST-6's doc). No limit is the default, so no existing stack changes behaviour.

## 2026-10-19 COST-4
- Research (Infracost docs and search snippets; the JSON-format page returned 404, so the field names come from snippets): the legacy CLI (v0.10) `infracost diff --path plan.json --format json` prints one JSON document on stdout with top-level string fields `currency`, `totalMonthlyCost`, `pastTotalMonthlyCost`, `diffTotalMonthlyCost`; the key is `INFRACOST_API_KEY`; the CLI sends only price-relevant attributes (resource type, region, size), not the plan. The docs now describe a 2.0 CLI (`infracost scan`, `INFRACOST_CLI_AUTHENTICATION_TOKEN`, `ghcr.io/infracost/ci:2`) whose output shape I did not verify. A CVE was fixed in 0.10.45, so the image should be that or later. The Plan JSON API uploads the whole plan and is **not** used.
- Built: in `packages/iac/src/pipeline-gen.ts`, `PlanInput.cost { stacks, image }` and the exported `COST_FILTER`. Each selected stack in `cost.stacks` gets an `estimate:<stack>` job in a new `estimate` stage (between the waves and `summary`): it needs the stack's plan artifacts, runs the cost image, `allow_failure: true`, and its script is one chain that keeps `cost.json` only when there is a key, `infracost diff --path <dir>/plan.json --format json` succeeds and `COST_FILTER` accepts the answer, and otherwise `rm -f cost.json` and ends well. The summary job of an estimated stack also needs `estimate:<stack>` (artifacts), and a line after the counts merges `cost.json` into `summary.json` when it exists and is readable JSON; with none the summary is posted as before. `COST_FILTER` reads the delta, total and currency (strings or numbers) into the four fields the plan-summary route takes, with the route's bounds (delta +-1e12, total 0..1e12, a `^[A-Z]{3}$` currency); anything else is no output, never a guess. One problem is reported (`cost.image`) when a costed stack has no usable image; a `cost` with no selected stack needs no image and changes nothing. `apps/api/src/mr-plan.ts`: `MrPlanConfig.costImage` and `planRequest(..., limits)`: a stack is estimated only when `limitFor(limits, tags)` finds a limit (nothing is sent to the pricing service otherwise); the merge request turn reads `allCostLimits` in its lock; a drift check passes none. `apps/api/src/worker-main.ts`: `ORCH_COST_IMAGE`. `.env.example`, `docs/iac.md` and `docs/self-host.md` name the setting and the runner's `INFRACOST_API_KEY`.
- Decision: a separate estimate job, not a step in the plan job or the summary job. The plan job holds the cloud credentials and runs the stack's code; the summary job holds the platform token and the policy engine. The estimate job holds neither: no `id_tokens`, no `variables`, no `ORCH_*`, nothing of the platform's, and `INFRACOST_API_KEY` is named only in it. Its image can then be just infracost and jq (no combined policy-plus-cost image), and it cannot fail the plan.
- Decision: **no estimate image configured, or no limit that reaches a stack, means no estimate job**. With a limit and no image the plan is still made and its apply is denied as `cost-unavailable` (COST-3), and COST-5 will say why on the merge request; planning is not refused (unlike policy, whose verdict an apply cannot do without). An image that is not an image reference is refused with a note, as a bad policy image is.
- Tests: 11 + 3 + 4 in `pipeline-gen.test.ts` (snapshot; stage, job, needs and artifacts; the key named only in estimate jobs and nothing of the platform's in them; the summary needs the estimate and merges it before the post while other jobs are byte-identical; no costed stack is the pipeline as before; a bad image; with policy, each job keeps its own image; an apply has none; `COST_FILTER` run through real `jq` on Infracost-shaped JSON, with 15 refused inputs; the estimate and merge lines run in a real shell with a fake `infracost` and `curl`: the four fields and the key reaching the tool, six ways to have no estimate that all end well with no file, and the summary posted with and without a cost, including an empty and an unreadable `cost.json`) and 6 in `mr-plan.test.ts` (a tag's limit estimates only its stack, the organization's limit every stack, no limit or another organization's or an unmatched tag nothing, no image plans without an estimate, a bad image is named in the note, a drift check has none).

## 2026-10-19 COST-5
- Built: **the merge request note** (`apps/api/src/mr-note.ts`): after the policy block, `Cost (estimate):` with a line per stack that has a view: `+42.00 USD a month, total 1234.50 USD (estimate by `infracost`); limit 100.00 USD: warn (`cost-near-limit`)`, or `no estimate; limit ...: deny (`cost-unavailable`)`, or `...; no limit`. Figures are `toFixed(2)` with an explicit sign on the delta; the tool and rule names are in code spans, the currencies and stack names go through `plain()`; no resource address is shown. `NoteView.limits` is optional (a caller that passes none shows each estimate with no verdict); `writeNote` reads `allCostLimits` in the merge request's transaction, so the note says what the limits are when it is written. **The view** (`apps/api/src/cost-view.ts`, new): `costViewOf(stack, limits)` judges as the apply does (`judge(costVerdict(limitFor(limits, tags), estimate))`) and returns `{estimate, limit, verdict, rules}`; null for a stack nobody has summarized (its estimator may still run, so "unavailable" would be premature) and for a stack with neither an estimate nor a limit. The limit is copied field by field (tag, maximum, warn-at, currency): a row from the database also has an id and an organization. **The run API** (`apps/api/src/routes/runs.ts`): each stack of a run has `cost` (null or the view); list, get and the apply's answer read the organization's limits once per request, create passes none (a new run has no summary). `docs/openapi.json` regenerated. `policyLine` and the cost line share one rule-name formatter (a few names, then "and N more").
- Migration 0036 (additive): `run_stacks.tags text[] not null default '{}'`, the stack tags of the commit as `mr-plan` scanned it (`createRun` takes `tags`, a map of stack to tags). Needed because the limit that applies depends on a stack's tags and a run's stack had none, so a note or an API answer could not tell which limit to show. The apply still rescans at apply time and judges with the tags it finds then.
- Decision: the note and the API show the verdict **now**, from the limits in force when it is written or read, as the apply computes it (COST-3's decision). The note is rewritten on each run event, not when a limit changes, so a note can be older than the limits; the API answer cannot. A tag dropped or added between the plan and the apply can make the apply judge with a different limit than the one shown (docs, COST-6).
- Decision: the note uses `costVerdict` and not `planVerdict`: the policy block above already shows the policy's part, and the apply keeps `policy_denied` and `cost_denied` apart. `planVerdict` stays a pure core function with its tests; production code does not call it (COST-3's follow-up said COST-5 would; it does not need to).
- Tests: 6 in `mr-note.test.ts` (pass, warn, deny, unavailable and a saving in one snapshot; an estimate with no limit, a limit with no estimate yet; a currency that is not the limit's; a tag's own limit; a tool and currency that try to be markdown, with no link outside a code span and no heading; an integration test: the note says "no limit", then a limit is set and the next write says deny, and another organization's limit changes nothing), 2 in `runs.test.ts` (the view per stack with a tag limit, the organization's and none; list equals get; a raised limit changes the verdict on the next read; an estimate with no limit; a limit with no estimate; none: null; an organization's limits do not reach another's), 1 in `db/runs.test.ts` (tags kept and default), 5 in `cost-view.test.ts`, and `mr-plan.test.ts` keeps the run's tags.
