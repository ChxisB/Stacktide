## 2026-10-19 Feature 20 review (once over the whole feature, not per task)

### `/security-review`: one High finding, fixed test-first
- **The link was a GET (`/auth/sso/:slug/login?link=1`), so another site could start it in a signed-in person's browser** (the session cookie is `SameSite=Lax`, which a cross-site top-level GET carries). An organization that runs its own provider could have sent a victim there, and the victim's account would have been linked to an identity that provider controls: whoever runs a provider can then sign in as them, with their GitLab roles. Cross-tenant account takeover. **This supersedes the SSO-7 entry above**, which describes the GET.
- **Fix:** the link starts with **`POST /auth/sso/:slug/link`**, answers `200 {location}` and sets the flow cookie, and needs the live session cookie (401 otherwise, and the provider is not asked). A browser-started cross-site POST cannot carry the Lax cookie, and the API's 415 on a non-JSON body stops a cross-site form post. The web page makes the call with `fetch` (no body) and then navigates to `location`. `?link=1` on the login route is now ignored. The route is `public:` (own 401), `noAudit:` (the link is audited as `identity.link` when the callback completes it), rate-limited as `login`.
- **Proof:** new tests in `sso-login.test.ts` (a GET never starts a link; a POST from someone signed in does; no provider or one turned off is 404) and `identities.test.tsx` (the page asks the API and goes where it says; the API's 404 is shown in the page and the browser stays). Three mutations were run and caught. Route lists (`authz.test.ts`), `docs/openapi.json`, `docs/sso.md` and ADR-0016 decision 8 are updated.
- **Residual risk, not fixed, an open decision for you:** a person who deliberately links a hostile organization's provider hands that provider their account. The real remedy is **provider-scoped sessions**: a session started by a provider carries only that provider's roles (no GitLab roles, no platform admin) and cannot create API tokens or manage identities. That reverses ADR-0016 decision 7 (higher of GitLab's and the provider's role), so I did not build it. The page warns in plain words ("Link only a provider you trust: whoever runs it can sign in as you"), as does `docs/sso.md`.
- A web test ("giving one up…") failed once at 19 s under load and passed on rerun: a load flake to watch.

### `/code-review`: 14 findings, unverified (the reviewer ran nothing)
Fixed, each test-first (red, then green):
- **#2 username/name overwrite.** `signInSso` replaced `users.username`/`name` with the provider's values on every sign-in, including for a person who also signs in with GitLab: a provider could rename a GitLab person to a colleague's name in audit labels and the member list. Now a person with a `gitlab` identity keeps GitLab's values (`packages/db/src/sso.test.ts`).
- **#5 `ORCH_SSO_REDIRECT_URI`.** Now must be `https` (http only for `localhost`, `127.0.0.1`, `[::1]`) and end exactly in `/auth/sso/callback`, or the API refuses to start, naming the key and never echoing the value (`auth-config.test.ts`). Docs updated.
- **#8 `/auth/me.platformAdmin`.** Computed from `principal`, which a bearer token can make someone else's; it now counts only when the principal is the cookie's own person (`authz.test.ts`, a call with alice's cookie authenticated as the platform admin).
- **#11 duplicate role rules.** `roleMap` refuses the same `claim`+`value` twice, whatever the roles (`packages/core/src/sso.test.ts`). This also gives the web table unique row keys.
- **#13 index.** Migration **0045** adds `sso_memberships_provider_idx` on `sso_provider_id` (the primary key leads with `user_id`); a db test reads `pg_indexes`.
- **#3 `gitlabGroupId`.** My first fix (make the web field optional) was wrong and I reverted it: the API has accepted an organization with no group since before this feature, but **nobody holds a role in such an organization** (roles come from the group or a provider, and only an owner can set a provider up), so a group-less organization can't be started. The web form keeps asking for the group, its comment and `docs/sso.md` now say why, and this LOG's "optional GitLab group id" (SSO-6 entry) means the API only. **Open decision:** an SSO-only organization has no way to get its first owner; the choices are to let a platform admin hold `sso.manage`, or to require the group in the API. Not built (it changes the auth model).

Declined or accepted as limits, with reasons:
- **#1 `email_verified` and nested claims** (Entra leaves `email_verified` out; Keycloak's `realm_access.roles` is nested): both are ADR-0016 decisions (6 and the role map's exact-match rule), accepted. Now written down in `docs/sso.md` ("what the provider's token must carry"). The first real provider sign-in is a human gate.
- **#4 membership not tied to the session / logout doesn't end it:** ADR-0016 accepts the 12-hour window and the SSO-7 entry already lists it. The code comments say "for as long as the session lasts"; the docs now say plainly that logout does not end the role early.
- **#6 deleting a provider leaves its people as accounts with no way in:** their roles go with the memberships and they hold nothing; documented. No cascade of users (it would delete audit-attributed people).
- **#7 flow cookie not cleared on error exits:** I proposed fixing it before and **reverse that**. The cookie holds `state`, the verifier and the nonce for at most 10 minutes; the authorization code is single-use at the provider, a new login overwrites the cookie, and the GitLab flow behaves the same. A replay needs the victim's own browser cookie and a valid code, which gives an attacker nothing. Not a vulnerability; left.
- **#9 one extra indexed query per authenticated request** (`ssoRolesOf`): deliberate (a provider turned off must give no role at once); recorded in SSO-4. Upgrade: cache per request or skip when no provider is enabled.
- **#10 discovery uncached on an unauthenticated route:** a shortcut recorded in SSO-3 (keys are cached); throttled by the login rate limit. Upgrade: cache discovery for a short time.
- **#12 four copies of cookie → `findSession`:** each has a different follow-up; a helper would be a refactor with no behaviour change. Left.
- **#14 `keySets` never evicted:** one small entry per key-set address a provider has used since start; bounded by providers. Documented.

Not run: a real provider; the Playwright journey (no browser). The reviewers ran nothing; the security finding's exploit path was confirmed by reading the code and by the new tests that fail without the fix.
