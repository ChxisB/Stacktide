# 12 Extra Sync Targets - Log

## 2026-10-18 EXT-1
- **What:** three more connection types, each checked against its real system before it is stored, with one secret sealed per connection and everything else in the open. ADR `docs/adr/0013-target-credentials.md` (Proposed, covers the invariant-3 exception and why runner-side sync was not the first build).
  - `aws_assume_role`: config `{roleArn, region}`, secret = the external ID. The platform's own AWS identity comes from `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` / `AWS_SESSION_TOKEN` (empty counts as unset); without it the type answers 503 `aws_identity_unavailable`. SigV4 is signed in `packages/sync/src/aws.ts` (checked against AWS's published vectors), only to `sts.<region>.amazonaws.com` built from the region. The check is `AssumeRole` (900 s, external ID) then `GetCallerIdentity`.
  - `kubernetes`: config `{server, namespaces[1..20], ca?}`, secret = a service-account token. The check is a `SelfSubjectAccessReview` per namespace and verb (get, list, create, update, delete) on Secrets.
  - `vault_approle`: config `{address, roleId, authMount, kvMount, prefix}`, secret = the AppRole secret ID. The check logs in, asks `capabilities-self` for the data and metadata paths under the prefix (`deny` beats everything, `root` is all) and revokes the client token.
  - `packages/sync/src/http.ts`: one `send` for all of them (no redirects, 10 s deadline, 1 MiB body cap, failures reduced to a reason) and `httpsOrigin` (https, no credentials, path, query or fragment).
  - Routes: `POST /organizations/:orgId/connections` accepts the three types as more variants of the discriminated union; a loopback `server`/`address` is refused (`base_url_refused`) unless the app allows it; a failing check is 422 `connection_test_failed` with fixed words and nothing stored; the `/test` route re-checks with the stored secret and audits `{ok, reason?}`. The audit row of a create leaves out the `ca` (a chain is longer than an audit value may be).
  - `checkCloud` in `apps/api/src/connections.ts`; `openAnyConnection` (the GitLab opener is now a type check on top); `AppDeps.cloud` (fetch and AWS identity seam, for tests and `index.ts`). The web connection test shows the `summary` of a non-GitLab answer.
- **Deviation from the TASKS wording:** type names use underscores (`aws_assume_role`, `vault_approle`) because `connections.type` is CHECKed `[a-z][a-z0-9_]*`.
- **Tests:** 6 http, 20 aws (3 AWS-published SigV4 vectors, a session token, a fake STS, canary leak checks, matrices), 12 kubernetes, 12 vault, and 32 API tests (per kind: sealed at rest and absent from the row, list, audit and logs; re-check on `/test`; refusals store nothing; 401 on a stored connection is an answer, not an error; members get 403; no master key 503; a stale stored config is 422; loopback matrix; CA kept, trusted and not audited; GitLab opener refuses another type).
- **Mutations:** 29 (`run99`) on the trust boundaries: redirects, body cap, timeout, https/credentials/path checks, ARN and external-ID rules, body hashing, who is blamed for an identity refusal, the assumed-role ARN match, the Kubernetes verb list, `allowed === true`, the CA, namespaces, Vault token revoke, `deny`/`root`/list/delete, the 400 login, dotted prefixes, loopback refusal, the `ca` audit strip, stored-on-failure, a secret in the open config, stale-config handling and the missing AWS identity. 28 killed first run; **E18 (`deny` ignored) survived** because the test used a path that had no other capabilities, so the test now gives the path every capability plus `deny`, and E18 is killed.
- `/code-review` (medium): 10 findings. **Fixed:** an empty `AWS_*` variable stopped the API from starting (now an unset identity); a stored config that no longer parses was a 500 (now 422 `connection_config`, `checkCloud` is async); a refusal of the identity call made with the just-assumed role blamed the platform's identity (now `unexpected`); the Vault login message now says the auth mount may be the problem; the prefix message said "without dots" when it means "not starting with a dot". **Not changed:** the SSRF guard is literal loopback only (private clusters are legitimate targets; see REVIEW); the loopback guard is create-only, as GitLab's already is; sequential namespace checks are bounded by the first failure (a timeout throws at once), only a slow-but-answering server stacks; `testGitlab` has no injected fetch, as before; `testSchema` is a plain union, the response is an allow-list.
- Inline security review: the secret is read only by `openConnection`/`prepare`, sealed by `createConnection`, and passed to the check functions and nowhere else; no route response, list, audit row or log line has it (canary tests through every kind, including the create body echoed on a 422); the platform's base AWS secret is never sent (only used to sign) and a test asserts that; error text is built from fixed words, never from the system's reply, the URL or the config; redirects are not followed, so a credential is never replayed at an address an answer names; `https` only, which also keeps the cloud metadata endpoint (http) out of reach; the Vault client token is revoked even when the check fails.
- **REVIEW (design gates, not decided by me):**
  1. **The ADR is "Proposed".** It records the invariant-3 exception; nothing here is agreed until you accept it. It also records why runner-side sync (CI job with OIDC) was not the first build and that the adapters' `Remote` seam would serve it.
  2. **Nothing has talked to a real STS, API server or Vault.** All checks are tested against contract-level fakes written from the vendors' documentation; the Vault `capabilities-self` response shape and the Kubernetes review are the likeliest to differ.
  3. **The platform's AWS identity is a static key pair from the environment** (no IRSA, ECS or IMDS refresh). That is a held credential too; it should be allowed only `sts:AssumeRole`.
  4. Commercial `aws` partition only; the Kubernetes `server` is an origin (no Rancher-style path); Vault has no Enterprise namespace or nested mount. Each is a `shortcut:` comment in its schema.
  5. **SSRF:** only literal loopback hosts are refused. Private ranges and DNS rebinding are open, and a `/test` reason (`network`, `timeout`, `not_found`) lets an org admin probe from the platform's network. Org-admin only, as for GitLab connections.
  6. The Kubernetes check cannot tell cluster-wide secret access from a namespaced token; RBAC is the limit and the namespace list is enforced by the adapter (EXT-4).
  7. Whether Vault's `delete` capability is enough for prune (KV v2 soft-deletes; destroying versions needs `destroy`) is decided in EXT-5.
  8. Type names use underscores (see Deviation).
  9. The key-rewrap job (master key rotation) must also cover these sealed secrets; it does not exist yet.
  10. `GET` lists connections of any type; there is **no UI, CLI or api-client support** for creating the new types (the web only shows a `summary` for a test).
  11. The `/test` and any later use do not re-apply the loopback refusal (create only); a connection created with `loopbackConnections` and moved to a production app would be reached.
  12. Other `ok: true` test answers now have a `summary` and no `user`; the OpenAPI response is a plain union.
  13. Equivalent/untested: the revoke-self failure is swallowed by design (tested); the 10 s revoke adds up to another deadline after a slow check.
- One flake seen in the first gate (`membership.test.ts`, "every GitLab error kind fails closed"), not touched by this task; passes alone three times and in the next full gate.

## 2026-10-18 EXT-2
- **What:** the `aws-ssm` sync target, AWS Systems Manager Parameter Store under one path prefix, reached through an `aws_assume_role` connection. Docs: `docs/aws-targets.md` (config, the role's IAM permissions, limits).
  - `packages/sync/src/aws-ssm.ts`: `awsSsmAdapter(session, deps)`, config `{region, prefix, kmsKeyId?, protected?}`. A key at scope `*` is `<prefix>/<KEY>`, in another scope `<prefix>/<scope>/<KEY>`; a secret is a `SecureString` (with `kmsKeyId` if set), anything else a `String`. Standard tier, 4096 **bytes**, `{{ }}` refused, file variables `unsupported`.
  - **Ownership:** every parameter it creates carries the tag `orch-managed=<prefix>`. `read` lists only parameters that match `Path` (recursive) **and** `tag:orch-managed=<prefix>`; `update` and `delete` call `ListTagsForResource` first and answer `not_found` unless the tag matches; `create` never sets `Overwrite` (it cannot be combined with `Tags`) and answers `exists`, so a hand-made parameter or one of another target under an overlapping prefix is never listed, overwritten, adopted or pruned.
  - `packages/sync/src/aws-json.ts`: `awsJson` (signed JSON 1.1 call to `<service>.<region>.amazonaws.com`, the host built from the region only), `AwsApiError` (reason plus AWS's error name, a plain word; AWS's message is dropped), `assumedSession` (the role's credentials asked for on first use and again 60 s before they lapse; callers that arrive together share one request; a failed request is not remembered).
  - `packages/sync/src/fake-aws.ts` (exported from `@orch/sync/testing`): STS and SSM contract fake that re-signs every request, expires the role's credentials after 900 s, refuses the platform's own identity on SSM, and puts text in every error message so a client that passes AWS's words on is caught.
  - API: `TARGET_TYPES['aws-ssm'] = {connection: 'aws_assume_role', validate}` (so the `type` enum in OpenAPI grew; regenerated); `openTarget` is now a switch on the type; `openAwsSession` in `connections.ts` (checks the connection type again, needs the platform identity or answers 503 `aws_identity_unavailable`); `cloud` is threaded through plan, apply, auto-sync, drift and the worker (`worker-main.ts` loads the `AWS_*` env too). `isProtected(config)` replaces the GitLab-only `protected === true`, in the planner and in `pipeline-validate` (which used to skip every target that was not `gitlab-variables`).
- **Tests:** 46 adapter (the shared conformance suite against the fake, plus targeted: mapping, tiers and sizes, tagging, never-touch matrix, paging, races, failures in fixed words, credentials lifecycle, region, canaries), 9 API integration (`sync-cloud.test.ts`: plan→apply→re-plan is all no-ops, prune leaves hand-made and other-prefix parameters alone, a clash fails the line with the tag to add, update bumps the version and keeps the tag, no platform identity sends nothing, a role that does not trust the external ID is 502 with fixed words, wrong connection type/org/config refused at creation and at open, nothing secret in responses/rows/audit/jobs/logs), 1 pipeline-validate (an AWS target is judged by its `protected` flag), 1 `isProtected` and the registry list.
- **Mutations:** 25 (`run100`) on ownership (tag key and value compared, update/delete checks, create overwrite, read filter, tag value), decryption, paging, error mapping, `{{ }}`, size by bytes, name checks, the believed error word, credential refresh/sharing/failure memory, `isProtected`, the planner's use of it, pipeline validation of unknown types and the connection-type check at open. 24 killed first run; **F11 (a delete racing the ownership check is `not_found`) survived**, so a test now deletes the parameter between the two calls, and F11 is killed.
- `/code-review` (medium): 9 findings. **Fixed:** `pipeline-validate` skipped every non-GitLab target (an unprotected `aws-ssm` target mapped to production passed the pipeline check but failed the plan); the size limit counted UTF-16 units, not bytes; `assumedSession` let concurrent callers each assume the role; an unlisted-shape comment on `itemOf` (the deeper-tagged case was already tested as "left alone"). **Not changed:** the timeout finding is wrong (`send` has a 10 s default); throttling retry is a `shortcut:` in `awsJson`; the check-then-write race and type-change on overwrite are REVIEW items below; the missing `ssm:ListTagsForResource` surfaces at plan/apply, documented with the IAM table; the target registry holds no per-type `isProtected` because every config carries the flag in the same place.
- Inline security review: the external ID and the platform's secret key are used to sign and to assume only, never sent to SSM (asserted); the role's keys live in one closure; AWS's reply text never reaches an error (a fixed phrase plus AWS's error name, matched against `^[A-Za-z]{1,64}$`); the host is built from a validated region; values go only in the body of signed HTTPS calls; names are built from validated parts (no `/`, no dot-only parts), so a key cannot climb out of the prefix; the target's connection must belong to the organization and be an `aws_assume_role` one at open time as well as at creation (a gitlab token is never used as an external ID).
- **REVIEW (design gates and facts I could not verify):**
  1. **Real SSM was never called.** The fake mirrors my reading of AWS's documentation. Unverified: `Overwrite` when the type changes (String to SecureString), the `{{ }}` rule, `Path` + `tag:` in one `DescribeParameters`, throughput limits and `TooManyUpdates`, `ListTagsForResource` on a missing parameter (`InvalidResourceId`).
  2. Standard tier only (4096 bytes); advanced-tier values and policies are out.
  3. One extra `ListTagsForResource` per update and delete, and **a check-then-write race**: a parameter replaced by an untagged one between the check and the `Overwrite` is overwritten. SSM has no conditional put.
  4. Ownership is a tag any holder of `ssm:AddTagsToResource` can set: it is not a security boundary against someone with access to the account, only against the platform's own plans. A parameter made by hand is managed only once tagged `orch-managed=<prefix>` (until then `create` answers `exists`).
  5. Scopes are path segments: a scope containing `*` (such as `review/*`) is unsupported; the first prefix level may not start with `aws` or `ssm`; at most 13 prefix levels; 10 000 parameters per prefix; reads are sequential, 10 names at a time; no retry on throttling.
  6. `protected: true` means nothing to AWS; it is the owner's claim that IAM guards the prefix, so the production guardrail lets a production scope through. Pipeline validation now applies the rule to AWS targets too.
  7. The role needs `ssm:PutParameter`, `AddTagsToResource`, `GetParameters`, `ListTagsForResource`, `DeleteParameter` on the prefix, `DescribeParameters` on `*`, and `kms:Decrypt`/`GenerateDataKey` for secrets. The connection test proves only that the role can be assumed; a missing permission shows at plan/apply.
  8. The platform's own AWS identity is still a static key pair in the environment, and **the worker needs the same `AWS_*` env as the API** (both load it).
  9. Error messages contain AWS's error name (a service-defined word, `AccessDeniedException`), never AWS's message.
  10. `worker-main.ts` wiring of `cloud` into the three sync handlers is not covered by a test (the entry point is not unit-tested), the same class as POL-4's D1/D2.
  11. No UI, CLI or api-client support for choosing the `aws-ssm` type; the API accepts it.

## 2026-10-18 EXT-3
- **What:** the `aws-sm` sync target, AWS Secrets Manager under one name prefix, reached through the same `aws_assume_role` connection as `aws-ssm`. Docs: a new section in `docs/aws-targets.md` (config, layouts, tags, role permissions, limits).
  - `packages/sync/src/aws-sm.ts`: `awsSmAdapter(session, deps)`, config `{region, prefix, layout?: per-key | per-scope, kmsKeyId?, protected?}`. **`per-key`** (the default and it stays the default): one secret per item, `<prefix>/<KEY>` or `<prefix>/<scope>/<KEY>`, the secret is the value. **`per-scope`**: one secret per scope, `<prefix>/<scope>` (`<prefix>/_` for `*`), holding a JSON object; a write reads the object and puts it back with only its own key changed (other keys stay).
  - **Secret or plain:** Secrets Manager encrypts everything, so the flag is a tag `orch-plain:<KEY>` on a key that is *not* a secret (round trips exactly, so a plain item does not plan an update forever; the API test re-plans to all no-ops).
  - **Ownership:** every secret carries `orch-managed=<prefix>` and `orch-layout=<layout>`. `read` lists with the `name` and `tag-key` filters (prefix matches) and checks name shape, deletion and both tags again on the client; `update` and `delete` `DescribeSecret` first and answer `not_found` unless both tags match; `create` answers `exists` (also when `CreateSecret` races a hand-made one). The layout tag keeps the two layouts from reading each other's secrets.
  - **Versions:** a new value is a new version with a fresh random `ClientRequestToken` (so an old value written again takes `AWSCURRENT` back); reads ask for `AWSCURRENT` only, so `AWSPENDING` is never a value.
  - **Delete = scheduled deletion with the 30 day recovery window** (never `ForceDeleteWithoutRecovery`). Per-key: creating the key again inside the window restores the secret (`RestoreSecret`) and puts the value in, only when it is ours. Per-scope: the key leaves the object, the secret stays (`{}` when empty), then the plain tag is removed.
  - Sizes by bytes (1..65536; a per-scope secret's whole JSON is checked on every put and on the first create); names: a key and a scope are 1..100 of `[A-Za-z0-9_.-]` (not dots only), the name's last part may not look like an ARN suffix (hyphen + 6 characters), no scope `_` in the per-scope layout; `__proto__` and number-like keys survive (the object is read into a `Map`).
  - `packages/sync/src/aws-common.ts`: the region, prefix and KMS schemas, `label` and `failed` (fixed words plus AWS's error name) now shared by both AWS adapters; `fake-aws.ts` gained a Secrets Manager contract fake (versions and staging, token idempotency, filters, paging, tags with the 50 limit, scheduled deletion, restore).
  - API: `TARGET_TYPES['aws-sm']` (the `type` enum in OpenAPI grew; regenerated), `openTarget` case.
- **Tests:** 81 adapter (the shared conformance suite for both layouts, plus per-layout mapping, tag round trip and flips, versions and staging, foreign secrets, listing re-checks, delete/restore and the races between each pair of calls, paging, size limits, binary secrets, failures per denied action in fixed words with no leak, credentials: one AssumeRole per sync and nothing sent to Secrets Manager but a signature), 4 API integration tests in `sync-cloud.test.ts` (per-key apply with prune and an all-noop re-plan, per-scope keeps hand-made keys, a foreign secret is not taken over, a denied list is 502 `target_failed`, bad layout 422, a GitLab connection 422), 1 registry test. The leak test now spans both AWS types.
- **Mutations:** 42 (`run101`) on both tags, the ownership check in write/delete, restore only when ours, create overwrite, the per-scope merge (other keys kept, key presence), the plain-tag logic both ways, the secret flag on read, force delete, recovery window, the random token, `__proto__`, the prefix/shape/deleted re-checks on read, paging, size by bytes and the per-scope size guard, KMS, error mapping, placement rules, `_` as `*`. 37 killed first run; **5 survivors**: G20 (shape ignored the prefix), G21 (deleted secrets listed), G26 (`ResourceExistsException` not mapped), G31 (delete ignored placement: a literal scope `_` would delete a key of the `*` secret), G38 (a per-scope secret of two levels was read). Each now has a test (listing with injected entries, a race between describe and create, scope `_`, an ARN-like name that carries our tags, a two-level tagged name) and all five are killed.
- `/code-review` (medium): 10 findings. **Fixed:** a refused read (`InvalidRequestException`) of any secret was skipped as "deleted"; now it is believed only when a `DescribeSecret` shows the secret gone or scheduled for deletion, and otherwise fails the read; the per-scope `CreateSecret` had no size guard (the JSON of a first key can be twice the value with escaping); the doc said 49 plain keys (48: two of the 50 tags are the ownership tags). **Kept, as REVIEW items:** the per-scope delete puts then untags (a failure between leaves a stale plain tag, harmless and counted against the 48); the ARN-like rule (see 9).
- Inline security review: no value or credential reaches an error or a log (messages are the key and scope, a fixed phrase and AWS's error name; a non-JSON per-scope secret is reported by name only, with the JSON parse error dropped); values travel only in signed HTTPS bodies; the external ID and the platform key sign and assume only, never reach Secrets Manager (asserted); names are built from validated parts, so a key cannot climb out of the prefix; the object is a `Map` so `__proto__` is data; `RecoveryWindowInDays: 30` is asserted and `ForceDeleteWithoutRecovery` never sent; the connection type is checked again at open.
- **REVIEW (design gates and facts I could not verify):**
  1. **Real Secrets Manager was never called.** The fake mirrors my reading of AWS's documentation. Unverified: the `ListSecrets` filter semantics (prefix match on `name` and `tag-key`), `RestoreSecret` behaviour, which cases give `InvalidRequestException`, tag limits, `ClientRequestToken` idempotency.
  2. The `secret` flag is a tag: anyone with `secretsmanager:TagResource` can change how a key is shown. Ownership tags `orch-managed` and `orch-layout` can be set by any account holder with the same permission; they are not a security boundary, only protection against the platform's own plans. A secret made by hand is managed only once tagged (until then `create` answers `exists`).
  3. **Delete semantics:** prune is a scheduled deletion with a 30 day recovery window, not an immediate one (so it can be undone in the console); the name stays taken meanwhile. Per-key: re-creating inside the window restores the secret by `RestoreSecret`, `TagResource` and `PutSecretValue` in turn, which is **not atomic**, and `kmsKeyId` is not applied on restore. Per-scope: a secret that is scheduled for deletion by someone else is refused with a message, never restored.
  4. Per-scope has **no compare-and-set**: the object is read, changed and put back, the last put wins; every key written is a new version of the whole secret. Per-key makes a version per write.
  5. A per-scope secret that carries our tags but does not hold a JSON object fails the **whole read** (loud on purpose, never "empty").
  6. At most 48 plain keys per secret (50 tags minus the two ownership tags); the 49th fails the run with `LimitExceededException`.
  7. The prefix rules come from SSM: no `/aws…` first level, at most 13 levels; a key and a scope 1..100 characters.
  8. One `GetSecretValue` per secret, sequentially, no throttle retry; up to 10 000 secrets under a prefix; text secrets only (a binary secret is skipped, not an item).
  9. The **ARN-like name rule** is stricter than AWS needs (AWS only asks): a key whose last part ends in hyphen + 6 characters (`db-passwd`, `MY-SECRET`) is refused as `invalid`, and a tagged secret of such a name is never listed or deleted. GitLab keys cannot contain a hyphen, so it matters for scopes (`feature-branch` in per-scope) and hand-made keys only.
  10. Changing `layout` on a target creates a **parallel set**: the old secrets stay, invisible to the new layout.
  11. The platform's own AWS identity is still a static key pair; the role needs `secretsmanager:CreateSecret`, `PutSecretValue`, `GetSecretValue`, `DescribeSecret`, `TagResource`, `UntagResource`, `DeleteSecret`, `RestoreSecret` on the prefix, `ListSecrets` on `*`, and KMS rights when `kmsKeyId` is a customer key; the connection test proves only that the role can be assumed.
  12. No UI, CLI or api-client support for choosing the `aws-sm` type; the API accepts it. The key-rewrap job (master key rotation) is still unbuilt for connections.
- Gate: `bun run check` green: 3744 pass + 1 skip (the opt-in real-GitLab run) + 0 fail (root), 240 pass (web). New dependencies: none.
