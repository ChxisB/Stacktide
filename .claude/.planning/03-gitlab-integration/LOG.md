# Log - 03 gitlab-integration

## 2026-10-17 GL-1
- `packages/gitlab` (`@orch/gitlab`): `createGitlabClient({baseUrl, auth, ...})` with `request(method, path, {query, body})` and `paginate(path, query)` (async generator), plus `GitlabError` with `kind` (`unauthorized | forbidden | not_found | conflict | invalid | rate_limited | server | timeout | network | unexpected`), `status` and `retryAfterMs`. Methods for projects, MRs, pipelines and variables (GL-2..4) build on these two calls. `request` returns `unknown` by default so callers must validate/map to domain types.
- **API notes checked against docs.gitlab.com** (no target instance is known yet, so the exact version is unverified; GL-5's opt-in real run is where that gets confirmed): offset pagination default 20 / max 100 `per_page`; keyset needs `pagination=keyset` + `order_by` + `sort`; the `Link` header carries `rel="next"` and is absent on the last page (keyset also sends `X-Next-Cursor`); a 429 carries `Retry-After` in seconds (the client also accepts an HTTP date) alongside `RateLimit-*`; auth is `PRIVATE-TOKEN` for personal/project/group tokens and `Authorization: Bearer` for OAuth.
- Behaviour: auth strategies `private-token` and `oauth`; per-attempt timeout (15s, covers the body read); up to 3 retries; 429 is retried for every method (the request was refused), 5xx/timeout/network only for GET/HEAD/PUT/DELETE (a POST may have been applied: its `timeout`/`network` errors mean "outcome unknown"); backoff 500ms x 2^n with jitter; a wait (Retry-After included) above 30s fails at once as `rate_limited` carrying `retryAfterMs` so the job queue can reschedule instead of blocking a worker.
- Safety: token is required, 8+ chars; `baseUrl` must be https (http only for loopback unless `allowInsecureHttp`), without embedded credentials; redirects are never followed (a custom auth header would survive a cross-host redirect); the error names where a redirect pointed (origin + path only); `Link: next` URLs are rebuilt on the configured origin and must stay under `/api/v4`; request paths cannot carry `?`, `#`, `\`, or dot segments and cannot change host; errors and logs carry method, path (never the query), status and GitLab's own short reason (truncated to 200 chars, HTML ignored) and every message passes through a token scrub. Tests assert the token never appears in any error message, stack, JSON or log line when GitLab echoes it back; breaking the scrub, the redirect mode or the POST-retry rule each fails a test (checked by mutation).
- Gate: `bun run check` green, 122 tests before review fixes, 125 after (38 in this package, a local `Bun.serve` fake, no network, backoff via an injected `sleep`).
- `/code-review` (medium) found 8; fixed: path with query/fragment/dot segments, `per_page: undefined` overriding the default, tiny tokens, redirect gave no hint, `Link` could leave the API path, unknown-outcome semantics documented. Not changed: PUT/DELETE are still retried after an ambiguous failure, because a replay changes the outcome only for DELETE (404 for what was already removed): callers (GL-4, SYNC) treat 404 on delete as already gone; documented in `client.ts`. Not done: 408/425 are `unexpected` rather than retried. The completion-doc finding refers to a home-directory CLAUDE.md rule; the factory writes one per feature (Phase 4), not per task.
- Security (inline; `/security-review` unusable, see FND-4): this is the token-handling surface. No new dependency. Open limits: a token echoed URL-encoded or transformed by GitLab would not be scrubbed (GitLab tokens are `[A-Za-z0-9_-]`, so encoding is the identity); `paginate` has no page cap beyond loop detection (the server is trusted); `GitlabError.status`/`kind` reach callers, who must not forward `message` blindly into API responses beyond what GL-6 decides.
- Follow-ups: GL-2..4 add the typed methods and the shared contract suite (GL-5); real-instance verification is opt-in via `GITLAB_E2E_URL`.

## 2026-10-17 GL-2
- `createGitlab(opts)` / `gitlabApi(client)` returns a `Gitlab` object: `projects.{list,get}`, `groups.{list,get}`, `repository.{tree,getFile,compare,createBranch,commitFiles}`, `mergeRequests.{create,get,update,createNote,updateNote}`. Responses are validated with zod and mapped to domain types (`Project`, `Group`, `TreeEntry`, `RepoFile` with decoded text, `Comparison` with paths and change kind only, `Branch`, `Commit`, `MergeRequest`, `Note`); a payload of the wrong shape becomes `GitlabError("unexpected")` naming field paths, never values. `projects.list` uses keyset pagination in id order so an import can be repeated; `tree` is recursive keyset. Project refs are a numeric id or a full path (encoded as one segment).
- **Invariant 6 at the choke point:** `commitFiles` looks up the project and refuses its default branch (also `refs/heads/<default>`) before any write. It is defence in depth only: the name is read just before the write, so the default branch must also be protected in GitLab (PIPE/GL-7 should check or set that). Costs one extra GET per commit. MRs can be created, edited, closed and reopened; merging is deliberately not offered.
- **Mock built here, finished in GL-5.** `@orch/gitlab/mock` (`createMockGitlab`) is an in-process `Bun.serve` fake with auth, keyset-style `Link` paging, a branch/file model, atomic commits, compare, MRs and notes; later GL tasks add their endpoints to it, GL-5 adds failure injection and the real-instance switch. `contract.ts` is the suite every target must satisfy; `mock.contract.test.ts` runs it against the mock. Contract writes only to `orch-contract-*` branches and closes the MRs it opens; it has no `deleteBranch`, so a real sandbox run leaves those branches behind (GL-5 documents or adds cleanup).
- **Mock fidelity is from docs and memory, not from a real instance.** Least certain, to confirm in GL-5's real run: tree of a non-existent `path` (mock: empty list; the reviewer believes 404), 409 for a second open MR on one branch, 400 for an MR with equal source and target, 400 for `start_branch` on an existing branch. GL-7 must treat both empty and 404 as "absent" until then.
- Gate: `bun run check` green, 144 tests (57 in this package). Mutations checked: guard disabled fails the contract and the unit test; a non-atomic mock commit fails the atomicity test.
- `/code-review` (medium) found 9; fixed: `refs/heads/` bypass of the guard and documented its limits, tree `type` and MR `state` now enums (a new value fails decoding instead of falling through a switch), mock `start_branch` on an existing branch and equal-branch MRs, contract cases for both. Not done: memoising the default-branch lookup (commits are rare), branch cleanup (see above), reopen-conflicts in the mock. Completion-doc finding is the home-directory CLAUDE.md rule; the factory writes one per feature.
- Security (inline): no new secrets handling beyond GL-1's client; file contents flow to callers, so GL-7 and PIPE must not log them; commit messages and paths are caller-supplied. New dependency: `zod` 4.6.7 (already pinned elsewhere).

## 2026-10-17 GL-3
- `Gitlab` gains `pipelines.{trigger,get,jobs,retry,cancel}` and `ci.lint`. `trigger(project, ref, variables?)` sends `variable_type` (`env_var` | `file`); `jobs` is a paginated generator. Pipeline and job `status` is an enum where an unfamiliar value reads as `unknown` (a status GitLab adds later does not fail the response); `isFinished(status)` is true only for `success | failed | canceled | skipped` (`manual`, `scheduled` and `unknown` are not final, so a poller needs its own deadline).
- **`ci.lint` returns a typed result** `{valid, errors[], warnings[], mergedYaml|null}`: invalid config is a normal result, not an exception. It uses `POST /projects/:id/ci/lint`, which needs GitLab 15.7+ per the docs (target version unknown, GL-5's real run confirms). `dryRun` and `ref` are passed through; the mock ignores them.
- **Secret-safe trigger variables.** New client option `request(..., {redact: string[]})`: those values (4+ characters) are removed from GitLab's reason text and from network error text before truncation, in one longest-first pass, also in their JSON-escaped spelling (an object reason is re-serialised). Only GitLab's words are scrubbed, so a value like `POST` cannot mangle the fixed part of the message. `trigger` passes every variable value. Known limit: values under 4 characters are not scrubbed (a replace that short would mangle messages), documented on `PipelineVariable.value`. Zod decode errors name field paths, never values (GL-2 test), so the response path needs no scrub.
- Mock: pipelines, jobs derived from `.gitlab-ci.yml` on the ref (`Bun.YAML.parse`), manual jobs, retry and cancel (a finished pipeline stays as it is), project CI lint; helpers `pipelineVariables(id)` and `finishPipeline(id, status)` for tests. Trigger variables are kept for tests only and never returned, as in GitLab. Contract cases (trigger/get/jobs/cancel/retry on a manual-only pipeline so no runner is used; unknown ref `invalid`; unknown pipeline `not_found`; lint valid, no-script, broken YAML) run against the mock now and the real sandbox in GL-5. The contract commits `.gitlab-ci.yml` only on `orch-contract-*` branches.
- **Mock fidelity unverified:** status after cancel/retry of a manual-only pipeline on a real instance, the exact error texts, 400 vs another code for a missing ref or CI file, and lint of `include:`/`extends:` (the mock returns the input as `merged_yaml` and does not resolve them). The contract asserts only what GitLab documents.
- Gate: `bun run check` green, 155 tests (68 in this package). Mutations checked: dropping `redact` fails two tests; scrubbing after truncation instead of before fails the span test.
- `/code-review` (medium) found 8; fixed: scrub after truncation and JSON-escaped values, sequential-replace mangling (single pass, reason text only), mock cancel/retry on finished pipelines, doc of the short-secret limit and of `isFinished`. Not done: mock lint resolving `include` (see above).
- Security (inline): handles pipeline variable values, which are secrets. They go only in the request body, never in URL, logs or `Pipeline` results; tested for results and errors. New dependency: none.

## 2026-10-17 GL-4
- `Gitlab.variables.{list,get,create,update,delete}` for `{project}` and `{group}` owners (`VariableOwner`), plus the pure `canMask(value, {raw})`. A variable is identified by `{key, scope}` (`scope` = `environment_scope`, default `*`); inputs carry `value`, `type` (`env_var | file`), `protected`, `masked`, `raw`, `scope`, `description`; `create` also takes `hidden` (masked and hidden, create-only). Keys are validated (`[A-Za-z0-9_]{1,255}`) before any request.
- **Values are secrets at the type level.** `CiVariable` is a class whose `value` is a getter over a private field: `JSON.stringify`, spread, `Object.keys` and `console.log` (`value: [Getter]`) never show it, so a variable passed to a logger or response cannot leak it by accident. `value` is `null` when the target hides it. Create/update pass the value to the client's `redact`, so an error that echoes it is scrubbed.
- **Exact-scope writes.** GitLab's docs say an update with a `filter[environment_scope]` that matches nothing falls back to a same-named variable of another scope. `get` therefore compares the returned scope with the requested one (`not_found` otherwise) and `update`/`delete` call it first, so a write can never land on the wrong scope. Costs one extra GET per write (a bulk sync of N changes is 2N requests: SYNC already holds the list and may need a trusted fast path if rate limits bite) and is not atomic: a concurrent writer between the GET and the write can still defeat it. Create and update also fail with `unexpected` when GitLab returns a different scope than asked (a Free-tier group silently ignores scopes; the variable then exists at `*`).
- **`canMask`** follows docs.gitlab.com/ci/variables: single line, no spaces, 8+ characters; when `$` references are expanded (`raw: false`) only letters, digits and `_ : @ - + . ~ = /`. It cannot check the "must not equal the name of an existing variable" rule. The contract suite creates masked variables for a table of values and requires the target to agree with `canMask`, so the opt-in real run verifies the rules. **`create` sends `raw: true` unless told otherwise**, because the fetched docs summary and a reviewer disagreed about GitLab's own default; our default does not depend on it.
- Mock: project and group variables with the documented validation (key, duplicate key+scope `invalid`, masking), pagination, hidden variables (value `null`), and the scope fallback on GET/PUT/DELETE. Contract: lifecycle for project and group, scope-qualified update/delete/move, a missing scope is `not_found` and touches nothing, `canMask` agreement; every variable is removed again (cleanup errors other than `not_found` fail the test).
- **Unverified against a real instance:** hidden variables (is the value `null`? can masking be un-set?), the update-without-value case, group `environment_scope` (Premium), error texts, the fallback on GET/DELETE (assumed), whether `raw`/`description` are accepted on the target version. `hidden` is covered only by the mock; the mock's PUT does not forbid un-masking a hidden variable.
- Gate: `bun run check` green, 173 tests (86 in this package). Mutations checked: no exact-scope check, no scope comparison, and a wrong `canMask` length each fail tests.
- `/code-review` (medium) found 7; fixed: `raw` default no longer assumed, mock GET falls back so the scope guard is exercised, wording of `update`, Free-group scope silently dropped, cleanup swallowing errors, helper order in the contract. Not changed: the extra GET and its race (documented above); mock PUT on hidden variables (unknown real behaviour).
- Security (inline): handles variable values. They are only in request bodies, never in URLs, logs or results' enumerable fields; leak tests for results (`JSON.stringify`, spread, inspect) and errors. New dependency: none. Real-instance writes remain the GL-5 human gate.

## 2026-10-17 GL-5
- **Mock finished.** Failure injection: `mock.inject({method?, path?, status, times?, retryAfter?})` answers matching requests with the given status (and a `Retry-After`), then runs out. It applies before the auth and `/api/v4` checks, like a failing proxy in front of GitLab. Tests (client retry behaviour against the mock): 429 waits for `Retry-After` then succeeds; a wait beyond the cap fails at once as `rate_limited` carrying the wait; a GET retries through 500s and gives up at the limit; a POST is not retried after a 500; an injection hits only what it matches and runs out. Servers are stopped in `afterEach`, so a failing test cannot leak one.
- **Branch cleanup.** New `repository.deleteBranch(project, name)` (strips `refs/heads/`, refuses the project's default branch client-side, DELETE otherwise; the mock also 404s a missing branch and closes the MRs from it). The contract suite tracks every `orch-contract-*` branch it makes and removes them in `afterAll` (a failed setup skips cleanup and shows its own error; `stop()` always runs; a removal other than `not_found` fails the run). Fixes GL-2's "contract leaves branches behind".
- **Real-instance run: documented, opt-in, NOT performed.** `real.contract.test.ts` runs the same contract against a real sandbox when `GITLAB_E2E_URL` is set (`readE2eConfig`: needs token, group, a project inside the group, and `GITLAB_E2E_ALLOW_WRITES=yes`; URL is trimmed, https is enforced by the client except loopback, errors never echo the token); otherwise it registers one skipped test. README "GitLab contract against a real instance" lists what it writes and how to run it. **The first write to a real GitLab is a human gate and has not happened**, so the mock's fidelity is still unverified: every "mock fidelity unverified" item in the GL-2, GL-3 and GL-4 entries stays open until someone runs it. Expect failing contract cases there; the fix is the mock.
- Known limits: the real run leaves cancelled pipelines (no delete API used); a run killed midway leaves `orch-contract-*` branches and `ORCH_CONTRACT_*` variables to delete by hand; group-level contract variables are inherited by every project in the group while they exist, so the group must be dedicated; the mock's 400 for deleting the default branch is unreachable through the client (its guard fires first), kept so a raw request matches GitLab.
- Gate: `bun run check` green, 183 pass + 1 skip (the real-instance placeholder). New dependency: none.
- `/code-review` (medium) found 9; fixed: cleanup on failed setup and `stop()` in a finally, `refs/heads/` stripped before the DELETE, URL trim, README cleanup claims, test-server leaks, injection-order documented. Not done: https requirement beyond the client's own check; a sandbox marker on the group (README warning instead); per-branch `getProject` in cleanup (one extra GET each, only in the opt-in run); exercising the mock's default-branch 400.
- Security (inline): the e2e token is read from the environment, passed only to the client, never logged or echoed. Variable values the contract writes are throwaway literals. No new secret handling.

## 2026-10-17 GL-6 (REVIEW: crypto / key handling, delete semantics)
- **Connections**: `/organizations/:orgId/connections` (`GET` paged, `POST`, `POST /:id/test`, `DELETE /:id`), all org-admin (`connection.create|read|test|delete` in the one `RULES` table). `POST` checks the token against GitLab first (`/user` for the account, `/personal_access_tokens/self` for scopes) and stores nothing on failure (422 `connection_test_failed`, fixed message per `GitlabErrorKind`, never GitLab's own text or the URL). A known scope list must contain `api` or `read_api`; an unknown one (older GitLab, other token kind) passes with `scopes: null`. `test` returns 200 with `{ok:false, reason, message}` for a failed test, and is audited because it uses the credential. No route returns the token; the response schema is explicit (`connectionDto`).
- **Crypto (ADR-0007, REVIEW):** one DEK per connection, wrapped by the current master key with context `connection:<id>`, stored as `dek_key_id` + `dek_wrapped`; `secret_enc` is AES-GCM under that DEK with AAD `aad("connection", organizationId, id)`. Ids are generated before the insert so the binding exists at seal time. `openConnection` is the only way back to the plaintext. Tests rebuild a row by hand to show the secret's binding and the DEK's binding each refuse on their own (a moved secret alone is already refused by the per-row DEK, so a single mutation of either binding survived until that test).
- **Config:** `ORCH_MASTER_KEYS` (newest first). Unset: warn at start, create/test answer 503 `secrets_unavailable`, list/delete work. Unparseable: the API refuses to start (message names positions, never key text; tested). A `CryptoError` while opening answers 500 `secret_unreadable` and logs only the code and connection id.
- **Delete semantics (REVIEW):** `connections.organization_id` is RESTRICT, so an org with connections cannot be deleted (409 `organization_not_empty`, message now "projects or connections"). Deleting a connection deletes its secret. `type` is free text with a CHECK so EXT adds types without a migration. Migration `0009_connections` is additive, with the `updated_at` trigger.
- **SSRF (known, partly mitigated):** an org admin chooses the URL the server calls with their token. Mitigations: https required (loopback http allowed by the client), no credentials in the URL, redirects not followed, 10 s timeout, one retry with waits above 2 s refused, only decoded fields returned, fixed failure texts. In production (`NODE_ENV` not development/test) literal loopback hosts (`localhost`, `*.localhost`, `127.*`, `[::1]`, `0.0.0.0`) are refused with 422 `base_url_refused`. **Not done:** a DNS name that resolves to loopback, private ranges, link-local and cloud metadata addresses are not blocked (self-managed GitLab lives on private ranges, so this needs an allowlist or resolve-and-check). Failure messages still tell an admin whether a host answered, so create/test work as a port probe against internal hosts.
- **Limits / follow-ups:** no update or token-rotation endpoint (delete + recreate; later FKs from sync targets will block deleting a connection that is in use, so a `connection.update` is needed before SYNC); `connection.read` is admin-only for now; no per-org cap or rate limit on create/test; create needs GitLab reachable; `/personal_access_tokens/self` behaviour for project/group tokens is unverified (mock only), hence best-effort scopes; a stored `config` without `baseUrl` (hand edit) is a generic 500 on test; the `test` audit row is written after the outbound call, so a database failure there loses the row but not the call. **Rewrap (VAR-3/OPS-4):** per-connection DEKs must be covered by the master-key rewrap job before an old master key is dropped, or those secrets become unreadable (`unknown_key`).
- Gate: `bun run check` green, 655 pass + 1 skip. Mutations (22 total, run13/run14): all killed except two accepted: a DEK shared across rows (not observable through the public API; the wrap context and AAD still bind each row) and a token added to the `test` response (the zod response schema strips unknown keys, so it never reaches the wire; the leak test scans every response).
- `/code-review` (medium) found 10; fixed: loopback in production, scope check (README claimed `read_api`), retry wait bound, `openConnection` selects through the `visible` projection plus the secret columns, ordering comment. Not changed: the SSRF allowlist (above), the missing update route, the audit-after-use order, `testSchema.reason` as a plain string, parsing the URL twice.
- Security (inline): handles a credential. The token appears only in the create request body, the sealed column and the outbound `PRIVATE-TOKEN` header; leak tests scan responses (including unparseable and wrong-shape bodies), the audit table and every log line, plus the 422/500 bodies. Audit metadata holds `{type, name, baseUrl}`, `{ok, reason}` and `{type, name}`. New dependency: none (`@orch/crypto` is a workspace package, added to `db` and `api`).
