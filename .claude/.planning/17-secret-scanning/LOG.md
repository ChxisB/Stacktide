## 2026-10-19 SCAN-1
- Built: `packages/core/src/secret-report.ts` (`parseSecretReport(text)`, exported from `@orch/core`) and its test.
- Fields read, from GitLab's secret-detection report format (`gl-secret-detection-report.json`; known from its documented schema, not fetched or checked against a real report): `vulnerabilities[]` with `id` (the fingerprint), `identifiers[]` (`type`, `value`: the `gitleaks_rule_id` one is the rule), `location.file`, `location.start_line`, `location.commit.sha`, `severity`; and `scan.status` and `scan.partial_scan` for completeness. **Never read:** `raw_source_code_extract` (an unsanitized excerpt of the secret), `description`, `details`, `solution`, `message`, the commit's author and message, `links`.
- Decisions: an allowlist builds each finding from named fields (no spread, no copy); every refusal is one of three reasons (`malformed`, `too_large` over 5 MB of text, `too_many` over 1000) and none carries the report's text; an entry without an id, a path or a commit is skipped and counted; the same id twice is one finding; a path with control characters is skipped; a rule that is not a lower-case slug reads as `unknown`. `complete` is true only for a scan with `status: "success"` and no `partial_scan`: only then can a finding's absence mean it is gone (SCAN-2 uses this).
- **Unverified assumption (human gate):** that GitLab's finding `id` stays the same for the same finding from one scan to the next. If it changes when a line moves, a moved finding reads as new and the old one as resolved (on the default branch, from a complete scan), and a dismissal is lost. The first real report is the check; the parser keeps nothing else to match on.
- Tests: `secret-report.test.ts`, 11 (the allowlist; a planted secret in every other field, listed and unknown, is absent; exactly the allowlisted keys; rule fallback; severity words; skipped entries; duplicates; completeness; malformed, too large and too many; a refusal never carries the text).
