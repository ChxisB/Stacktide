# 07 CLI - Log

## 2026-10-17 CLI-1
- New package `apps/cli` (`@orch/cli`, private; dependency `zod` only, already in the repo; `@orch/api-client` is added by CLI-2, the first task that calls the API). Files: `cli.ts` (router, `CliError`, `fieldsOf`, `parse`), `config.ts`, `project.ts`, `commands.ts` (empty record, each later task adds its commands), `main.ts` (entry, version read from `package.json`, which `bun build --compile` bundles).
- **Router decision:** hand-written split of the first word for the commands (`orch [--json] <command> ...`), and `node:util parseArgs` (strict, exported as `parse`) for each command's own options. No library: Bun/stdlib covers it, and a dependency would be bundled into a binary we ship. `runCli(argv, deps)` returns the exit code with io/env/cwd injected, so every command is tested without spawning anything. `--json` is global before a `--` (so a command option cannot take the value `--json`; `--option=--json` works) and belongs to the command after it, which `run -- cmd` needs. Exit codes: 0 ok, 1 failure, 2 usage.
- `cli:build` script: `bun build --compile` into `dist/orch` (run from `dist`, then removes the 61 MB copy of bun that this Bun version leaves in the working directory). `binary.test.ts` compiles the real binary into a temp directory and runs `--version`, `--json --version` and a bad command through it. Targets for the other platforms are CLI-7.
- Config file (`config.ts`): `$ORCH_CONFIG`, else `$XDG_CONFIG_HOME/orch/config.json`, else `~/.config/orch/config.json`; strict schema `{apiUrl?, token?}`. **Security:** a file that group/others can read or write, or that another user owns, is refused (like ssh), with the fix named and never the token; check and read use one open handle (no swap between them); saving goes to a new `<file>.<pid>.tmp` (any earlier file or link of that name is removed first, created `wx` mode 0600), is renamed over the config, and is removed again if the write fails; the directory is created 0700; unreadable, non-JSON and badly-shaped files are errors that name fields only.
- `.orch.json` (`project.ts`): nearest file upwards, ending at the git root when there is one (outside a repository it climbs to the filesystem root; a directory of that name is skipped). Strict `{organization?, project?, environment?}`, short non-empty strings: **it cannot name the API or hold a token**, so a cloned repository cannot send the user's token anywhere. Unknown keys are refused by name.
- Unexpected errors print only the error's kind (`unexpected error (TypeError)`), never its message: that message may hold a URL, a path or a token. Commands must turn expected failures into `CliError` with their own safe text.
- Tests: 35 (`cli.test.ts`, `config.test.ts`, `project.test.ts`, `binary.test.ts`).
- Mutations: 40 on the permission/ownership/atomic-write rules, the strict schemas, the git-root stop, the router (`--json` scope, prototype names, exit codes, leading `--`, tail) and the entry point. Found weak at first and strengthened (no source change): a stale temporary file with wide permissions, a non-ENOENT stat error, the search reaching the filesystem root, length limits on every `.orch.json` field. Survivors, all equivalent: `wx`→`w` (only differs if someone recreates the name between the removal and the open), file handle not closed (a leak no test can see), `path.join(".")`→`path[0]` (the schemas are flat).
- `/code-review` (medium) found 10. **Fixed:** token written into a stale/linked predictable temp file; temp file left behind when the write fails; unknown keys named by scraping a zod message (now `fieldsOf` on the issue code); stat and read not atomic and no ownership check; a directory called `.orch.json` taken as the file; `-- cmd` with no command silently dropped; unexpected-error text printed; unused `@orch/api-client` dependency; `.bun-build` leftover (script now cleans up). **Not changed:** `orch push --message --json` cannot pass `--json` as a value (documented, `=` form works); `orch --json` with no command prints the text help; the config and `.orch.json` loaders are not wired to a command yet (CLI-2/CLI-3 use them), so `orch --help` lists no commands.
- Inline security review: no network, no credentials read or written yet; the only secret this task touches is the token in the config file (handling above). Limits: `shortcut:` POSIX-only mode and owner checks; the parent directory of an existing config is not checked; `apiUrl` is accepted as any URL here, **CLI-2 must refuse a plain `http://` API except on loopback** before it sends a token; the token is stored in the clear in the 0600 file (no keychain).
- Gate: `bun run check` green, 2123 pass + 1 skip, 91 files. New dependency: none.

## 2026-10-17 CLI-2
- **REVIEW (auth-model addition, built to the approved SPEC):** the API had no way to get a token without a session, and tokens cannot mint tokens, so the CLI uses the OAuth loopback flow with PKCE (RFC 8252). `orch login` listens on `127.0.0.1:<random port>`, opens `GET /auth/cli?port&state&challenge`; with a session the API stores a one-time code (hash only, bound to the challenge, 2 minutes on the database clock) in the new `cli_logins` table (additive migration 0021, `user_id` → users CASCADE) and redirects to `http://127.0.0.1:<port>/callback?code&state`; without a session it goes through `/auth/login` and back. The CLI trades `code + verifier` at `POST /auth/cli/token` for a token. The token never travels through the browser. The code is taken (deleted) before the verifier is checked, so a wrong verifier burns it.
- API (`routes/cli.ts`): `GET /auth/whoami` (signed in; kind, id, scopes, environment; id is the token's id for a token), `GET /auth/cli` (public, not audited: a code changes nothing anyone can use), `POST /auth/cli/token` (public; audited `token.create` with `via: cli_login`, actor the code's user), `POST /auth/cli/logout` (a token revokes only itself; 403 for any other caller; audited `token.revoke`, `via: cli_logout`). Port is `^\d{4,5}$` in 1024–65535, state and challenge URL-safe with fixed lengths. DB: `createCliLogin` / `takeCliLogin` / `revokeApiTokenById` in `packages/db/src/auth.ts`. Test-only change: `cli_logins` added to the schema-convention test's documented list of append-only tables (rows are written once, then consumed, expire or cascade; no `updated_at` could ever change).
- CLI: `login` (browser, or `--with-token` reading stdin only, never the command line; verified with `whoami` before it is stored), `whoami` (text or `--json`; organizations via the list endpoint), `logout` (revokes on the server best-effort, always forgets the token here and says which). `api.ts`: `apiUrlOf` (https, or http for localhost/127.0.0.1/[::1] only; no credentials, path, query or fragment; error text never repeats the value), `resolveApi` (URL: flag > `ORCH_API_URL` > config; **a stored token is only sent to the origin that issued it**, `ORCH_TOKEN` goes wherever the URL says), `call` (network failure, 401 hint, problem `detail (code)`, and "does not look like an orch API" for a non-JSON answer; messages never include the request). Login progress and the URL go to stderr so `--json` stdout is one document. The callback listener answers `GET /callback` only; a wrong or missing `state` gets 400 and does not end the login; a second valid answer gets 410; an `error` (even alongside a code) or no code ends it. It is closed right after the answer is flushed. New dependencies: none (`@orch/api-client` and the dev-time `@orch/api`, `@orch/core`, `@orch/db`, `drizzle-orm` are already in the repo; the CLI itself re-implements 3 lines of sha256/base64url so the binary does not bundle `@orch/gitlab`; the end-to-end login tests fail if it ever differs from the server's `pkceChallenge`).
- Tests: DB 8 + 1, API 21 (+ updated authz/spec/route lists, `docs/openapi.json` regenerated), CLI 29 end-to-end against the real app in-process + `api.test.ts` + `open.test.ts`. The last test of `auth.test.ts` checks that no printed line anywhere contains any token or its secret half; the API test checks the plaintext token, code and verifier are in no DB row, audit row or log line.
- Mutations: 66 on the exchange (verifier check, hashing, burn on mismatch, expiry, pruning, TTL, challenge format), port/state/challenge validation, scopes/30-day TTL, audit actor and `via`, redirect host, cache headers, logout rules, the listener (state check, once only, error handling, bound to loopback), token format and verification, nothing printed, config save, `apiUrlOf` rules, token-bound-to-origin, `ORCH_TOKEN` priority, 204/network/401/non-JSON handling. First run left 6 alive; each got a test (port with leading zeros, a code issued must not touch codes still waiting, the listener unreachable on the machine's own network address, logout must not send a token to `http://0.0.0.0`, an error answer that also carries a code) and was then killed. The no-op control survived as it should.
- `/code-review` (medium) found 9. **Fixed:** none needed in source. **Rejected:** "the CLI token can mint tokens" (it cannot: tested, 403); route-to-route import of the token DTO (same as `pipeline-runs` → `pipeline`); two revoke functions (the by-id one has no owner check on purpose and says so); CLI's own sha256 helper (see above); the callback ending on a state-only request (the state is the proof it is the CLI's own browser; the listener is local). **Accepted, REVIEW:** `*` scope and 30 days for a CLI token (name default "orch cli", one per login, not per machine); `orch logout` forgets the token locally even when revoking fails and says so (the user can revoke it in the web UI or with `DELETE /tokens/:id` from a session); no rate limit on the public exchange (codes are 256 bits, 2-minute life, one try); the RFC 8252 loopback threat: until a consent page exists (feature 08 web UI) a page that sends a signed-in user's browser to `/auth/cli` makes the API issue a code to a listener on the user's own machine, so only a local process (another user on a shared machine) can use it; junk codes can be created that way and are pruned by the next login.
- Inline security review: secrets are the token and the code/verifier. Token: only in the 0600 config (CLI-1 rules) and one `Authorization` header to the origin that issued it; never in a message, `--json`, audit or log. Code: only its hash is stored; single use; the callback URL is the only place it appears besides the loopback listener. A denial at GitLab shows only in the browser (the API answers 401 JSON at `/auth/callback`), so the CLI keeps waiting until its 5-minute timeout or Ctrl-C; the CLI's `error=` handling is for the future consent page. Limits: whoami shows ids, not names; Windows `open` via rundll32 is untested; "does not look like an orch API" only checks that the answer is JSON; plain-http hand-edited configs are refused rather than followed.
- Gate: `bun run check` green, 2200 pass + 1 skip, 96 files.
