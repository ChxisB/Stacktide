## 2026-10-23 - BLP-14 the resources table - done
- Migration `0067_resources.sql` (additive, with the hand-written `resources_updated` trigger), `packages/db/src/schema/resources.ts`, `packages/db/src/resources.ts` (`upsertResource`, `getResource`, `listResources`, `resourceStates`), exported from `@orch/db`. A row is the platform's record of a proposal: `(environment, kind, name)`, `cloud`, `inputs` (the parsed blueprint), `stack`, `path`, `proposalUrl`. Whether the resource exists is never stored.
- **Two unique keys:** `resources_project_key` on `(project, environment, kind, name)`, so a database and a bucket may both be `main`; and `resources_project_stack_key` on `(project, stack)`, the backstop for the dash clash found at BLP-13. A check says `stack = environment-name-kind`, so the two cannot disagree. Other checks repeat the schema's part regex and 12-character cap, `safeDir` for `path` (no `..`, no space, no leading dash), an http(s) link of at most 2000 characters, and `inputs` at most 10000 characters of text. The `inputs` check is size only: the driver stores a jsonb object as a JSON string, so its shape is `BlueprintSchema`'s, as in `variable_rotations`.
- **Upsert:** a repeat proposal changes the row it made (inputs, path, link) and keeps its id. **Cloud is immutable:** a repeat on the other cloud returns `undefined` and changes nothing (the route will say 409); moving a resource between clouds is a new name and a delete, which is a plan (ADR-0024). A clashing stack name or a project of another organization is the database's refusal, named by constraint.
- **State (`resourceStates`, with `resourceStateOf` from the earlier part of this task):** read from `run_stacks` of the project's `plan` runs, never stored. The newest run decides (run ids are v7: the highest is the latest proposal, not the one that finished last), and a stack that was ever applied stays `ready` through a run that was only planned, discarded or canceled. A failed run shows `failed`, plan or apply (documented `shortcut:` in `resource-state.ts`). A scheduled drift plan counts for nothing. Two queries, both one row per asked-about stack, so a page of resources costs two reads. The map has every name asked about, in the order asked.
- **Index added to `run_stacks`:** `(project_id, stack, run_id)`. Its keys are `(run_id, stack)` and a partial one on `applying`, so the state read would have scanned a project's whole run history. Additive; no existing query changes.
- **Tests (26, `resources.test.ts`):** storing and repeat; other cloud refused and nothing changed; `main` as a database and a bucket; the dash clash refused by name; another project or organization may reuse names; a project of another organization refused; eleven kinds of bad row refused by the database; no link yet; list order and paging; an id from another project or organization finds nothing; cascade on project delete; state for every one of the eight run states on a fresh stack, then on an applied one (the five states that leave it `ready`, then failed, then applying); the newest run decides over the one that finished last; drift ignored; another project's same-named stack ignored; many stacks at once and none. **Mutation checks:** no same-cloud guard, oldest run first, drift counted, and the ever-applied set ignored each failed a test; the file was restored (26 pass).
