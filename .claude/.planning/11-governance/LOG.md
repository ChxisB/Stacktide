# 11 governance - LOG

## 2026-10-18 GOV-1
- **What:** an organization's audit log can be read, exported and kept for a set time.
  - `GET /organizations/:orgId/audit-events`: cursor-paged by event id, newest first. Filters: `action` (exact, or a family such as `variable.*`), `actorKind`, `actorId`, `resourceType`, `resourceId`, `projectId`, `since` (inclusive), `until` (exclusive).
  - `GET …/audit-events/export`: `format=json|csv`, up to 5000 rows (`EXPORT_MAX`), more by following the `x-next-cursor` header. `cache-control: no-store`, `content-disposition: attachment`. It is read **and audited in one transaction** (`audit.export`: format, rows handed out, the filters it was asked for).
  - `GET|PUT …/audit-retention`: days to keep (30 to 3650) or `null` for ever (the default). Reading is for org admins, setting it for an owner (`audit.retention.update`, metadata: new and previous days).
  - Permissions: `audit.read`, `audit.export`, `audit.retention.read` (org admin), `audit.retention.update` (org owner). A token needs the action by name.
- **Migration `0029_audit_retention.sql`** (additive, plus one trigger function replaced by hand, see REVIEW 1): `organizations.audit_retention_days` with a CHECK (null, or 30 to 3650), index `audit_events (organization_id, id)`.
  - `audit_events_immutable()` now lets a DELETE through only while the transaction-local setting `orch.audit_purge` is `on`. UPDATE and TRUNCATE are refused as before.
  - `audit_purge_expired(batch)` takes **no cutoff**: it works through the organizations that have a retention, oldest event first, one batch shared by all of them, and returns how many it took from each. It turns the setting on for its own DELETE and off again before it returns. Organizations with no retention, events of a deleted organization and events that name none are never touched.
- **Worker:** the `audit.purge` schedule (`AUDIT_PURGE_SECONDS`, default 3600, 0 = off, minimum 60). Each run does up to 20 rounds of 1000 and, in the same transaction as each round's delete, writes an `audit.purge` event per organization (actor `system/audit-purge`, metadata: count). The handler is registered only when the interval is above 0.
- **CSV:** one JSON cell for the metadata; a cell starting with `=`, `+`, `-`, `@`, tab or return gets a leading `'` so a spreadsheet does not run it; CRLF lines.
- Docs: `docs/audit.md`; `AUDIT_PURGE_SECONDS` in `.env.example`; `docs/openapi.json` regenerated (106 operations; route guard table 108).
- Tests: 17 db (`audit-log.test.ts`: listing, paging with equal timestamps, every filter incl. both window edges to the millisecond, `_` is not a wildcard, retention get/set/check, purge by own retention only, boundaries, batch size shared across organizations, bad batch, gone org and switched-off retention keep events, flag off after the call even in the same transaction and after commit on the same connection, UPDATE/TRUNCATE still refused while the flag is on), 21 api (`audit-log.test.ts`: permissions per role, stranger 404, org isolation, filters, paging, bad filters/cursors, no secret in a list or an export, token scopes for read, export and retention, export audited with its facts and `attachment`, CSV and formula neutralising, export paging, retention validation, a refused change records nothing, the purge job incl. its record, a backlog, and a purge whose record cannot be written leaves the events), 5 CSV unit tests (`audit-export.test.ts`), worker schedule (`worker-main.test.ts`).
- Mutations: 59 (`run94`) over the org filter, prefix match and its slice, cursor and order, both window edges, each filter, the four permissions and the guard on each route, retention bounds and strictness, the export's audit/count/filters/paging/cursor/headers, each CSV rule, the purge SQL (retention, own-org scope, DELETE-only flag, flag reset and lifetime, batch sharing, oldest first, bounds, age unit), the purge handler (full batch, record, org, same transaction) and the worker wiring. First pass left 8: **fixed by stronger tests** `since`/`until` edges, `resourceId` alone, `audit.retention.read` by token, `attachment`, the flag outliving the transaction on the same connection (pool of one), a purge that cannot be recorded. **One equivalent:** `|| 3600` becoming `|| 60` only changes the stored interval of a *disabled* schedule.
- `/code-review` (medium). **Fixed:** the purge ran one query over all organizations (now per organization, each delete a range of the new index); a batch was given to each organization instead of shared; the handler was registered even when the schedule is off; no test that UPDATE and TRUNCATE stay refused while the flag is on. Nothing was rejected.
- Inline security review: every query carries `organization_id` of the route's organization (mutation A1) and the guard answers 404 to a caller who cannot see the organization, so one organization cannot read or count another's events; an event holds ids, key names and counts only (`audit()` refuses a value on the way in), and the export's own filters go through `checkMetadata`; the export cannot be cached or rendered inline; CSV cells are inert; the cursor is a validated uuid and the organization filter is applied under it, so a cursor from another organization reveals nothing; the purge function takes a batch size and nothing else, so a caller cannot choose what to delete; the trigger still refuses UPDATE/TRUNCATE and a DELETE outside the function; no GitLab, cloud or key material is touched.
- **REVIEW (design gates, not decided by me):**
  1. **The append-only guarantee is now "against platform bugs", not "against whoever holds the database credentials".** The flag is a setting any session of the app's database role can turn on and then `DELETE`. Before 0029 a DELETE was impossible without dropping the trigger (also possible for the owner role, but louder). Forward the log elsewhere (GOV-4) for a copy the application cannot reach. Migration 0029 *replaces* the trigger function: a loosening, though additive in schema.
  2. **No grace period or preview when retention is lowered**: the first purge tick after the `PUT` deletes irreversibly (owner-only, audited with the previous value, minimum 30 days).
  3. One `audit.purge` event per organization per round (atomic with the delete, noisy on a large backlog), and those events age out like any other.
  4. The export cursor is not bound to the filters it was made with. An id is all it holds, so mixing is harmless, but a client can page one filter's cursor into another's.
  5. `since` after `until` gives an empty export, and it is still audited.
  6. The export's OpenAPI 200 is `z.string()` (it returns a raw response); the JSON shape is the list's.
  7. The CSV `'` prefix changes the data it guards; a leading space or a line feed is not treated.
  8. TypeScript does not validate `batch` (the SQL does, error 22023).
  9. Events of a deleted organization, or that name none, are never purged and are visible to no organization.
  10. An organization early in id order with a huge backlog can starve later ones within a run (the rounds are capped at 20 x 1000 and the next tick continues).
  11. Audit read is org-admin only (no auditor role); there is no UI viewer and no CLI or api-client method yet.
  12. `AUDIT_PURGE_SECONDS` is instance-wide.
  13. `worker-main.test.ts` queue expectations changed because a new always-on queue (`audit.purge`) exists; nothing weakened.
- Gate: `bun run check` green: 3331 pass + 1 skip (the opt-in real-GitLab run) + 0 fail (root), 240 pass (web). No new dependencies.

## 2026-10-18 GOV-2
- **What:** an environment can be **protected**; its own variables then change only through a **change request** that a maintainer other than the author approves. Doc: `docs/change-requests.md`.
  - `PUT …/environments/:envId/protection` (`environment.protect`, org admin; audit `environment.protection.update` with new and previous value). `protected` shows on the environment. Deleting a protected environment is `409 protected_environment`.
  - On a protected environment every write route of its own variables (create, update, delete, restore one, restore the level, import, bulk; dry runs and reads excepted) answers `409 change_request_required`. The check (`writable`) is the first statement of the write's transaction with the environment row `FOR SHARE`; protection switching, environment delete and approval take it `FOR UPDATE`, so none can slip between check and write.
  - `…/environments/:envId/change-requests`: list (status filter, paged), get, `POST` (`ops` = the bulk-edit steps, sealed), `POST /:crId/approve`, `POST /:crId/reject`. Actions `change_request.read` (project reporter), `.create` (developer), `.approve` and `.reject` (maintainer). Every answer shows key names and actions (`diff`), never a value.
  - Approval is one transaction: lock environment, lock request, check (open, not past its time, approver is not the author), open the sealed edits, plan them against the variables as they are now (refuse the whole request on `conflict`/`kind_mismatch`/a rename of a gone key; a delete of a gone key is done), apply as the approver via `bulkLevel` (reason `change request <id>`), close the request, write the audit rows (`change_request.approve` plus the ordinary `variable.*` rows with `source: change_request`, request id and author).
  - Identity: `Principal.userId` for sessions and API tokens, `personRef` = `user:<id>` so a person's session and token are one decider. The database enforces the same (`decided_by_ref <> author_ref`).
  - Worker: `change_request.expire` (`CHANGE_REQUEST_EXPIRE_SECONDS`, default 300, 0 = off, min 60): 10 rounds of 500, drops sealed values, writes `change_request.expire` per request in the same transaction. Registered only when on; needs no keys.
  - An environment holds at most 50 open requests (`409 too_many_change_requests`).
- **Migration `0030_change_requests.sql`** (additive): `environments.protected boolean default false`; table `change_requests` with CHECKs (kind, status, status open/approved ⇔ sealed edits present, four-eyes), composite FKs to environment+project and project+organization (cascade), indexes (environment/status/id; partial expiry). Two hand-written triggers: `set_updated_at`, and `change_requests_transition()` (closed rows frozen; only open→approved|applied|rejected|expired and approved→applied|expired; id, scope, kind, diff, author and expiry immutable; sealed edits only droppable), ERRCODE 55000.
- **Tests:** 36 db (`change-requests.test.ts`: sealing and AAD, scoping, approve/conflict/delete-gone/atomicity, turn-taking of approvals and of approve vs reject, expiry incl. skip-locked and order, state machine below the app, protection locks), 33 api (`change-requests.test.ts`: every write route refused on a protected environment, dry runs and reads pass, project/org level not gated, role matrix, self-approval by session/token/either way, audit trail incl. the GOV-1 list, conflict, expiry job incl. a failing audit, the cap, a write that began before protection turned on cannot slip past it, no marker value in any response or audit row), 3 core, 2 structural (`protection-coverage.test.ts`: only the allowed files write variables; the seven writing routes call `writable`), worker schedule.
- **Mutations:** 111 (`run95`) over approval checks, locks, scoping, AAD, protection gate on each of the seven routes, guards and RULES, cap, expiry, audit content, identity, wiring, SQL checks and trigger clauses. First pass left 12: **5 fixed by stronger tests** (a rejection under way vs an approval and the reverse, expiry of an `approved` request, `SKIP LOCKED` not waiting, oldest-first with the planner forced to scan). **7 equivalent:** AAD without project, without organization or `variable` instead of `change_request` (the data key is looked up per organization/project and ids are unique, so the AAD parts are defence in depth only); `level !== "environment"` in `writable` (project-level routes have no `envId`); the environment existence check on `POST` (the composite FK answers 404 instead); default interval `|| 300` of a disabled schedule; `project_id` in the immutable list of the trigger (the composite FK already pins it).
- `/code-review` (medium). **Fixed:** approval did not lock the environment (a direct write or another approval could change the variables between plan and apply); a delete of a key that was already gone counted as a conflict; no cap on open requests (each seals up to 1 MiB); no structural guard that new write paths honour protection. **Declined:** none.
- Inline security review: pending values are sealed with the project DEK under AAD bound to organization, project, environment and request id, so a blob moved elsewhere does not open; no value appears in the diff, any DTO, audit metadata or log (an API test scans every response and the whole audit table for markers); every query carries organization, project and environment, and the guard answers 404 to a stranger; approver ≠ author is checked in code and again by a row CHECK; closed requests are frozen by trigger; approval plans against current variables under an environment lock; no GitLab or cloud is touched.
- **REVIEW (design gates, not decided by me):**
  1. A protected environment **refuses** direct writes (409) instead of turning them into requests; clients must call the change-request API.
  2. Only the environment's **own** variables are gated. Org/project variables it inherits are not.
  3. Protection is enforced in the route handlers (`writable`), not by a DB trigger. `protection-coverage.test.ts` guards new write paths; a trigger would need an approval bypass flag like `orch.audit_purge`.
  4. Approvers see key names and actions, not values (upgrade: a reveal-pending endpoint gated on `secret.reveal`).
  5. Approval applies in the same transaction (no separate apply step; durable `approved` exists only for GOV-3 kinds).
  6. Fixed 7-day lifetime. A lapsed request reads `open` until the job runs (default ≤ 5 min); approve refuses it, reject still works and is how values are dropped. With the job off, lapsed requests keep their sealed values until rejected, and already-queued jobs are left.
  7. Cap of 50 open requests per environment, counted without a lock (concurrent proposals can pass it by a few).
  8. No author withdraw for developers (a maintainer author may reject their own); no title/reason field; protect/unprotect is org-admin only.
  9. The dev principal can never approve its own request, so four-eyes cannot be shown with `ORCH_DEV_AUTH`.
  10. Identity is `userId`: one person with a session and a token counts once, but two accounts of one human are not detected.
  11. A stale request is refused whole and must be proposed again.
  12. Approval plans twice (opens every secret of the level twice; `shortcut:` comment) while it holds the environment `FOR UPDATE`, which also blocks direct writes and other approvals there.
  13. `expiresAt` is computed on the app server and compared with DB `now()` (7 days, only gross skew matters).
  14. Pending values are sealed with the project DEK: the key-rewrap job (unbuilt for connections, variable keys, sinks) must include them.
  15. A request may be made for an unprotected environment (voluntary review).
  16. No UI, CLI or api-client methods yet.
  17. Always-on new worker queue changes `worker-main.test.ts` expectations; `session.test.ts` expects `userId` in the principal. Nothing weakened. The old conflict tests used "a delete of a gone key" as the conflict; it is now "a rename of a gone key", with new tests for the delete case (behaviour changed after review, disclosed).
- Gate: `bun run check` green: 3412 pass + 1 skip (the opt-in real-GitLab run) + 0 fail (root), 240 pass (web). No new dependencies.

## 2026-10-18 GOV-3
- **What:** applying a plan in a protected environment needs an **approval** from a maintainer other than whoever asked. Doc: `docs/change-requests.md` ("Approvals to apply").
  - Two new request kinds on the GOV-2 routes: `sync_apply` (`targetId`, `planId`) and `iac_apply` (`runId`, optional `stacks`; default the planned ones). Asked in the protected environment the apply is guarded by (`409 environment_not_protected`, `target_not_mapped`, `not_planned`, `plan_not_applicable`, `plan_expired`, `drift_run`). `POST` needs `change_request.create` (developer); approve/reject need a maintainer, and the approver is never the author.
  - **Approving applies nothing.** The request stays `approved` until an apply uses it: `consumeApproval` runs inside the apply's own claim transaction (row lock, oldest of the 20 newest covering, the tightest cover first), moves it to `applied`, and the apply audit row gains `changeRequestId`. A failed claim rolls the approval back, so it is not spent by an apply that does not start. One approval, one apply.
  - **What is gated:** a sync target whose `environmentMapping` names a protected environment (`applySyncRun`, the apply route, `@bot apply`, the merge handler); IaC stacks whose `stack.yml` `environment` is protected (`applyRun`, bound to run id + stack at its `planJobId`). Auto-sync/remediation does nothing for a gated target (info log); drift checks and plans are not gated.
  - **Revoke:** a maintainer may reject an `approved` apply request until an apply uses it. Variables requests keep the GOV-2 rule (approved ones cannot be rejected).
  - `apps/api/src/apply-approval.ts`: `protectedMappings`, `approvalRequired` (409 `approval_required`, names the environments, never a value).
- **Migration `0031_apply_approvals.sql`** (additive columns, replaced trigger function): `change_requests.subject_id uuid` + `subject jsonb` (`{targetId?, stacks?}`), `_subject_check` (`(kind='variables') = (subject_id is null)`), `_kind_check` widened, `_ops_check` (apply kinds carry no sealed edits), index `change_requests_subject_idx`; `change_requests_transition()` makes both subject columns immutable and allows `approved → rejected` for apply kinds only. Sealed edits column is untouched. No data is changed.
- **Tests:** 14 db (`approvals to apply`: store, approve, expiry, revoke, once-only, run/target/plan job binding, other project and other organization, tightest cover, lapsed/rejected, row lock under contention, trigger and CHECKs below the app), 12 sync (`a protected environment (GOV-3)`: ask → approve → apply once, one approval one apply, not spent by an apply that does not start, two applies at once, unprotected/unmapped/other project, asking rules incl. expired plan, a foreign-target approval, revoke, auto-sync), 8 + 5 IaC (`applyRun` gate: per-stack, subset, new plan job needs a new approval, merge handler, route 409/202 + audit, developer asks/maintainer approves, self-approval, revoke), 2 MR-command, existing tests unchanged (the IaC and MR-command harnesses gained an `environment`/`files` option).
- **Mutations:** 46 (`run96`): consume scoping (project, organization, run, target, plan job), row lock, spending, tightest cover, revoke, protection lookups, the sync and IaC gates, auto-sync skip, audit id, claim-transaction placement, route preconditions (unprotected, unmapped, unplanned, applied, expired plan, plan job in the subject), trigger and CHECK clauses. First pass left 4: **3 fixed by stronger tests** (G10 other organization, H2 approval for another target of the same plan, J7 expired plan at ask time; all killed on rerun). **1 equivalent:** G19 (a type guard whose absence the runtime throws on anyway).
- `/code-review` (medium). **Fixed:** consume could use a broader approval than needed (now the tightest cover first); an approved apply request could not be revoked; the ask route accepted an unprotected environment or a target that does not map it; approving an apply kind needed the variable keys. **Declined:** #3 a tamper-proof stack→environment binding (needs a server-side assignment; recorded as REVIEW 1).
- Inline security review: no secret is read, sealed or logged by this task (apply kinds hold no `ops_enc`; `diff` is key names/targets only); every query carries organization and project, and `consumeApproval` filters on both (mutants G9/G10 killed); approver ≠ author is the GOV-2 code check plus the row CHECK; the approval cannot be re-pointed (trigger freezes subject, kind, scope); the approval is spent in the same transaction as the claim, under a row lock, so two applies cannot share one; no GitLab or cloud is touched in tests (mock only).
- **Unrelated fix:** `notify.test.ts` ("each failure waits twice as long as the one before", POL-2) claimed its job at a fixed `NOW` of 2026-10-18 12:30:15 UTC while the job was queued at the real clock, so it passed only before that moment today and failed afterwards. It now starts its clock at the queued job's own `runAt` (+1 ms, the column keeps microseconds). No assertion was removed or loosened. The same fixed date appears in `stack-drift.test.ts` (api and db) and `notifications.test.ts`; those pass because they drive their own clock or pass explicit times.
- **REVIEW (design gates, not decided by me):**
  1. IaC gating follows the repo-declared `stack.yml` `environment`; an MR can remove it (GitLab MR approvals/CODEOWNERS are the other defence). A tamper-proof binding needs a server-side stack→environment assignment.
  2. The sync gate is conservative: any mapped protected environment gates every apply of the target.
  3. A request is anchored to the environment it was filed under, but serves whichever gating environment applies (approval roles are project-wide). For IaC the environment is not checked against the stacks at ask time, only that it is protected.
  4. Auto-sync/remediation silently does nothing for gated targets (info log only; the flag stays on).
  5. An approval is bound to the run (sync: plan id + target; IaC: run + stack at its `planJobId`); a plan made again needs a new approval.
  6. A subset apply of IaC consumes the whole approval; the tightest covering approval is used first.
  7. On the merge path an unapproved gated stack refuses the whole merge-apply (MR note).
  8. Fixed 7-day lifetime; an unused approval lapses through the expiry job; "revoke" is "reject an approved apply request".
  9. Protection state is read without a lock at apply time (a switch racing an apply may go either way).
  10. Asking needs only `change_request.create` (developer); the applier need not differ from the approver.
  11. Duplicate open requests per plan are allowed, capped by the 50-open limit (counted without a lock).
  12. `APPROVALS_LOOKED_AT = 20` (`shortcut:` comment): more than 20 open approvals for one project and run could hide a covering one.
  13. No UI, CLI or api-client methods.
  14. drizzle jsonb through `Bun.sql` is stored double-encoded (SQL `->>` returns null), so the run id has its own `subject_id uuid` column; never query `subject` in SQL.
  15. Migration 0031 is additive but replaces a trigger function (adds immutable columns and the apply-kind approved→rejected move): a loosening for apply kinds only.
  16. Apply audit events gain `changeRequestId`.
  17. The plan-expiry check at ask time uses the app clock (the apply re-checks at apply time).
  18. `approveApply` does not check that the run is still planned, so a dead approval can exist until it expires.
  19. Mutant G19 is equivalent; H2 is equivalent through the API (the run id fixes the target) and is killed by a direct-database test.
- Gate: `bun run check` green: 3455 pass + 1 skip (the opt-in real-GitLab run) + 0 fail (root), 240 pass (web). No new dependencies.
