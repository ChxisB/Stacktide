## 2026-10-17 API-8
- Table `audit_events` (migration `0002_audit_events.sql`): actor kind/id, `action`, `resource_type/id`, `organization_id`/`project_id` (plain uuids, **no FKs**, so rows outlive the org), `metadata` jsonb, `request_id`, `ip`, `at`. Append-only: hand-appended triggers reject UPDATE, DELETE (row) and TRUNCATE (statement) with SQLSTATE 55000. No `updated_at`, so the "every table has created_at/updated_at" guard in `repo.test.ts` now excludes `audit_events` explicitly.
- `audit(tx, ctx, event)` in `@orch/db`: refuses to run outside a transaction (audit row commits or rolls back with the change it records), validates `action` (`resource.verb`), `resourceType`, actor. `checkMetadata` is the leak tripwire (invariant 1): plain JSON only, string <= 256, <= 100 array items, depth < 3, total <= 4096, finite numbers, and key names that contain a secret word (`value`, `secret`, `token`, `password`, `credential`, `plaintext`, `ciphertext`, `authorization`, `cookie`, `apiKey`, `privateKey`) are refused unless the last word says it only describes one (`secret_count`, `token_id`, `*_name`, `*_kind`). Errors name the key or path, never the value (canary test: refused write is not echoed, not logged, not stored).
- Route coverage (invariant 4): `auditPlugin(resolver)` (replaces the bare principal plugin in `createApp`; it still provides `principal`). Routes declare `{ audit: "project.create" }` (string or array) or `{ noAudit: "reason" }` (blank reason throws at registration); handlers call `audit(tx, {...})` in their own transaction. Checks: undeclared action, or any action on a route with no declaration, throws inside the transaction (rolls back); a 2xx with no audit row is a 500; `unauditedRoutes(app)` lists mutating routes with neither option and a test runs it over `createApp`; both options are in `hooks.detail` as `x-audit` / `x-no-audit` (visible to API-5's OpenAPI).
- Elysia 1.4.30 findings: a macro returning `{detail: {...}}` merges into `app.routes[i].hooks.detail`, which is how route markers stay introspectable (a macro that returns hooks gets its own option key stripped from `route.hooks`); a returned `status(409)` or `Response` leaves `set.status` unset, so `afterHandle` reads `response.code` / `response.status` first; `.as("scoped")` at the end of the plugin lifts hooks and the principal to the parent app; values from a `.use`d plugin's derive are typed possibly-undefined in the same chain, so the plugin narrows at runtime.
- Gate: `bun run check` green, 227 pass + 1 skip (run 5 times in a row). Mutations each fail a test: no afterHandle check, no declared-action check, `declared` never set, `unauditedRoutes` always empty, blank `noAudit` allowed; trigger on UPDATE only, no TRUNCATE trigger; `forbiddenKey` always false, no `DESCRIBES` exemption, no camelCase split, no `apikey`/`privatekey` phrases, no transaction guard, no size limit.
- Fixed a flaky `main.test.ts` (failed once in a full run): the access-log line is written after the response, the test sent SIGTERM right after it. It now waits for the line first; the assertion is unchanged.
- `/code-review` (medium) found 10; fixed: a returned `status(409)`/`Response` was read as success and became a 500; a route with no declaration could write any action (now deny by default, also for `noAudit` routes); the doc comment claimed the "wrote none" check rolls back (it does not, see below). Not done, on purpose: (1) "wrote none" runs after the handler returned, so that change has committed; it is a tripwire for the route's own test, not a runtime guarantee. (2) `written` counts inserts, not commits: a handler that catches a rolled-back transaction and still answers 200 slips past it. (3) `ip` is the socket peer; behind a proxy it will be the proxy (trusting `X-Forwarded-For` blindly would be spoofable, so a trusted-proxy setting belongs to OPS) and it is untested through `app.handle` (no socket), only a real server fills it. (4) The key denylist is a tripwire, not a proof: `password_name` is allowed by design and a key like `key`/`pat`/`dsn` is not recognised; the real control is that callers pass ids, names and counts. (5) Null-prototype objects are refused; the size limit counts UTF-16 units. (6) `at` is the transaction start time (`now()`), so it can disagree with commit order; the id is a v7 uuid generated at insert. (7) Only an index on `(organization_id, at)` and `(resource_type, resource_id)`; add one on `at` or `project_id` when a query needs it.
- **Ops caveat:** the append-only triggers stop UPDATE/DELETE/TRUNCATE from the app, but the table owner or a superuser can drop or disable them. The production app role must not own `audit_events` (OPS-4 should grant it INSERT/SELECT only). A future retention or purge job (GOV) will need a deliberate path around the trigger.
- Security (inline; `/security-review` unusable): no secret, auth or crypto handling; the audit write path only ever sees ids, names, counts; refused metadata never echoes values (test); the request id is the validated one from the `http` plugin.
- No new dependencies.
- Follow-up: every route added from API-4 on must declare `audit`/`noAudit`; the `unauditedRoutes(createApp(...)) == []` test fails the gate otherwise. API-4 should assert one audit row per mutation with the actor.

## 2026-10-17 API-6
- Table `jobs` (migration `0003_jobs`, with the `jobs_updated` trigger): `queue`, `payload` (jsonb), `run_at`, `attempts`/`max_attempts`, `status` (`queued|running|done|dead`, CHECK), `last_error`, `locked_by`/`locked_at`. Partial indexes for claiming (`queued` rows by queue, run_at) and for the stale-lock sweep (`running` rows by locked_at).
- Queue API in `@orch/db` (`jobs.ts`), all on an `Executor`, so a caller can `enqueue` inside the transaction of the change that needs the job (a rollback takes the job with it: test). `claim` takes due jobs oldest first with `FOR UPDATE SKIP LOCKED` inside an `array(subquery)` (evaluated once, so `limit` holds under concurrency); each claim counts as an attempt. `complete` and `fail` are fenced by `(id, running, locked_by, attempts)`: a worker whose lock expired, even one that claimed the job again itself, cannot finish a run it no longer owns (tests for both). `fail` requeues at `backoffMs` (1s doubling, 15 min cap, no overflow) or buries the job as `dead` on its last attempt; stale `running` rows are handed out again, and exhausted ones go `dead` ("lock expired") instead of looping forever.
- **Clock:** `run_at`, `locked_at` and the backoff default to the **database** clock (`now()`), so workers need not agree on the time; `now` is an injected override for tests and for API-7's fake clock. (First version used the worker's clock; Docker for Mac's VM clock drifts from the host's, which is exactly the flakiness and the prod skew this avoids.)
- **Payloads are ids and parameters, never values.** `enqueue` runs the audit tripwire (`checkMetadata`: plain JSON, size and depth limits, no secret-looking key names) and refuses with `JobError("job payload ...")`; the handler reads the value from the vault when it runs. Queue names: `[a-z0-9][a-z0-9_.-]{0,63}`; `maxAttempts` 1..100.
- **`last_error` and logs:** only `Name: message` of a thrown error is stored or logged, scrubbed (`scrubText`), one line, 500 chars (cut after scrubbing). Thrown strings and objects are described, not dumped. The worker never logs a payload.
- **Found by the security review: Drizzle errors carry bound values.** `DrizzleQueryError.message` is `Failed query: <sql>\nparams: a,b,c`, so a failed insert in a handler would have put the row's values into `last_error` and the logs (the same is true of the 500 logging from API-1..4). The shared scrubber now masks everything after `params:`. Core tests and a jobs test with a real failing insert (the premise assertion shows the raw message does leak the canary).
- Other scrubber changes in `@orch/core` (benefit every log line): tokens by shape (GitLab `gl*`, GitHub, Slack, Stripe-style), AWS key ids, JWTs, `key=value` / `"key": "value"` pairs (escaped quotes handled). Over-redacts on purpose, in the logger's existing spirit (`passed: true` is masked). **Limits:** a secret with spaces in an unquoted `password=...` leaks past the first space; the scrubber is a net for free text, the rule is still to keep secrets out of error text.
- Worker (`apps/api/src/worker.ts`, library) and `worker-main.ts` (entrypoint; root script `bun run worker`; env `WORKER_CONCURRENCY` 1..100 (4), `WORKER_POLL_MS` 10..60000 (1000)). `createWorker({db, logger, handlers})`: queues are the handler keys (a worker never claims a queue it has no handler for), claims are bounded by free slots, success -> `complete`, a throw -> `fail`. The handler gets `{id, queue, payload, attempt, log, signal}`; `signal` aborts at the lock timeout and when `stop()` runs out of drain time. `stop()` stops claiming, waits for running jobs (`drainMs`, 10s), aborts the stragglers and waits up to 2 s more for them to record their failure before the caller closes the database. SIGTERM/SIGINT in the entrypoint run that, then close the pool, exit 0. No handlers are registered yet: later features add theirs in `worker-main.ts`.

## 2026-10-17 API-7

- Added `schedules(name, cron | interval_seconds, queue, payload, next_run_at, last_run_at, enabled)` (migration `0004_schedules`, additive, `schedules_updated` trigger; a check enforces exactly one of cron/interval), `upsertSchedule` and `fireDue` in `packages/db/src/schedules.ts`, and a small cron evaluator in `packages/core/src/cron.ts`. Every worker calls `fireDue` at the top of each poll, so no separate scheduler process exists. `jobQueue`/`jobPayload` were extracted from `enqueue` and reused for schedules (same validation as jobs).
- **Double-fire protection:** `fireDue` selects due, enabled rows `FOR UPDATE SKIP LOCKED` in one transaction, enqueues, then moves `next_run_at`/`last_run_at` before commit. A second worker either skips the locked row or sees it already moved on. Each schedule runs in its own savepoint: a row that cannot fire is reported through `onError` (the worker logs `schedule failed to fire` with the scrubbed error), stays due and does not block the others (review finding).
- **Time:** the database clock (`now()`) unless a `now` is injected (tests, the worker's fake clock), the same rule as the job queue.
- **Cron:** five fields, UTC; `*`, `a`, `a-b`, `*/n`, `a-b/n` and lists; 7 = Sunday; dom/dow OR when both are restricted, AND when either starts with `*` (Vixie). Refused: names, `L W ? #`, seconds, bare `a/n`, reversed or out-of-range values. Errors name the field, never the input. A valid but impossible expression (`0 0 30 2 *`) is refused at upsert (`nextCronRun` gives up after a bounded search).
- **Intervals** keep their grid (`first + k*step`); a tick missed while workers were down fires once, then resumes on the grid (skipped, not replayed). The first run is `now + interval` or the next cron match.
- **Upsert:** idempotent by name. It keeps `next_run_at` unless cron, interval or `enabled` changed (so re-registering at every boot neither delays nor re-fires), and restarts the timing when they did. Re-enabling restarts from now (no catch-up burst).
