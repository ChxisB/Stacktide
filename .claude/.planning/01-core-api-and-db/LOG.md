## 2026-10-17 API-1
- `packages/db` (`@orch/db`): `createDb(url, max)`, `migrateDb(db)`, `db:generate` / `db:migrate` scripts, baseline migration `0000_baseline.sql` (shared `set_updated_at()` trigger function every table will use), `createTestDb()` in `@orch/db/testing` (unique `orch_test_<hex>` database per call, migrated, with an idempotent `drop()`).
- **ADR-0004 driver check: passed.** `drizzle-orm/bun-sql` (query builder, `execute`, migrator) works on `Bun.sql` against Postgres 18.6; covered by a test, so a Bun or Drizzle upgrade that breaks it turns the gate red.
- Gate: `bun run check` green, 34 tests (needs `bun run dev:db`). Two `bun test packages/db` processes run in parallel without interfering and leave no `orch_test_*` databases or connections behind; four child processes each get their own database (test).
- Finding worth keeping: a default `Bun.sql` client opens ~7 connections on its first query (more under concurrency); `{max: 2}` opens exactly 2. Postgres allows 100, and the first draft hit `too many clients`. Test databases use a pool of 2, the admin client lives for one statement, and `db:migrate` uses a pool of 1.
- `/code-review` (medium) found 8; fixed: `drop()` skipped later steps on error and returned early on concurrent calls (now one shared promise with try/finally), admin connection leaked when `CREATE DATABASE` failed, every failure was reported as "not reachable" (a bad password is now reported as the server's own message), admin connection held for the whole file, `.env` auto-load could leak into the missing-`DATABASE_URL` child test (child runs in the tmp dir). README now warns that `db:migrate` falls back to the local database. Not fixed: migrate has no advisory lock (see follow-ups).
- Security (inline; `/security-review` unusable, see FND-4): the only dynamic SQL is `CREATE/DROP DATABASE <name>` where `name` is generated from hex; connection errors name the host only (tests assert the password never appears, for unreachable and rejected-credential cases); `TestDb.url` carries credentials and is documented as never-log; the `.env.example` credentials are throwaway, bound to loopback.
- New deps (exact-pinned): `drizzle-orm` 0.45.4, `zod` 4.6.7 (config schema for the migrate entrypoint) in `packages/db`; `drizzle-kit` 0.31.11 as a dev dependency (SQL generation per ADR-0004).
- Follow-ups: `db:migrate` takes no advisory lock, so concurrent runs against one database can race. Deploys must run it as one step; add a lock when OPS builds the deploy path (`shortcut:` comment in `migrate.ts`). Crashed test runs leave `orch_test_*` databases behind (`shortcut:` in `testing.ts`).

## 2026-10-17 API-2
- Tables `organizations` (slug unique), `projects` (unique name per org; `gitlab_project_id` bigint nullable, unique per org only when set; `default_branch` default `main`), `environments` (unique slug per project; `sort_order` replaces the SPEC's `order`, a reserved word). Migration `0001_base_schema.sql` (generated by drizzle-kit, plus hand-appended `updated_at` triggers; drizzle-kit does not model triggers). Constraint names are explicit and stable so API-4 can map a 409 to the field.
- Conventions as code: `schema/columns.ts` gives every table a v7 id (`Bun.randomUUIDv7()` from Drizzle, `uuidv7()` as the PG18 default for raw SQL) and `created_at`/`updated_at`. Two guard tests fail if a table lacks the `set_updated_at` trigger or either timestamp column; the trigger guard was shown to flag a table without one.
- Tenant integrity: `environments` carries `organization_id` and a composite FK `(project_id, organization_id)` to `projects(id, organization_id)`, so it cannot name another org than its project (test). Repo reads and deletes take `organizationId`, so a guessed id from another tenant matches nothing (test).
- **REVIEW (delete semantics):** `projects -> organizations` is `ON DELETE RESTRICT` (an org with projects cannot be deleted; SQLSTATE 23001), `environments -> projects` is `CASCADE`. Chosen as the conservative reading of the SPEC; change it if you want org deletion to cascade.
- `repo.ts`: `Executor` type accepts a `Db` or a transaction (test proves rollback), so API-8 can write audit events in the same transaction. `pgCode(e)` extracts the SQLSTATE from a Drizzle error and only trusts errors the server sent (not `EPIPE`-style socket errors). Create/get/delete for the three tables and `listEnvironments`; update and pagination arrive with API-4.
- Fixed from API-1: `db:generate` never worked (`drizzle-kit` is a dev dependency of `packages/db`, not on the root script PATH); now runs through `bunx`. Biome now ignores `packages/db/drizzle/meta` (generated JSON). The "migrating again is a no-op" test hardcoded one migration; it now compares counts.
- Gate: `bun run check` green, 56 tests; db tests run 5 times in a row without a failure and without leaving test databases.
- `/code-review` (medium) found 8; fixed: org scoping in repo, DB-side id default, `pgCode` matching socket errors, a flaky `updated_at` test (millisecond truncation), delete results (now `true`/`false`), trigger-comment. Not done: index on `environments.organization_id` (nothing queries by it yet); `bigint` number mode precision (comment only, GitLab ids are far below 2^53).
- Security: no secrets, auth or crypto in this task, so no `/security-review`. No new dependencies.
- Follow-up: nothing checks that `db:generate` is drift-free (it reports "No schema changes" today); consider a CI step.

## 2026-10-17 API-3
- `apps/api` (`@orch/api`): `createApp({logger, principal, ready})` returns an Elysia app (exported as `App` for the Eden client in API-5); `index.ts` is the process entry (`bun run dev`): zod config, `createDb(url, 5)`, listen, SIGTERM/SIGINT graceful stop (10s forced-exit timer, exit 1 if closing fails). `DomainError(code, status, message)` lives in `@orch/core`; `pingDb` in `@orch/db`.
- Errors are `application/problem+json` (`type: urn:orch:problem:<code>`, `code`, `request_id`). Mapping: `DomainError` -> its own status/code; unknown route 404 `not_found`; validation 422 `validation_failed` with `errors:[{path,message}]` only; malformed body 400 `bad_request`; Elysia `status(4xx/5xx, payload)` (thrown or returned) -> `http_<status>` with the payload dropped; anything else -> logged with the request id and returned as a generic 500.
- Request id: inbound `x-request-id` kept only if `[\w.-]{1,128}`, otherwise a v7 UUID; echoed as a header and in every problem. One access-log line per request (`method`, `path` without query string, `status`, `duration_ms`, `request_id`).
- `/health` is liveness. `/ready` pings the database with a 2s timeout; concurrent calls share one check, failures return a 503 `not_ready` with no driver text. Known limit: a timed-out query is abandoned, not cancelled.
- `ctx.principal`: `principalPlugin(resolver)` is a named plugin (`orch.principal`) that route modules `.use()`; `devPrincipal` returns `{id:"dev", kind:"dev"}`. **Fail-closed until AUTH-3:** the entry point refuses to start when `NODE_ENV` is not `development`/`test` (case-insensitive) or when `HOST` is not loopback, so the stub cannot be exposed by accident.
- Findings worth keeping (Elysia 1.4.30): hooks need `{as: "global"}` to cross plugin boundaries and only apply to routes registered after them; a thrown `status()` reaches `onError` with a numeric `code`, a returned one skips `onError` and only shows up in `mapResponse` as `response.code` (with `set.status` still 200); `onAfterResponse` runs after `handle()` returns, so tests poll for the log line; a plugin cannot see types derived by its parent, hence the named `orch.principal` plugin.
- Gate: `bun run check` green, 87 tests (needs `bun run dev:db`); `bun install --frozen-lockfile` clean. A subprocess test boots the real entry point against a test DB: serves, answers `/ready`, goes 503 when the DB is dropped while `/health` stays 200, exits 0 on SIGTERM, refuses production / non-loopback host, names a missing `DATABASE_URL` key.
- `/code-review` (medium); fixed: unauthenticated `/ready` fan-out (shared check), thrown/returned `status()` leaking payloads and mis-mapping to 500, dev principal reachable in non-dev environments or on a public interface, inbound request-id log/header injection, shutdown hanging or swallowing close errors, unused `drizzle-orm` dep in api, mis-binding of `request_id` in the fallback logger. A reported string status in the access log did not reproduce; the status-by-name test stays as a regression guard. Not fixed: `WeakMap<Request,…>` state relies on Elysia passing the same `Request` object through hooks (true in 1.4.30, covered by the request-id/access-log tests, so an upgrade that breaks it turns the gate red).
- Security (inline): error bodies never carry driver, stack or input text (canary tests for 500, 503, 422, 400 and `status()`); validation errors expose path + rule only; the query string is never logged; no auth/crypto/secrets handled here, the dev principal is the only identity and is fenced as above. `/ready` is deliberately unauthenticated.
- New deps (exact-pinned): `elysia` 1.4.30 in `apps/api` (ADR-0003); `zod` 4.6.7 reused.
- Follow-up: AUTH-3 replaces `devPrincipal` and must delete the two fail-closed guards in `index.ts` once real authentication is wired; API-8's route-audit coverage test will register against `createApp`.

## 2026-10-17 API-8
- Table `audit_events` (migration `0002_audit_events.sql`): actor kind/id, `action`, `resource_type/id`, `organization_id`/`project_id` (plain uuids, **no FKs**, so rows outlive the org), `metadata` jsonb, `request_id`, `ip`, `at`. Append-only: hand-appended triggers reject UPDATE, DELETE (row) and TRUNCATE (statement) with SQLSTATE 55000. No `updated_at`, so the "every table has created_at/updated_at" guard in `repo.test.ts` now excludes `audit_events` explicitly.
- `audit(tx, ctx, event)` in `@orch/db`: refuses to run outside a transaction (audit row commits or rolls back with the change it records), validates `action` (`resource.verb`), `resourceType`, actor. `checkMetadata` is the leak tripwire (invariant 1): plain JSON only, string <= 256, <= 100 array items, depth < 3, total <= 4096, finite numbers, and key names that contain a secret word (`value`, `secret`, `token`, `password`, `credential`, `plaintext`, `ciphertext`, `authorization`, `cookie`, `apiKey`, `privateKey`) are refused unless the last word says it only describes one (`secret_count`, `token_id`, `*_name`, `*_kind`). Errors name the key or path, never the value (canary test: refused write is not echoed, not logged, not stored).
- Route coverage (invariant 4): `auditPlugin(resolver)` (replaces the bare principal plugin in `createApp`; it still provides `principal`). Routes declare `{ audit: "project.create" }` (string or array) or `{ noAudit: "reason" }` (blank reason throws at registration); handlers call `audit(tx, {...})` in their own transaction. Checks: undeclared action, or any action on a route with no declaration, throws inside the transaction (rolls back); a 2xx with no audit row is a 500; `unauditedRoutes(app)` lists mutating routes with neither option and a test runs it over `createApp`; both options are in `hooks.detail` as `x-audit` / `x-no-audit` (visible to API-5's OpenAPI).
- Elysia 1.4.30 findings: a macro returning `{detail: {...}}` merges into `app.routes[i].hooks.detail`, which is how route markers stay introspectable (a macro that returns hooks gets its own option key stripped from `route.hooks`); a returned `status(409)` or `Response` leaves `set.status` unset, so `afterHandle` reads `response.code` / `response.status` first; `.as("scoped")` at the end of the plugin lifts hooks and the principal to the parent app; values from a `.use`d plugin's derive are typed possibly-undefined in the same chain, so the plugin narrows at runtime.
- Gate: `bun run check` green, 227 pass + 1 skip (run 5 times in a row). Mutations each fail a test: no afterHandle check, no declared-action check, `declared` never set, `unauditedRoutes` always empty, blank `noAudit` allowed; trigger on UPDATE only, no TRUNCATE trigger; `forbiddenKey` always false, no `DESCRIBES` exemption, no camelCase split, no `apikey`/`privatekey` phrases, no transaction guard, no size limit.
- Fixed a flaky `main.test.ts` (failed once in a full run): the access-log line is written after the response, the test sent SIGTERM right after it. It now waits for the line first; the assertion is unchanged.
- `/code-review` (medium) found 10; fixed: a returned `status(409)`/`Response` was read as success and became a 500; a route with no declaration could write any action (now deny by default, also for `noAudit` routes); the doc comment claimed the "wrote none" check rolls back (it does not, see below). Not done, on purpose: (1) "wrote none" runs after the handler returned, so that change has committed; it is a tripwire for the route's own test, not a runtime guarantee. (2) `written` counts inserts, not commits: a handler that catches a rolled-back transaction and still answers 200 slips past it. (3) `ip` is the socket peer; behind a proxy it will be the proxy (trusting `X-Forwarded-For` blindly would be spoofable, so a trusted-proxy setting belongs to OPS) and it is untested through `app.handle` (no socket), only a real server fills it. (4) The key denylist is a tripwire, not a proof: `password_name` is allowed by design and a key like `key`/`pat`/`dsn` is not recognised; the real control is that callers pass ids, names and counts. (5) Null-prototype objects are refused; the size limit counts UTF-16 units. (6) `at` is the transaction start time (`now()`), so it can disagree with commit order; the id is a v7 uuid generated at insert. (7) Only an index on `(organization_id, at)` and `(resource_type, resource_id)`; add one on `at` or `project_id` when a query needs it.
- **Ops caveat:** the append-only triggers stop UPDATE/DELETE/TRUNCATE from the app, but the table owner or a superuser can drop or disable them. The production app role must not own `audit_events` (OPS-4 should grant it INSERT/SELECT only). A future retention or purge job (GOV) will need a deliberate path around the trigger.
- Security (inline; `/security-review` unusable): no secret, auth or crypto handling; the audit write path only ever sees ids, names, counts; refused metadata never echoes values (test); the request id is the validated one from the `http` plugin.
- No new dependencies.
- Follow-up: every route added from API-4 on must declare `audit`/`noAudit`; the `unauditedRoutes(createApp(...)) == []` test fails the gate otherwise. API-4 should assert one audit row per mutation with the actor.

## 2026-10-17 API-4
- Routes (`apps/api/src/routes/`): `/organizations` (list, get, create, patch, delete), `/organizations/:orgId/projects[/:projectId]`, `/organizations/:orgId/projects/:projectId/environments[/:envId]`. Ids are in the path, all parents are checked (`orgId` scopes every project query; an environment is addressed by org + project + id), so an id from another tenant is a 404. `createApp` now takes `db`; route modules take `{db, principal}` and `.use(auditPlugin(principal))` (Elysia dedupes the named plugin: the principal resolver runs once per request, verified).
- Validation is zod (4.6.7) through Elysia's Standard Schema support; no adapter needed, and the existing 422 mapper handles it (path + rule only; test shows a submitted value never comes back). Bodies are `z.strictObject`, so unknown fields (`organizationId`, `role`, `slug` on PATCH) are 422. Slugs: lower-case words joined by single dashes, <= 63. Names trimmed, 1-100. Branch names: conservative charset, no `..`, no trailing `/` or `.lock`. PATCH must name at least one field. **Slugs are immutable** (organization slug and environment slug are identifiers other systems will refer to): chosen without asking, a PATCH with `slug` is a 422. Change it if you want renames.
- Pagination: keyset, `limit` 1..100 (default 50), response `{items, nextCursor}` (`nextCursor` is null on the last page; an exact fit does not produce an empty extra page). Organizations and projects order by v7 id (creation order); environments by `(sort_order, slug)`. The cursor is base64url JSON of the last row's key, validated by a schema per list (a projects cursor on the environments list, a forged out-of-range number, a NUL byte, a non-uuid: all 400 `invalid_cursor`, none reaches Postgres). It is not signed: it only narrows the caller's own query.
- Errors: unique violations map by constraint name to 409 (`slug_taken`, `name_taken`, `gitlab_project_linked`); foreign-key violations on create to 404 (`not_found`); deleting an organization that still has projects is 409 `organization_not_empty` (SQLSTATE 23001, the REVIEW-tagged RESTRICT from API-2); the response never names the constraint or the SQL (test). `pgConstraint()` added next to `pgCode()` in `@orch/db`; the mapping must run after the transaction (a failed statement aborts it), via `.catch(mapDbError({...}))`.
- Audit (invariant 4): create/update/delete of each resource writes `organization.*`, `project.*`, `environment.*` in the same transaction, with `organizationId`/`projectId`, the caller, and request id. Metadata: `slug`/`name` on create and delete (so the row says what was removed), `fields: [names]` on update, never new values. A test asserts `unauditedRoutes(createApp(...)) == []` and that the declared action set is exactly the nine. A failed request (409, 404, 422) writes no audit row (tests count rows).
- Repo (`@orch/db`): `get`/`update`/`list` for organizations and projects, `get`/`update`/`delete`/paged `list` for environments. An update with no given fields is a read (drizzle would throw on an empty SET).
- Resource JSON is camelCase with ISO-8601 timestamps (problem+json keeps its snake_case `request_id` from API-3). Deletes answer 204 with no body. No response schemas yet: API-5 adds them for the OpenAPI doc.
- Gate: `bun run check` green, 256 pass + 1 skip (3 runs). Mutations each fail a test: keyset `>=` on projects and environments, `nextCursor` on exact fit, update ignoring the organization, no parent check, no `strictObject`, `mapDbError` rethrowing everything, metadata carrying values, no cursor validation, unmapped RESTRICT.
- `/code-review` (medium) found 8; fixed: a well-formed but out-of-range environment cursor reached Postgres and became a 500 (the key is now `[sortOrder, slug]` with the same bounds as the input); `204` was set inside the transaction callback for project/environment delete (now after commit, like the organization delete). Dismissed: "`constraint` may be missing from the driver error" (every 409/404-FK mapping runs against the real database in `routes.test.ts`); the exists-check/list race (benign); the empty-patch branch in repo updates (real behaviour for direct callers, and tested); SELECT-then-DELETE (a concurrent delete correctly answers 404). Not done: the three route files repeat the `audited` builder and delete flow (small, and later features add their own routes).
- **Known gap, closes in AUTH-3:** nothing scopes these routes to the caller. `GET /organizations` lists every organization and any principal can read, change or delete any of them. Safe only while the dev principal (loopback-only, fenced in `index.ts`) is the sole caller. AUTH-3's route-guard coverage test is what enforces a guard on every one of these routes.
- Security (inline): no secrets handled; inputs are validated and parameterised (Drizzle), error bodies carry codes and fixed text only, and the cursor and ids are validated before they reach SQL.
- No new dependencies.
