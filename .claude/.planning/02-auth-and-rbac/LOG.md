# Log - Auth and RBAC

## 2026-10-17 AUTH-1 (REVIEW: auth model, session handling)

- **Flow:** authorization code + PKCE (S256), scope `read_user`. `GET /auth/login` makes a random `state` and PKCE verifier, keeps `{state, verifier, return_to, expiry}` in an `orch_login` cookie (HttpOnly, SameSite=Lax, Path=/auth, 10 min) and redirects to GitLab. `GET /auth/callback` compares `state` with the cookie (constant time), trades the code for an access token, reads `/user`, drops the token, upserts the user, starts a session, clears the login cookie and redirects to `return_to`. `GET /auth/me`, `POST /auth/logout` (204; 401 when there is no live session, and the dead cookie is cleared). No new table for the flow: the browser carries it.
- **Sessions:** `sessions(user_id, token_hash, expires_at)` (migration `0005_auth`, additive, `users` + `sessions`, `updated_at` triggers). The cookie holds 256 random bits; only its SHA-256 is stored. Absolute lifetime (default 12 h), checked against the database clock. A sign-in issues a new token and ends the session the browser arrived with (no fixation); other browsers keep theirs. Expired rows are removed on the way in `createSession`. The TTL is validated when the routes are built (before any code is spent).
- **GitLab client:** `packages/gitlab/src/oauth.ts` (`gitlabOAuth`: `authorizeUrl`, `exchangeCode`, `currentUser`), `parseBaseUrl` extracted from the client. The token POST is never retried (a code works once). Errors carry the status and the OAuth error code (`invalid_grant`) only. The mock GitLab got the OAuth endpoints and controls (approve as a user, deny, one-use codes, S256 check, issued tokens listed for leak checks).
- **Config:** `GITLAB_URL`, `GITLAB_OAUTH_CLIENT_ID`, `GITLAB_OAUTH_CLIENT_SECRET`, `GITLAB_OAUTH_REDIRECT_URI`: all four or none (a partial set fails the start, naming keys only). An https redirect URI turns on `Secure` cookies. None set: `/auth/login` answers 503. Placeholders only in `.env.example`.
- **Audit:** `auth.login` and `auth.logout` rows with actor kind `user` (the audit helper takes an actor override: the caller is only known after the callback runs). Metadata is the GitLab id only.
- **Leak checks:** the access token, client secret, session token and code appear in no log line, response body, audit row or session row (the table holds the hash). Access log is path-only, so `code` and `state` do not reach it.
- Gate: `bun run check` green, 383 pass + 1 skip. 27 API tests (happy path, bad/missing/forged/wrong-browser state, expired flow, replayed code, denied, `error` beside a `code`, inactive account 403, GitLab down 502, refused client secret 401 logged at error, session expiry, rotation, logout, two browsers, open-redirect cases, cookie flags, 503 when unconfigured), 24 oauth tests against the mock, db tests, 5 config tests. `docs/openapi.json` regenerated; the spec test now has a separate check for the `/auth/*` operations.
- **Mutations, 30/30 killed:** state not compared (and absent state accepted), flow expiry, challenge = verifier, verifier not sent, expired session accepted, old session kept, protocol-relative and backslash redirects, login cookie kept, inactive user allowed, no HttpOnly/SameSite/Secure, logout keeps the session, TTL ignored, provider `error` ignored (survived the first run; test added), actor override ignored, wider scope, error echoes the body, flow cookie path, cacheable redirects, username not refreshed, partial config accepted, Secure never derived, state reused as verifier, TTL unchecked at start, dead cookie kept, refused secret only warned (survived; level assertion added), fractional Max-Age (survived; test added).
- `/code-review` (medium) found 10. Fixed: TTL validated only after a code is spent (and a fractional `Max-Age`), the logout 401 left a dead cookie, `request_id: "undefined"` in the log, a refused client secret was only a warning (now error). Dismissed, recorded as limits: see below.
- Security (inline): no secret in any log, error, audit row or table (tests above). State is bound to the browser by the cookie; session fixation is prevented by issuing a new token; `return_to` is a path on this site (CR/LF and `//` are refused, so no open redirect or header injection); redirect URI comes from config only; `/auth/me` and redirects are `no-store`; logout is POST with a SameSite=Lax cookie and a JSON-only API (415 guard). Found while writing the tests: nothing leaked. `/security-review` is unusable here (no remote), so this is the review.
- **Known limits (decide in AUTH-3/AUTH-5 or OPS):**
  - The login cookie is unsigned. Someone who can set cookies for the host (a sibling subdomain) can mount a login CSRF with their own code and state. A `__Host-` cookie (https only, Path=/) or an HMAC (needs a server secret: crypto gate) would close it.
  - A GitLab account blocked after sign-in keeps its session until it ends (12 h). There is no "revoke all sessions of a user" and no idle timeout. AUTH-5 (membership) should refresh the user, or an admin revoke should be added.
  - Failed sign-ins (inactive account, bad state, refused code) are logged at warn/error where GitLab was asked, but are not audit rows. Bad-state callbacks are not logged.
  - One `orch_login` cookie: two tabs starting a sign-in at once make the first one fail with 400 "Start again".
  - The access token is not revoked at GitLab after use (read_user only, 2 h).
  - `/auth/login` is not rate limited.
  - A rejected client secret surfaces to users as 401 `login_failed`; the log line (level error) says why.
  - The auth routes still run under `auditPlugin(principal)` with the dev principal; AUTH-3 must make the resolver anonymous-capable and list `/auth/*` as `public`.
  - Sessions per user are unbounded until they expire.
  - OAuth is mock-tested only. Fidelity against a real GitLab is unverified (it needs a browser; the opt-in contract run cannot cover it).
- No new dependencies (`@orch/gitlab` added to the API package as a workspace link).

## 2026-10-17 AUTH-2 (REVIEW: role model, permission table)

- `packages/core/src/authz.ts`: pure, total `can(subject, action, resource)`, plus `RULES` (the one table), `isAction`, `ORG_ROLES`, `PROJECT_ROLES`, the `Subject` and `Resource` types. In `core`, with no dependencies, so the API, CLI and UI can all use it. Code, not DB tables (task text).
- **Model, as the SPEC says:** org roles `viewer < member < admin < owner`; project roles `reporter < developer < maintainer`. An org role confers a project role on every project of that org (viewer -> reporter, member -> developer, admin/owner -> maintainer); a direct project role adds to that (the higher wins). Secret reveal needs project `maintainer`. Unknown action, unknown kind, unknown role name, missing ids: all deny.
- **Decisions the SPEC left open (please check):**
  - `organization.create` needs `platformAdmin` (no org exists to hold a role); it grants nothing else, and is ignored for CI principals. Where the flag comes from is AUTH-3's call (config).
  - `project.create` and `project.delete` need **org admin** (a project maintainer can change a project and its environments, not create or remove it); `organization.update` admin, `organization.delete` owner.
  - A project-only member (no org role) cannot read the org record.
  - Scopes (tokens and CI jobs: required, none or empty means nothing; users: optional) are an action, `resource.*` or `*`. They only narrow the roles, never widen them.
  - `developer` is not required by any action yet; later features add their actions to `RULES` (variable read/write, sync, tokens, ...) and the hand-written matrix in the test must grow with them.
- Gate: `bun run check` green, 415 pass + 1 skip. The test writes the expected matrix out by hand (13 actions x 9 kinds of holder, both directions, not derived from `RULES`), plus cross-org and cross-project, ids/actions that exist on every object (`__proto__`, `constructor`), unknown role names and kinds, scopes (narrow, never widen, wildcard, not a pattern, malformed input never throws).
- **Mutations, 22 run, 20 killed**: rank `>`/`>=` for org and project, each inherited role, direct role ignored, inherited ignored, `in` instead of `hasOwn` for actions, scopes ignored/any/loose prefix, token without scopes, kind unchecked (survived first; test added), CI platform admin, truthy platform flag, project ids optional, `project.delete` / `secret.reveal` / `organization.read` rules loosened, no array guard, no string guard. Two survivors are equivalent for now: viewer inheriting `developer` (no action needs the developer rank yet, so nothing can observe it) and the plain lookup instead of `hasOwn` in `own` (a prototype value is never a role name, so the later rank check rejects it; `hasOwn` stays as belt and braces).
- `/code-review` (medium) found 6. Fixed: malformed `scopes` (null, a string, non-strings) made `can` throw, against its "total" promise; a test assertion that passed for the wrong reason. Dismissed: project roles are keyed by project id alone (the resource's ids must come from the stored row, as the `Resource` doc says; **AUTH-3's guard must build it that way, never from path parameters alone**); an own `__proto__` key from `JSON.parse` (needs attacker-chosen role-map keys and ids); an `assertCan` that maps a denial to 403/404 (AUTH-3's guard); typed resources per rule kind (a wrong shape fails closed).
- Security (inline): no I/O, no secrets, no state. Fails closed on every path I could find. The risk is in what feeds it: whoever builds the `Subject` (AUTH-3/5/6) and the `Resource`.
- Follow-ups for AUTH-3: list routes need filtering by the subject's roles (`can` answers per resource); a `platformAdmin` source; the 403-or-404 rule.
- No new dependencies.
