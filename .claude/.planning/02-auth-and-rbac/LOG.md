# Log - Auth and RBAC

## 2026-10-17 AUTH-1 (REVIEW: auth model, session handling)

- **Flow:** authorization code + PKCE (S256), scope `read_user`. `GET /auth/login` makes a random `state` and PKCE verifier, keeps `{state, verifier, return_to, expiry}` in an `orch_login` cookie (HttpOnly, SameSite=Lax, Path=/auth, 10 min) and redirects to GitLab. `GET /auth/callback` compares `state` with the cookie (constant time), trades the code for an access token, reads `/user`, drops the token, upserts the user, starts a session, clears the login cookie and redirects to `return_to`. `GET /auth/me`, `POST /auth/logout` (204; 401 when there is no live session, and the dead cookie is cleared). No new table for the flow: the browser carries it.
- **Sessions:** `sessions(user_id, token_hash, expires_at)` (migration `0005_auth`, additive, `users` + `sessions`, `updated_at` triggers). The cookie holds 256 random bits; only its SHA-256 is stored. Absolute lifetime (default 12 h), checked against the database clock. A sign-in issues a new token and ends the session the browser arrived with (no fixation); other browsers keep theirs. Expired rows are removed on the way in `createSession`. The TTL is validated when the routes are built (before any code is spent).
- **GitLab client:** `packages/gitlab/src/oauth.ts` (`gitlabOAuth`: `authorizeUrl`, `exchangeCode`, `currentUser`), `parseBaseUrl` extracted from the client. The token POST is never retried (a code works once). Errors carry the status and the OAuth error code (`invalid_grant`) only. The mock GitLab got the OAuth endpoints and controls (approve as a user, deny, one-use codes, S256 check, issued tokens listed for leak checks).
- **Config:** `GITLAB_URL`, `GITLAB_OAUTH_CLIENT_ID`, `GITLAB_OAUTH_CLIENT_SECRET`, `GITLAB_OAUTH_REDIRECT_URI`: all four or none (a partial set fails the start, naming keys only). An https redirect URI turns on `Secure` cookies. None set: `/auth/login` answers 503. Placeholders only in `.env.example`.
- **Audit:** `auth.login` and `auth.logout` rows with actor kind `user` (the audit helper takes an actor override: the caller is only known after the callback runs). Metadata is the GitLab id only.
- **Leak checks:** the access token, client secret, session token and code appear in no log line, response body, audit row or session row (the table holds the hash). Access log is path-only, so `code` and `state` do not reach it.
- Gate: `bun run check` green, 383 pass + 1 skip. 27 API tests (happy path, bad/missing/forged/wrong-browser state, expired flow, replayed code, denied, `error` beside a `code`, inactive account 403, GitLab down 502, refused client secret 401 logged at error, session expiry, rotation, logout, two browsers, open-redirect cases, cookie flags, 503 when unconfigured), 24 oauth tests against the mock, db tests, 5 config tests. `docs/openapi.json` regenerated; the spec test now has a separate check for the `/auth/*` operations.
- **Mutations, 30/30 killed:** state not compared (and absent state accepted), flow expiry, challenge = verifier, verifier not sent, expired session accepted, old session kept, protocol-relative and backslash redirects, login cookie kept, inactive user allowed, no HttpOnly/SameSite/Secure, logout keeps the session, TTL ignored, provider `error` ignored (survived the first run; test added), actor override ignored, wider scope, error echoes the body, flow cookie path, cacheable redirects, username not refreshed, partial config accepted, Secure never derived, state reused as verifier, TTL unchecked at start, dead cookie kept, refused secret only warned (survived; level assertion added), fractional Max-Age (survived; test added).
- `/code-review` (medium) found 10. Fixed: TTL validated only after a code is spent (and a fractional `Max-Age`), the logout 401 left a dead cookie, `request_id: "undefined"` in the log, a refused client secret was only a warning (now error). Dismissed, recorded as limits: see below.
- Security (inline): no secret in any log, error, audit row or table (tests above). State is bound to the browser by the cookie; session fixation is prevented by issuing a new token; `return_to` is a path on this site (CR/LF and `//` are refused, so no open redirect or header injection); redirect URI comes from config only; `/auth/me` and redirects are `no-store`; logout is POST with a SameSite=Lax cookie and a JSON-only API (415 guard). Found while writing the tests: nothing leaked. `/security-review` is unusable here (no remote), so this is the review.
- **Known limits (decide in AUTH-3/AUTH-5 or OPS):**
  - The login cookie is unsigned. Someone who can set cookies for the host (a sibling subdomain) can mount a login CSRF with their own code and state. A `__Host-` cookie (https only, Path=/) or an HMAC (needs a server secret: crypto gate) would close it.
  - A GitLab account blocked after sign-in keeps its session until it ends (12 h). There is no "revoke all sessions of a user" and no idle timeout. AUTH-5 (membership) should refresh the user, or an admin revoke should be added.
  - Failed sign-ins (inactive account, bad state, refused code) are logged at warn/error where GitLab was asked, but are not audit rows. Bad-state callbacks are not logged.
  - One `orch_login` cookie: two tabs starting a sign-in at once make the first one fail with 400 "Start again".
  - The access token is not revoked at GitLab after use (read_user only, 2 h).
  - `/auth/login` is not rate limited.
  - A rejected client secret surfaces to users as 401 `login_failed`; the log line (level error) says why.
  - The auth routes still run under `auditPlugin(principal)` with the dev principal; AUTH-3 must make the resolver anonymous-capable and list `/auth/*` as `public`.
  - Sessions per user are unbounded until they expire.
  - OAuth is mock-tested only. Fidelity against a real GitLab is unverified (it needs a browser; the opt-in contract run cannot cover it).
- No new dependencies (`@orch/gitlab` added to the API package as a workspace link).

## 2026-10-17 AUTH-2 (REVIEW: role model, permission table)

- `packages/core/src/authz.ts`: pure, total `can(subject, action, resource)`, plus `RULES` (the one table), `isAction`, `ORG_ROLES`, `PROJECT_ROLES`, the `Subject` and `Resource` types. In `core`, with no dependencies, so the API, CLI and UI can all use it. Code, not DB tables (task text).
- **Model, as the SPEC says:** org roles `viewer < member < admin < owner`; project roles `reporter < developer < maintainer`. An org role confers a project role on every project of that org (viewer -> reporter, member -> developer, admin/owner -> maintainer); a direct project role adds to that (the higher wins). Secret reveal needs project `maintainer`. Unknown action, unknown kind, unknown role name, missing ids: all deny.
- **Decisions the SPEC left open (please check):**
  - `organization.create` needs `platformAdmin` (no org exists to hold a role); it grants nothing else, and is ignored for CI principals. Where the flag comes from is AUTH-3's call (config).
  - `project.create` and `project.delete` need **org admin** (a project maintainer can change a project and its environments, not create or remove it); `organization.update` admin, `organization.delete` owner.
  - A project-only member (no org role) cannot read the org record.
  - Scopes (tokens and CI jobs: required, none or empty means nothing; users: optional) are an action, `resource.*` or `*`. They only narrow the roles, never widen them.
  - `developer` is not required by any action yet; later features add their actions to `RULES` (variable read/write, sync, tokens, ...) and the hand-written matrix in the test must grow with them.
- Gate: `bun run check` green, 415 pass + 1 skip. The test writes the expected matrix out by hand (13 actions x 9 kinds of holder, both directions, not derived from `RULES`), plus cross-org and cross-project, ids/actions that exist on every object (`__proto__`, `constructor`), unknown role names and kinds, scopes (narrow, never widen, wildcard, not a pattern, malformed input never throws).
- **Mutations, 22 run, 20 killed**: rank `>`/`>=` for org and project, each inherited role, direct role ignored, inherited ignored, `in` instead of `hasOwn` for actions, scopes ignored/any/loose prefix, token without scopes, kind unchecked (survived first; test added), CI platform admin, truthy platform flag, project ids optional, `project.delete` / `secret.reveal` / `organization.read` rules loosened, no array guard, no string guard. Two survivors are equivalent for now: viewer inheriting `developer` (no action needs the developer rank yet, so nothing can observe it) and the plain lookup instead of `hasOwn` in `own` (a prototype value is never a role name, so the later rank check rejects it; `hasOwn` stays as belt and braces).
- `/code-review` (medium) found 6. Fixed: malformed `scopes` (null, a string, non-strings) made `can` throw, against its "total" promise; a test assertion that passed for the wrong reason. Dismissed: project roles are keyed by project id alone (the resource's ids must come from the stored row, as the `Resource` doc says; **AUTH-3's guard must build it that way, never from path parameters alone**); an own `__proto__` key from `JSON.parse` (needs attacker-chosen role-map keys and ids); an `assertCan` that maps a denial to 403/404 (AUTH-3's guard); typed resources per rule kind (a wrong shape fails closed).
- Security (inline): no I/O, no secrets, no state. Fails closed on every path I could find. The risk is in what feeds it: whoever builds the `Subject` (AUTH-3/5/6) and the `Resource`.
- Follow-ups for AUTH-3: list routes need filtering by the subject's roles (`can` answers per resource); a `platformAdmin` source; the 403-or-404 rule.
- No new dependencies.

## 2026-10-17 AUTH-3 (REVIEW: authorization model in the API, dev-auth switch)

- **What:** every route declares `guard: "<action>"`, `signedIn: "<reason>"` or `public: "<reason>"` (macros in `apps/api/src/guard.ts`, shown in OpenAPI as `x-guard` / `x-signed-in` / `x-public`). `createApp` throws at start if a route has none (`GET /openapi/json` is the one allowlisted route). `sessionPrincipal` (`session.ts`) turns the `orch_session` cookie into a `Principal` (only the SHA-256 is looked up); no cookie, an unknown or an ended session is anonymous (401). `auditPlugin` accepts anonymous callers; a route names the actor itself (sign-in) or the audit is refused. `GET /organizations` lists only the organizations the caller can read (`visibleOrganizations`, `listOrganizations(..., only)`).
- **Answers:** no caller 401; allowed by `can()` pass; a caller who cannot read the parent (project, else organization) gets 404 with the same text whether or not it exists; any other refusal 403 `Not allowed: <action>`. `organization.create` has nothing to hide: 403. The guard runs in the macro's `transform`, so after the body is parsed and before it is validated (verified by experiment): a bad JSON body is a 400 before the caller is known, a schema error 422 only for callers that passed.
- **Decisions to check (please review):**
  - **Path ids are trusted** (the AUTH-2 note said to build the resource from the stored row). They are safe only because every query repeats org and project ids (composite keys: a mismatch is a 404). Every future route (variables, secrets, tokens) must keep that; it is written in the `Resource` doc in `authz.ts` and checked by the cross-org tests, not by the type system.
  - A scoped token or CI job gets 404 for anything its scopes cannot read, and 403 only where the scope lets it read the parent. A narrow token learns nothing about what exists; the cost is a less helpful error. (`/code-review` flagged it; kept.)
  - The project list needs `organization.read`, so a project-only member cannot list the org's projects.
  - `GET /openapi/json` is public (the same document is committed as `docs/openapi.json`).
  - **Dev switch:** `ORCH_DEV_AUTH=1` (exact literal) selects the all-powerful dev principal. `index.ts` refuses it unless `NODE_ENV` is development/test and `HOST` is loopback, and logs "authentication is off". `bun run dev` sets it. Without it the API starts with session auth in any environment (before, production refused to start). This changes the previous "dev principal is refused in production" rule into "dev auth is refused in production".
  - `ORCH_PLATFORM_ADMIN_GITLAB_IDS` (comma separated, safe integers; empty means none) is the platform admin source. A platform admin can create an organization and then cannot read it, because **nobody holds a role until AUTH-5** (default `roles` is empty; a throwing `roles()` fails the request). Tested and documented.
- Gate: `bun run check` green, 467 pass + 1 skip. New: `guard.test.ts` (answers, 403/404, scopes, order of checks, declarations, tripwire), `session.test.ts`, `authz.test.ts` (real app, real sessions: 15 non-public routes all 401 anonymously, role matrices, cross-org, list filtering and paging, audit actor, coverage tables of every route's guard), plus `main.test.ts`, `audit.test.ts`, `auth-config.test.ts`, `spec.test.ts`, `core/authz.test.ts`.
- **Mutations, 43 run, 42 killed:** anonymous passes, dev inverted, no/always 404, parent action, wrong param, project id ignored, signedIn lets anonymous in, `beforeHandle` instead of `transform`, unknown action accepted, each OpenAPI marker, allowlist by path only, org-create hiding, missing reasons, 403 text, 404 naming the id, scopes ignored on the parent check; session: everyone/nobody platform admin, roles dropped, token not hashed, wrong cookie, role failure swallowed; audit: actor precedence, anonymous allowed (survived first: the NOT NULL column also gave a 500; the test now checks the refusal message); org list unfiltered/dev filtered/non-dev unfiltered, `only` ignored, empty `only` means all, `visibleOrganizations` unfiltered; entrypoint: dev auth in production, non-loopback, always dev, platform admins not passed (survived first; test added). **Survivor:** the start-up tripwire in `createApp` (`if (open.length > 0) throw`) has no seam to test; the coverage tests assert the same property.
- `/code-review` (medium) found 8. Fixed: an empty `ORCH_PLATFORM_ADMIN_GITLAB_IDS` crashed start-up and ids above 2^53 would be rounded; the README still said every caller is the dev principal. Dismissed: public OpenAPI (above); 404 for scoped callers (above); session lookup on public routes (it only happens with an `orch_session` cookie; `/auth/me` and logout look the session up twice, which is cheap); the platform-admin dead end (documented until AUTH-5); `dev` special-cased in two places (a token or CI resolver cannot produce it: `Subject["kind"]` has no `dev`); guard ordering (a guard without the principal plugin answers 401, so it fails closed and the coverage tests catch it); the "completion doc per task" rule in the home `CLAUDE.md` (the factory writes it per feature).
- Security (inline): no secret reaches a log, error or audit row (the logger redacts cookie/session/token keys; tests cover the session token). Every path I could find fails closed: no principal, unknown action (throws at route definition), a throwing role source, a throwing session lookup. Cookies are HttpOnly, SameSite=Lax, Secure over https; unsafe methods need a JSON body (415 guard), so a cross-site form cannot reach them. No existence oracle between a missing and a hidden org or project (same text, tested). `/security-review` is unusable here (no remote).
- **Known limits:** nobody holds a role until AUTH-5, so only the dev principal and platform-admin organization creation work; sessions are not revoked when GitLab blocks the user (AUTH-1 limits stand); the body is parsed before the caller is checked, so a malformed body is a 400 for anyone; the `createApp` tripwire is not directly tested; the Windows `cmd` shell cannot run the `dev` script's inline `ORCH_DEV_AUTH=1`.

## 2026-10-17 AUTH-4 (REVIEW: token format, token-to-role model)

- **What:** `POST/GET /api/v1/tokens`, `DELETE /api/v1/tokens/:tokenId` (`signedIn`, own tokens only). A token is `orch_<8 id chars>.<43 char secret>` (256 bits). The server stores only its SHA-256 and a display `prefix`; the secret is returned once, with `cache-control: no-store`, and cannot be read back. Table `api_tokens` (migration `0006_api_tokens`, additive, `updated_at` trigger). `callerPrincipal` (`credentials.ts`) resolves the caller: an `Authorization: Bearer <orch-shaped token>` decides alone (a bad token is a hard 401, no fallback to the cookie); any other `Authorization` header is ignored and the cookie is used. `isScope` in `core` validates scopes at creation.
- **Decisions to check (please review):**
  - **Lookup is by hash, not by prefix.** The prefix is for display and for recognising a leaked token; it is never compared.
  - **Expiry is mandatory:** default 30 days, 1..365 (`MAX_TOKEN_TTL_DAYS`), on the database clock. Revoking keeps the row.
  - **A token acts as its owner.** Roles are resolved per request (`roles(user)`, same source as sessions), narrowed by the token's scopes (they only narrow, as AUTH-2 says). The owner's platform-admin status is inherited, subject to the `organization.create` scope. `*` is allowed as a scope and never widens.
  - **Only signed-in users manage tokens.** A token (even with `*`) and the dev principal get 403, so a token cannot mint tokens. Another user's token is 404 on revoke.
  - The audit actor of a token request is `{kind: "token", id: <token id>}`; the owner is found through the token row.
  - `last_used_at` is written at most once a minute (the select computes `stale` on the database clock; a busy token costs one query, not a write).
- Gate: `bun run check` green, 501 pass + 1 skip. New: `api-tokens.test.ts` (db: hash only, scopes, expiry on the DB clock, refused non-digests and lifetimes, unique hash, cascade with the user, use/throttle/expired/revoked/unknown, revoke once and own only, list own only, paged), `tokens.test.ts` (API: create shown once with no-store, 30-day default, validation, list never shows the secret or hash, revoke, 404 for others' tokens, token and dev principal refused, bearer rules, scopes narrow, audit actor and no secret in any log line or audit row), `core/authz.test.ts` (`isScope`), bearer entrypoint test in `main.test.ts`, coverage tables.
- **Mutations:** first pass 47 run (14 of them in the refactored code), survivors: 3 equivalent (shape pre-filter, which is only an optimisation; subject kind in the principal, which `can()` never reads for users; the DTO stripping the hash, which the response schema strips anyway) and 2 real (scheme optional in the header, token owner never platform admin), both fixed with tests and then killed. After the review refactor, 21 more on `tokenOf`/`bearerPrincipal`, the `stale` throttle, `scopeMatches`/`isScope` and `MAX_TOKEN_TTL_DAYS` plus 6 on the db lookup/lifetime checks: all killed.
- `/code-review` (medium) fixed: the header logic (a non-token `Authorization` header must not shadow a valid cookie; a bad token must not fall back), the `stale` select (one query instead of an unconditional update), scope matching shared between `can()` and validation (`scopeMatches`), the TTL constant. Dismissed: completion doc per task (the factory writes it per feature).
- Security (inline): only the SHA-256 is stored and looked up; the secret is shown once and never logged (tests scan every log line and audit row for it); constant-time comparison is not needed because the lookup is an indexed equality on a hash of a 256-bit secret; expired, revoked, unknown and malformed tokens are one 401; no existence oracle on revoke. `/security-review` is unusable here (no remote).
- **Known limits:** no cap, rate limit or pruning of tokens per user, and the list shows revoked and expired tokens forever; the owner is not in the audit row (follow-up: an "on behalf of" column); no admin revoke of someone else's token; a GitLab user blocked after the token was made keeps a working token until the roles source (AUTH-5) drops them; `last_used_at` lags by up to a minute; failed bearer attempts are not audited or rate limited.
- No new dependencies.

## 2026-10-17 AUTH-5 (REVIEW: GitLab-to-role mapping, link columns)

- **What:** roles now come from GitLab. `organizations.gitlab_group_id` (migration `0007_org_gitlab_group`, additive, nullable, partial unique index) links an organization to a GitLab group; `projects.gitlab_project_id` already linked a project. For a signed-in user (session or token owner) `gitlabRoles` (`apps/api/src/membership.ts`) asks GitLab for the user's access level on every linked group and project (`GET /groups|projects/:id/members/all/:user_id`, inherited and invited members included) and maps it with `orgRoleOf` / `projectRoleOf` (`core/membership.ts`). The user is keyed by the GitLab id stored at sign-in, never by name. New in `packages/gitlab`: `members.accessLevel(owner, userId)` and `users.current()`; the mock got users, members and inheritance (`addMember`, `removeMember`, `tokenUser`). `GITLAB_MEMBERSHIP_TOKEN` (needs the four sign-in settings) wires it in `index.ts`; without it nobody holds a role (a start-up warning says so). `POST /organizations` accepts `gitlabGroupId`; the patch still rejects it.
- **Decisions to check (please review):**
  - **Mapping.** Group: Reporter and Security Manager -> viewer, Developer -> member, Maintainer -> admin, Owner -> owner. Project: Reporter and Security Manager -> reporter, Developer -> developer, Maintainer and Owner -> maintainer. Minimal, Guest, Planner and any level GitLab adds later hold nothing (deny by default). Both tables are in `core/membership.ts` and pinned by tests level by level.
  - **Active only.** Level counts only if the account `state` is `active` and the `membership_state` is active (an invite awaiting approval holds nothing; a missing `state` holds nothing). A blocked GitLab user loses API roles within the TTL.
  - **Fail closed.** If GitLab cannot answer (401, 403, 429, 5xx, timeout, network, a body that does not decode) the request fails with 503 `membership_unavailable`, nothing is guessed, an expired answer is never served in its place, and the failure is not cached. Only a 404 reads as "not a member" (GitLab answers 404 for non-members and for what the token cannot see). The log line names kind, status and the GitLab message (no token); 401 and 403 log at error, the rest at warn.
  - **Cache.** Per GitLab user id, 5 minutes (`ttlMs`), at most 10 000 users, oldest first; callers at the same moment share one lookup; at most 8 GitLab calls at once, none start after one fails.
  - **The organization's group link is immutable** (set on create by a platform admin, unique, no relink path): relinking would let whoever can patch an org make GitLab's members of another group its owners. Linking an existing organization is therefore impossible for now (follow-up: an owner-only relink, as a human gate).
  - **A project's `gitlabProjectId` may be changed by a maintainer** and decides who gets roles on it (see limits).
  - The membership token needs `read_api` and must be a member (or admin) of every linked group and project: a link it cannot see reads as "no members" (404) without a log line.

Kept and recorded below: one bad link fails every user's lookup (503), the creator of a link waits for the TTL, the fan-out per user, a 404 token problem is silent, project links may cross organizations, the two `gitlabLinks` queries are sequential. Dismissed: decode/DB errors unlogged (a malformed GitLab body is a `GitlabError("unexpected")` and is mapped and logged; a DB error reaches the global handler); no CHECK on the bigint (the API validates, as for `gitlabProjectId`); a membership token without the OAuth keys (refused on purpose: tokens are minted by signed-in users); the completion doc per task (the factory writes it per feature).

The membership token is only read from the environment into the GitLab client; config errors name keys, never values (tested), and neither the log nor the 503 holds the token or the URL path (tested). Roles derive only from active members, deny by default for unknown levels and for any failure. Org link changes cannot be made through the API after creation.
