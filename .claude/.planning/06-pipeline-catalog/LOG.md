## 2026-10-17 PIPE-3 (done before PIPE-2)
- Order: PIPE-3 before PIPE-2. Both depend only on PIPE-1, and PIPE-2's "renders with defaults, snapshots committed" needs the real renderer, so doing PIPE-2 first would have meant a throwaway one. No task added or removed.
- **New dependency: `yaml` 2.8.1 (exact pin, `packages/pipelines`).** Why not `Bun.YAML` (checked): its `stringify` leaves a trailing space after every key, writes `2026-01-01` as a plain scalar (GitLab's Ruby parser reads a date, not text) and the parser silently drops tags such as `!reference`. `yaml` gives the quoting rules of YAML 1.1 (what GitLab reads), a document model to refuse tags, duplicate keys and keys that are maps, and stable output. The GitLab mock (`packages/gitlab/src/mock/server.ts`) still uses `Bun.YAML` for its own lint stand-in; it is a test double and is left alone.
- `pipeline.ts`: `parsePipeline(text)` reads a template strictly (one document, unique keys, merge keys and anchors expanded, no tags, no map as a key which is what an unquoted `{{ params.x }}` parses to, aliases that don't loop, JSON values only) and `checkPipeline(manifest, text)` lists what is wrong: a placeholder that is not exactly `{{ params.name }}` (docker-style `{{.Names}}` is left alone), a placeholder in a key, a parameter used and not declared (own keys only), a parameter declared and never used. `loadTemplates` now calls it instead of `Bun.YAML` (PIPE-1's follow-up on parser divergence is closed).
- `render.ts`: `render(template, layers)` -> text of a `.gitlab-ci.yml`. A `Layer` is `{ params?, overrides? }`, lowest first (org defaults, project, environment). Params: later layer wins per name, `undefined` changes nothing, checked by `paramsSchema` (defaults filled, unknown refused). Placeholders are filled in parsed string **values** only: a placeholder that is the whole value keeps its type (`retry: 2`), one inside text is text, keys are never touched, and a value that itself holds `{{ ... }}` is not filled again. Then each layer's `overrides` is merged over the result: maps merge key by key (left order, new keys after), a list or a scalar replaces, no placeholders in overrides. Output: header comment naming `template@version`, YAML 1.1 quoting, 2-space indent, no line folding, anchors expanded, template key order kept. Before returning, the text is read back as YAML 1.1 and 1.2 and must equal the tree; if not (a param `0o17` reads as a number in 1.2), `RenderError` rather than a file that says something else. Errors name layers/parameters/keys, never a value (tested with a canary).
- **Manifest rule added (PIPE-1 code, found in review):** a string parameter must declare `enum` or `pattern`, because string params land in `script:` lines and "inert" only covers YAML structure, not shell. A template that wants free text says so with a pattern of its own.
- Tests: 145 in the package (pipeline 22, render 67, loader 11, manifest 45). Render covers exact output, typed vs text placeholders, precedence across layers, merge/replace rules, 38 hostile values in 3 places read back identically as YAML 1.1 and 1.2, a seeded 400-string property run (refused count bounded), `__proto__` in params and overrides, overrides literal, no mutation of inputs, error aggregation.
- Mutations: 43 checked (render fill/merge/layering/read-back/writer options, parser strictness, placeholder checks, the new string rule, loader call). 2 survive, both equivalent: R17 (read back as 1.2 only: the writer already quotes for 1.1, so the 1.1 read-back is a second line of defence) and R20 (`aliasDuplicateObjects` true: `fill` and `merge` copy every object, so the writer never sees a shared one).
- `/code-review` (medium) found 10. **Fixed:** string params could carry shell syntax (rule above); a later layer's `undefined` (or a `__proto__` key through `Object.assign`) clobbered earlier params; the loader test pinned `yaml`'s wording. **Dismissed:** the `|| !checked.success` guard (it narrows the type and `problems` covers layer errors); `<<` in an override giving a generic error (rare, the check refuses it safely); replacing a map by `null` (PIPE-5 lints the result); first-line-only yaml messages (position is on that line); re-parsing per render (not a hot path); unused-parameter rule (deliberate typo guard); the second parser (done above).
- Flaky test and gate: see PIPE-1. Gate: `bun run check` green, 1789 pass + 1 skip.
- Inline security review: no network, no credentials. Values can't become structure (filled after parsing, written by a serializer, read back and compared). A string param can't carry shell syntax unless its template allows it with an explicit pattern. **`overrides` can add or replace any job, so whoever may set them can make the project's pipeline run anything: PIPE-6 must put them behind the same guard as writing `.gitlab-ci.yml` (REVIEW).** Params are written into the repo in the clear, so they must never hold a secret (variables are for that): documented, not scanned.
- **Limits / follow-ups:** `!reference` and other tags are refused, not supported; template comments are dropped (the output has one generated header); integer-like keys (`"1": ...`) are reordered by JS objects; the rendered text is not linted here (PIPE-5); `0o17`-like values are refused; a literal `{{ params.x }}` cannot be written in a template; layers hold the template's `params` and `overrides` only, there is no way to delete a key (only replace); no org/project/environment storage of layers yet (PIPE-6).

## 2026-10-17 PIPE-9
- Built: include mode. A project's pipeline can be a thin `.gitlab-ci.yml` (`include:` of `<name>/<version>/pipeline.yml` in a templates project, with the parameters as `inputs`) instead of the whole rendered file. `packages/pipelines`: `renderInclude(template, layers, {project, ref?})` (same layers, params and overrides as `render`; project path and ref are checked; `include` cannot be overridden), `includeFile(template)` (the file the templates project must hold: a `spec:` of inputs made from the manifest, then the pipeline with `{{ params.x }}` as `$[[ inputs.x ]]`), `includePath`, and `readBack` shared by both renderers (YAML 1.1 and 1.2, every document). `bun run templates:include <dir>` writes those files (`packages/pipelines/src/include-files.ts`).
