# 06 Pipeline Catalog - Log

## 2026-10-17 PIPE-1
- New package `packages/pipelines` (`@orch/pipelines`; deps `@orch/core`, `zod`, both already in the repo). `manifestSchema` (strict): `name` (`/^[a-z][a-z0-9-]{0,63}$/`), `version` (`x.y.z`), `description`, `params` (a JSON-Schema-subset object: scalar `string|number|integer|boolean` parameters with `description`, `default`, `enum`, `pattern`, `maxLength`, `minimum`, `maximum`; `required`; no extra keys anywhere), `detects` (project tags from `PROJECT_TAGS`), `requiresVariables` (`KEY_PATTERN` keys). `superRefine` makes a manifest that could never validate an input a load error: a `required` name that is not declared (own keys only, so `toString` is not), required with a default, a `pattern` that is not a regular expression or sits on a non-string, `maxLength` on a non-string, `minimum`/`maximum` on a non-number or an empty range, an `enum` value or `default` that its own parameter would refuse (each error names the parameter and field).
- `paramsSchema(manifest)` builds the validator for a render's parameters (zod `fromJSONSchema`, `additionalProperties: false`, defaults filled). Every string is capped at `DEFAULT_MAX_LENGTH` (1000) unless the manifest sets `maxLength`.
- `loadTemplates(root = TEMPLATES_DIR)` reads `<root>/<name>/<version>/{manifest.json,pipeline.yml}`, sorted by name then version as numbers (`1.10.0` after `1.2.0`). Every problem across all templates is collected into one `TemplateError(problems)` (missing file, not JSON, schema issue with its path, name/version different from the directory, pipeline not YAML or not a mapping). Plain files and dot-directories at any level are ignored; a missing root is the raw error, not an empty catalog.
- Tests: 53 (`manifest.test.ts`, `loader.test.ts`; a rejection table that asserts exactly one issue at an exact path, so a row cannot pass for the wrong reason).
- Mutations: 24 checked on the manifest and loader (each refine, both defaults, the length cap and its override, strictness at every level, directory/name/version match, numeric version order, presence checks, aggregation, dot-directories). 1 survived at first (Q11: the `.git/HEAD` fixture held only a file so the dot-directory filter never mattered): fixture now has a version directory inside `.cache`; killed. None left.
- `/code-review` (medium) found 7 on the first version. **Fixed:** `name in properties` accepted inherited names (`Object.hasOwn`); invalid `pattern` only failed at render time; unsatisfiable constraints (empty range, `required` with a default, enum values that break their own pattern) loaded fine; unbounded strings; dot-directories read as templates. **Dismissed:** none worth a note.
- Flaky test found in the full gate and fixed (SYNC-8, not PIPE-1): `events()` in `sync-runs.test.ts` had no `ORDER BY`, so `.at(-1)` of the drift events could be the older one (1 run in 3). Now ordered by `at`; 6 repeat runs and the full gate green.
- Inline security review: the loader reads only a fixed directory inside the repo (names come from `readdir` and are joined as path segments, so no traversal); manifests and pipelines are repo-trusted data, never executed; parameters are inert scalars with a length cap; no network, no credentials, no secrets.
- Gate: `bun run check` green, 1697 pass + 1 skip. New dependency: none.
- **Limits / follow-ups:** the loader parses YAML with `Bun.YAML` and PIPE-3 will render with the `yaml` package (new dependency, justified there): PIPE-3 must switch the loader to the same parser so they cannot disagree; GitLab's `!reference` tags and unquoted `{{ }}` placeholders are not understood yet (templates must quote placeholders; the renderer detects unquoted ones); symlinked directories are ignored; files are checked one at a time (fine for a catalog of tens); `TEMPLATES_DIR` does not exist until PIPE-2 adds templates; patterns are repo-trusted and only length-capped, not ReDoS-proof; uses `import.meta.dir` and `Bun.YAML` (Bun only).

## 2026-10-17 PIPE-3 (done before PIPE-2)
- Order: PIPE-3 before PIPE-2. Both depend only on PIPE-1, and PIPE-2's "renders with defaults, snapshots committed" needs the real renderer, so doing PIPE-2 first would have meant a throwaway one. No task added or removed.
- **New dependency: `yaml` 2.8.1 (exact pin, `packages/pipelines`).** Why not `Bun.YAML` (checked): its `stringify` leaves a trailing space after every key, writes `2026-01-01` as a plain scalar (GitLab's Ruby parser reads a date, not text) and the parser silently drops tags such as `!reference`. `yaml` gives the quoting rules of YAML 1.1 (what GitLab reads), a document model to refuse tags, duplicate keys and keys that are maps, and stable output. The GitLab mock (`packages/gitlab/src/mock/server.ts`) still uses `Bun.YAML` for its own lint stand-in; it is a test double and is left alone.
- `pipeline.ts`: `parsePipeline(text)` reads a template strictly (one document, unique keys, merge keys and anchors expanded, no tags, no map as a key which is what an unquoted `{{ params.x }}` parses to, aliases that don't loop, JSON values only) and `checkPipeline(manifest, text)` lists what is wrong: a placeholder that is not exactly `{{ params.name }}` (docker-style `{{.Names}}` is left alone), a placeholder in a key, a parameter used and not declared (own keys only), a parameter declared and never used. `loadTemplates` now calls it instead of `Bun.YAML` (PIPE-1's follow-up on parser divergence is closed).
- `render.ts`: `render(template, layers)` -> text of a `.gitlab-ci.yml`. A `Layer` is `{ params?, overrides? }`, lowest first (org defaults, project, environment). Params: later layer wins per name, `undefined` changes nothing, checked by `paramsSchema` (defaults filled, unknown refused). Placeholders are filled in parsed string **values** only: a placeholder that is the whole value keeps its type (`retry: 2`), one inside text is text, keys are never touched, and a value that itself holds `{{ ... }}` is not filled again. Then each layer's `overrides` is merged over the result: maps merge key by key (left order, new keys after), a list or a scalar replaces, no placeholders in overrides. Output: header comment naming `template@version`, YAML 1.1 quoting, 2-space indent, no line folding, anchors expanded, template key order kept. Before returning, the text is read back as YAML 1.1 and 1.2 and must equal the tree; if not (a param `0o17` reads as a number in 1.2), `RenderError` rather than a file that says something else. Errors name layers/parameters/keys, never a value (tested with a canary).
- **Manifest rule added (PIPE-1 code, found in review):** a string parameter must declare `enum` or `pattern`, because string params land in `script:` lines and "inert" only covers YAML structure, not shell. A template that wants free text says so with a pattern of its own.
- Tests: 145 in the package (pipeline 22, render 67, loader 11, manifest 45). Render covers exact output, typed vs text placeholders, precedence across layers, merge/replace rules, 38 hostile values in 3 places read back identically as YAML 1.1 and 1.2, a seeded 400-string property run (refused count bounded), `__proto__` in params and overrides, overrides literal, no mutation of inputs, error aggregation.
- Mutations: 43 checked (render fill/merge/layering/read-back/writer options, parser strictness, placeholder checks, the new string rule, loader call). 2 survive, both equivalent: R17 (read back as 1.2 only: the writer already quotes for 1.1, so the 1.1 read-back is a second line of defence) and R20 (`aliasDuplicateObjects` true: `fill` and `merge` copy every object, so the writer never sees a shared one).
- `/code-review` (medium) found 10. **Fixed:** string params could carry shell syntax (rule above); a later layer's `undefined` (or a `__proto__` key through `Object.assign`) clobbered earlier params; the loader test pinned `yaml`'s wording. **Dismissed:** the `|| !checked.success` guard (it narrows the type and `problems` covers layer errors); `<<` in an override giving a generic error (rare, the check refuses it safely); replacing a map by `null` (PIPE-5 lints the result); first-line-only yaml messages (position is on that line); re-parsing per render (not a hot path); unused-parameter rule (deliberate typo guard); the second parser (done above).
- Flaky test and gate: see PIPE-1. Gate: `bun run check` green, 1789 pass + 1 skip.
- Inline security review: no network, no credentials. Values can't become structure (filled after parsing, written by a serializer, read back and compared). A string param can't carry shell syntax unless its template allows it with an explicit pattern. **`overrides` can add or replace any job, so whoever may set them can make the project's pipeline run anything: PIPE-6 must put them behind the same guard as writing `.gitlab-ci.yml` (REVIEW).** Params are written into the repo in the clear, so they must never hold a secret (variables are for that): documented, not scanned.
- **Limits / follow-ups:** `!reference` and other tags are refused, not supported; template comments are dropped (the output has one generated header); integer-like keys (`"1": ...`) are reordered by JS objects; the rendered text is not linted here (PIPE-5); `0o17`-like values are refused; a literal `{{ params.x }}` cannot be written in a template; layers hold the template's `params` and `overrides` only, there is no way to delete a key (only replace); no org/project/environment storage of layers yet (PIPE-6).

## 2026-10-17 PIPE-2
- Three starter templates under `packages/pipelines/templates/<name>/1.0.0/`: `bun-app` (detects `bun`), `node-app` (detects `node`, npm + `package-lock.json`), `docker-image` (detects `docker`). Bun/Node: stages `check` (typecheck, lint, test) and `build` (artifact: the build output dir, 1 week), pipelines on merge requests and the default branch; every job installs for itself (the cache, keyed on the lockfile, only makes that quick). Docker: a `build` job on merge requests only builds; a `publish` job on the default branch logs in with the CI-provided `$CI_REGISTRY_*` variables and pushes `:<short sha>` and `:latest`. All parameters have defaults, so `requiresVariables` is empty for all three (the registry login uses variables GitLab itself provides).
- Every string parameter has a pattern: versions `^[0-9][0-9A-Za-z.-]{0,30}$`, script names `^[A-Za-z0-9_][A-Za-z0-9:_-]{0,39}$`, paths `^(?![/-])(?!.*\.\.)[A-Za-z0-9._/-]{1,100}$` (no leading `/` or `-`, no `..`). Review found that a leading `-` lets a value become an option (`testScript: "--version"` makes `bun run --version` pass with no tests); the patterns now forbid it.
- Tests (`templates.test.ts`, 27): the catalog is exactly the three, each suits its project tag, each default render is a committed snapshot (`__snapshots__/templates.test.ts.snap`), every job runs in a declared stage, a given parameter reaches the output, and every non-enum string parameter of every template refuses 20 hostile values (shell syntax, quotes, newline, `..`, absolute path, `-x`, `--help`, `~`, `*`, empty).
- Mutations: 2 checked on the tightened patterns (leading `-` allowed again in script names; in paths): both killed by the hostile-value test. The templates have no logic of their own beyond that.
- `/code-review` (medium) found 5. **Fixed:** leading `-` in script names and in `dockerfile`/`context`; nasty-value list lacked option-like values; the docker `build` job pushed a commit-tagged image from every merge request (now MRs build only, push happens on the default branch). **Not changed:** every check job in a pipeline uploads the same `node_modules`/`.npm` cache (redundant uploads, harmless: same content, last wins).
- Gate: `bun run check` green, 1816 pass + 1 skip. New dependency: none.
- **Limits / follow-ups:** the rendered pipelines have never been linted by GitLab (PIPE-5 does it against the mock, a real lint is a later human step); `bun.lock` cache key assumes Bun 1.2+ text lockfile; a project without those `package.json` scripts needs other script names or overrides; `docker-image` needs a runner that allows Docker-in-Docker (privileged) and a project with the container registry enabled; `latest` moves on every default-branch pipeline; the MR build does not log in, so a Dockerfile that pulls a private base image from the project's registry fails on merge requests.
