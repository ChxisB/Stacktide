- **Decisions and deviations (report these):**
  - The lock's owner is the job (`ci:<project>:job-<id>`), and **the lock id alone proves nothing**: a refusal shows the holder's id to everyone (Terraform prints it), so every release and every write also needs the owner to be the holder. Unlock needs the owner *and* the id (ADR-0017 #7); `POST ?ID=` needs both; `DELETE` of the state needs the owner only, because Terraform's delete sends no id.
  - A write with a lock held and no `?ID=` is refused with 423 even for the holder; a write when no lock is held needs nothing (a `-lock=false` job on a protected ref is not refused, and nothing is held off, as with any Terraform backend).

  - Releasing what is not held (never taken, expired) is a 200 `{released: false}`, because Terraform can unlock after the token ended; an `UNLOCK` with no lock info is 422 `invalid_lock`, so `terraform force-unlock` from a CI job (which sends none) does not work: the admin API is the way.

A lock needs no master key. `LOCK` needs the stack to be in the scan (403 `unknown_stack`); `UNLOCK` and force-unlock do not, so a removed stack's lock can still be ended.
  - Force-unlock is `POST .../force-unlock` with the new action `state.force_unlock` (org admin), through a session or an API token; the CLI has none (STATE-10 is read-only). It answers only `{released}`: the holder's lock info is not returned to the admin.
  - `LOCK`/`UNLOCK` are left out of `docs/openapi.json` (not OpenAPI verbs; they appeared as `lock` and `unlock` path-item keys); the `POST`/`DELETE .../lock` aliases are documented.
  - Deleting a project with a lock held succeeds (the lock cascades); with state it still gives 409.
