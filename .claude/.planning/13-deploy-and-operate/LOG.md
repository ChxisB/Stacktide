# 13 Deploy and Operate - Log

## 2026-10-18 OPS-3 Metrics
- **What:** `GET /metrics` in the Prometheus text format, behind a static bearer token and off unless one is configured. Docs: `docs/metrics.md`.
  - `apps/api/src/metrics.ts`: a small registry (counter, histogram, text render, label escaping), a per-family cap of 500 label sets (`orch_metrics_series_dropped_total` counts what it refused), `requestMetrics`, `renderStats`, `bearerMatches` (SHA-256 digests of both sides compared with `timingSafeEqual`).
  - `apps/api/src/http.ts` reports every response to an observer; the `route` label is the **registered pattern** (`unmatched` when no route matched), the method is one of the seven known verbs or `other`.
  - `apps/api/src/app.ts`: the route. No `ORCH_METRICS_TOKEN` -> 404; wrong or missing token -> 401 with `WWW-Authenticate: Bearer`; a failing read -> logged, 503 `metrics_unavailable` with no detail. Queue and run figures are cached for 5 s, a failed read is not kept.
  - `packages/db/src/metrics.ts`: `operationalStats` counts `jobs` (per queue and status), `sync_runs` and `run_stacks` (per status) and the age of the oldest waiting job (due `run_at`), running job (`locked_at`), applying sync run, queued/planning/applying stack run.
  - `packages/gitlab/src/client.ts`: the `RateLimit-Remaining`/`RateLimit-Limit` headers of every response are sampled per `host[:port]` (at most 20 hosts), exposed by `gitlabRateLimits()`.
  - `.env.example`: a commented `ORCH_METRICS_TOKEN` block (min 32 chars). `docs/openapi.json` regenerated.
- **Deviation from the SPEC wording:** run **durations** are not delivered. `sync_runs` and `run_stacks` keep no start time (only `createdAt`/`updatedAt`) and `jobs` clears `lockedAt` on completion, so there is nothing to subtract. State counts and the age of the oldest in-flight item are delivered instead. A histogram needs a start-time column (a migration) and is a follow-up.
- **Tests:** 15 in `apps/api/src/metrics.test.ts` (names/labels, registered route not asked path, unknown route and method folding, cardinality guard, escaping, auth matrix, 404/401/503, no token or secret in any output or log, cache and failed-read behaviour), 3 in `packages/db/src/metrics.test.ts` (against real Postgres), 4 in `packages/gitlab/src/client.test.ts` (header parsing, host cap, last-answer-wins).
- **Mutation checks:** 30 mutants (token compare, scheme/anchor, prefix match, 404/401 branches, challenge header, content type, cache, failed-read memo, error detail, route label, method folding, series cap and its counter, escaping, bucket cumulation, histogram sum, undeclared labels, gauge row cap, empty-age handling, GitLab host cap, header parsing, host label, and the `where` filters of the three queries). 27 killed at first; the 3 survivors (scheme not anchored at the start, gauge rows not capped, a negative age) got tests (`xBearer`/`Basic Bearer` headers, 525 rows, a job locked "in the future") and are killed. One equivalent mutant is not in the list: `given !== ""` is unreachable with a token of at least 32 characters.
- `/code-review` (medium): 9 findings. Fixed: the three queries now run concurrently. Checked, no change: the `WWW-Authenticate` header does survive the error mapper (asserted, mutant T6). Documented in `docs/metrics.md`: `/metrics` scrapes count in the request figures; the rate limit is the last answer per host, not per token; the 20-host cap and the 500-row gauge cut are silent; full group-by scans per scrape (the `shortcut:` note); API process only.
- Inline security review: the token is compared as digests in constant time; it is never logged, echoed or put in a label (asserted over output and logs); labels are code-defined names, route patterns and the GitLab host, never an id, key, value or payload; the endpoint is off by default and unauthenticated callers learn nothing (401 body has no `orch_` lines).
- **REVIEW (design gates and facts I could not verify):**
  1. **Auth model:** a static bearer token from the environment, one for the whole instance, no rotation story beyond redeploying, and **no rate limit** on failed attempts until OPS-5. The dev principal is deliberately not enough.
  2. **Per process:** request figures are the API process's own (one scrape target per replica); the worker has no `/metrics` and no HTTP listener, and the GitLab rate limit shown is only what the API process saw (the worker makes most of the GitLab calls).
  3. **Run durations are not delivered** (above). Counts of `done` jobs and finished runs shrink when rows are deleted, so they are gauges, not counters.
  4. The queue/run figures are full `group by` scans at scrape time, cached 5 s (`shortcut:` in the code); move to maintained counters when the `jobs` table is large.
  5. The `host` label comes from base URLs that organizations choose (capped at 20, first seen kept, the rest silently not shown).
  6. Two structural test lists were extended, nothing weakened: `/metrics` is a public route (`authz.test.ts`, with the reason "scraped by Prometheus ... answers 404 without one") and is excluded from the documented operations (`spec.test.ts`, like `/health`).
  7. A scrape holds up to three pool connections at once (the stats queries run concurrently).
- Gate: `bun run check` green: 4029 pass + 2 skip + 0 fail (root), 240 pass (web). New dependencies: none.

## 2026-10-18 OPS-5 Hardening
- **What:** rate limits, CORS allowlist, security headers, body limits, a `bun audit` CI job. Docs: `docs/hardening.md`. Cookie flags were already asserted (`auth.test.ts`: HttpOnly, SameSite=Lax, Path, Max-Age, and `Secure` over https); nothing added there.
  - `apps/api/src/rate-limit.ts`: fixed-window in-memory counters and a `limit:` route macro. Each route declares its class (`x-rate-limit` in the route detail and the OpenAPI doc); a route that declares none is simply unlimited, one with an unknown class or an app without a limiter fails with 500 (a wiring error, asserted). Classes (`LIMITS`): `login` 30 per 5 min (IP; browser and CLI sign-in routes share it), `ci_exchange` 600/min (IP), `webhook` 600/min (IP), `token_create` 10 per 10 min (the caller), `reveal` 60/min (the caller; single reveals and environment exports). A token counts as its owner. A signed-out caller of a caller class is counted by IP. The dev principal is never limited. Refusal: 429 `rate_limited` with `Retry-After`, naming no limit and no address; counted in `orch_rate_limited_total{limit}`; logged with the class only. `limit` is listed before `guard:` on the reveal routes so a caller who may not reveal is counted too (macro transforms run in option order).
  - `apps/api/src/hardening.ts` + `http.ts`: security headers on every response (CSP `default-src 'none'; frame-ancestors 'none'`, `nosniff`, `no-referrer`, `X-Frame-Options`, HSTS only when the sign-in redirect is https), CORS off unless `ORCH_CORS_ORIGINS` lists exact origins (preflight answered only for a listed origin with `Access-Control-Request-Method`; `Vary: Origin`; credentials only for a listed origin), a declared-`Content-Length` cap (`ORCH_MAX_BODY_BYTES`, default 2 MiB, 1..64 MiB) answered `413 payload_too_large`, and `maxRequestBodySize` on the Bun server (same number).
  - Client address: the peer, or with `ORCH_TRUSTED_PROXY_HOPS=n` the n-th entry from the right of `X-Forwarded-For` (ports and `[v6]` brackets stripped, validated with `isIP`), else the peer. A header that cannot be used (hops 0 but the header is sent; the entry is not an address) is logged once per process, with no address in it. `ORCH_RATE_LIMIT_SCALE` (0.1..100) multiplies every limit.
  - `apps/web/src/server.ts`: the dev proxy appends the caller's address to `X-Forwarded-For` (and drops the header when the peer is unknown).
  - `.gitlab-ci.yml`: an `audit` job (`bun audit`, ignoring the one dev-only esbuild advisory GHSA-67mh-4wv8-2f99 by id). `.env.example`: four commented entries. `docs/openapi.json` regenerated (+`x-rate-limit`).
- **Tests:** `rate-limit.test.ts` (windows, scale, refusal callback, eviction and sweep, route option errors, client address rules incl. ports/brackets and the one-time warnings), `hardening.test.ts` (headers, CORS cases, env bounds, body cap incl. any-length digit strings), `limits.test.ts` (route level against real Postgres: each class, a token sharing its owner's count, guard order, dev principal, the logged warning), 5 real-server tests in `main.test.ts` (headers, CORS, 413, bad settings), a structural list in `authz.test.ts` (every route's limit class), the XFF test in `apps/web/src/server.test.ts`.
- **Mutation checks:** 61 mutants over the limiter, header/CORS logic, `http.ts`, `app.ts` wiring, every route's `limit:` line, `index.ts` and the web proxy: 59 killed at first; 2 survivors (ended windows not swept, preflight for any method) got stronger tests and are killed. After the code-review fixes: 16 more (hop arithmetic, `isIP` check, port and bracket handling, both warnings, warn-once, the `app.ts` wiring, length digits) all killed. Not covered: the `else headers.delete("x-forwarded-for")` branch of the web proxy (it needs a unix-socket peer; no test).
- `/code-review` (medium): 10 findings. Fixed: the forwarded-for header with hops 0, or an unusable entry, is now logged once instead of silently pooling all clients; `ip:port` and `[v6]:port` entries are read; a `Content-Length` of any number of digits is judged (it was skipped past 15); the unknown-peer web proxy no longer passes a forged header; entries are validated with `isIP` (the old character class accepted `1.2.3.4:99999999`). Kept as REVIEW items: 3, 7, 8, 9, 10. One finding (a second `vary` writer) was invalid.
- Inline security review: refusals and warnings carry no address, class or secret (asserted); a forged forwarded-for entry at the start of the chain does not choose a bucket; CORS matches whole origins only and sends credentials only to a listed one; the CSP/headers also cover problem and 404 responses; the limiter keys are `class|who`, so one class's count never spends another's.
- **Dependency change:** `yaml` 2.8.1 -> 2.8.3 in `packages/iac` and `packages/pipelines` (`bun.lock`), a security patch so that `bun audit` is clean apart from the ignored dev-only advisory. No new dependency.
- **Disclosed test edits (nothing weakened):** `cli-login.test.ts` and `tokens.test.ts` build their app with `hardening: { rateLimitScale: 100 }` because one app instance there makes more sign-in/token calls than the real limits allow (23 tests failed without it); `authz.test.ts` gains a structural test and `LIMITS` import (no existing expectation changed); `packages/db/src/metrics.test.ts` (OPS-3): the lower edge of the age bands gets one second of slack, because the rows are stamped by the host clock and read by the Docker VM's clock (a 239.999994 s reading failed once).
- **REVIEW (design gates and facts I could not verify):**
  1. **In-memory, per replica:** a restart forgets; at `maxKeys` (10 000) the oldest counter is dropped, so a flood from many addresses can reset others' buckets, including over-limit ones. Move to Postgres before running several replicas.
  2. IPv6 clients are counted per address, not per /64.
  3. **The proxy count must be true.** Unset behind a proxy: all clients share one bucket (now logged once). Set too high: a caller picks their own bucket by forging the header.
  4. **The numbers are guesses:** `ci_exchange`/`webhook` 600/min/IP, `login` 30 per 5 min shared by the browser and CLI sign-in routes (an office behind one NAT may need `ORCH_RATE_LIMIT_SCALE`), `reveal` 60/min shared by single reveals and environment exports.
  5. No global per-IP safety net: floods of invalid credentials still cost a lookup. Put a proxy limit in front.
  6. The SPA HTML served by `startWeb` has no CSP or security headers (OPS-2 decides how production serves it); the API's CSP is `default-src 'none'`.
  7. CORS is off by default; credentialed CORS only works same-site (the cookie is `SameSite=Lax`); there is no Origin-header CSRF check beyond JSON-only plus SameSite; the preflight allow-lists for headers/methods are fixed (a browser fails closed on anything else).
  8. Bun's `maxRequestBodySize` (equal to the cap) answers first on the real server with a plain-text 413 for all oversized bodies; the problem+json 413 appears only where the declared-length check is reached. With `createApp` alone, chunked bodies have no cap.
  9. The body cap defaults to 2 MiB and cannot go below 1 MiB (a plan summary and a webhook may be that large).
  10. The dev principal is exempt from every limit.
  11. `GET /metrics` is not rate limited (its token is the only protection).
  12. The `yaml` pin bump above; the remaining esbuild advisory (dev-only, drizzle-kit) is ignored in CI by its GHSA id and will need revisiting.
  13. **The `audit` CI job is unproven on a real pipeline** (FND-6 `[!]`) and "CI fails on a seeded vulnerable dependency" is not demonstrated: only the local exit codes were checked (`bun audit` exits 1 on a finding, 0 once the ignored advisory is excluded). The job also turns every pipeline red on any new advisory or when the advisory database is unreachable. To close: seed a vulnerable version on a throwaway branch in a real pipeline.
  14. The unknown-peer branch of the web proxy has no test.
- Gate: `bun run check` green: 4085 pass + 2 skip + 0 fail (root), 241 pass (web). New dependencies: none.
