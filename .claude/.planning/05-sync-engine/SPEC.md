# 05 Sync Engine - Spec
Prefix: SYNC · Milestone: M1 · Status: building

## Goal
Safely push the resolved variables for an environment to external targets with Terraform-style plan/apply, and detect when targets drift.

## Scope
Adapter contract + conformance suite; diff/plan engine; GitLab CI variables adapter; target config API; plan/apply jobs; auto-sync on change; drift detection.

## Non-goals
Other targets (EXT), approvals on protected environments (GOV-4), rotation.

## Design
- Contract (`packages/sync`, SYNC-1): `SyncAdapter<Config> { type; capabilities { canReadValues, supportsMasking, supportsScopes, supportsFiles }; check(item): void; validate(config): Config; connect(config): Remote }`, `Remote { read(): RemoteItem[]; create(item); update(item); delete(ref) }`. An item is `{ key, scope, value, secret, file }` (`value` is `null` when the target hides it; scope `*` when it has none). Errors are `SyncError` with a kind (`not_found`, `exists`, `invalid`, `unsupported`, `unmaskable`, ...) and never carry a value. `check(item)` throws what a write of the item would throw because the target can never hold it (`invalid`, `unsupported`, `unmaskable`) without touching the target: whoever builds a plan calls it for every wanted item before `plan()`, so an unmaskable secret fails the plan, not the apply. Every adapter must pass `runAdapterConformance`.
- Plan (`plan(desired, actual, { unmanaged, lastApplied })`, SYNC-2) = list of `{ key, scope, action: create|update|delete|noop|adopt, changed: ["value"|"secret"] }` ordered by key then scope. **Plans never contain values.** Value comparison happens in memory; when a target hides a value (hidden variables) compare against the stored last-applied HMAC, and update when there is none.
- Unmanaged remote items (nothing wanted in that key and scope): policy `ignore` (default, left out of the plan) | `adopt` (listed as `adopt` so they can be imported; the target is not changed) | `prune` (listed as `delete`). `prune` is explicit per target and a human gate in UI/CLI.
- GitLab mapping: variables with no environment override -> `*` scope; environment-specific overrides -> that environment's `environment_scope` (GitLab falls back to `*`). A value that cannot satisfy GitLab's masking rules while marked secret **fails the plan** with a clear error - it is never silently unmasked.
- Targets (SYNC-4): `sync_targets(project_id, name, type, connection_id, config, environment_mapping, unmanaged_policy, auto_sync)`, name unique per project; `/organizations/:orgId/projects/:projectId/sync-targets` (list, get, create, patch, delete; audited as `sync_target.*`). `config` is validated by the type (`TARGET_TYPES` in `packages/sync`, no client needed), stored as parsed, and holds no credential (that is the connection's); the connection must be in the organization and of the kind the type needs (`gitlab` for `gitlab-variables`); `environment_mapping` maps environment slugs of the project to the target's scope (not `*`, no two the same, at most 100). `type` never changes. Reading needs `sync.target.read` (project reporter); create, update, delete need an org admin (`sync.target.*`, REVIEW: a target aims the connection's token at something). A connection with targets cannot be deleted (409 `connection_in_use`); a project's targets go with it.
- Plan endpoint (SYNC-5): `POST .../sync-targets/:id/plan` (project maintainer) stores a run and its lines (keys, scopes, actions; expires in 15 minutes) and `GET .../runs/:runId` returns it. Desired state = the project's resolved variables at `*` plus, per mapped environment, only the overrides at its scope; keys that do not resolve and mapped environments that are gone are listed under `skipped` and their refs are never pruned. Each run stores a digest of the variable ids/versions and the target's settings, which apply compares.
- Apply endpoint (SYNC-6): `POST .../sync-targets/:id/apply {planId}` (project maintainer) applies a stored plan id only, answers 202 and hands the run to the `sync.apply` job. Refused with 409 when the plan was applied already (`plan_not_applicable`), has expired (`plan_expired`), is stale (`plan_stale`: the variables or the target's settings changed, so plan again) or another apply is running on the target (`apply_in_progress`, the per-target mutex: a partial unique index). The job writes creates, then updates, then deletes, records `applied`/`failed` per line, retries a target that does not answer through the queue, and ends the run `applied` or `failed`. A run that cannot finish (dead job, or no worker for an hour) is ended by the next apply on that target. The worker needs `ORCH_MASTER_KEYS` of its own.
- Auto-sync (SYNC-7): a variable create, new value, delete or rename (organization, project or environment level, through the repo functions every route, import, restore and bulk edit uses) queues a `sync.auto` job for each target with `auto_sync` that the variable reaches (an organization's variable: all the organization's targets; a project's or environment's: the project's), in the change's own transaction. The job carries ids only and is held back 30 s (`AUTO_SYNC_DELAY_MS`) from the first change; while one waits, further changes add nothing (`jobs.dedupe_key` = target id, a partial unique index on queued jobs, cleared when the job is taken), so a burst of changes makes one job and one run. The job plans the target as if its policy were `ignore` (so it never deletes: removing is a person's call) and, if the plan creates or updates anything, applies it as the job (same audit rows, actor `job`, plan marked `auto`). A target that is applying is queued again; a plan the target or the variables refuse (a 4xx: a value the target cannot hold) is logged and not retried; anything else (the target does not answer, a secret cannot be opened) fails the job for the queue to retry. Protected environments (GOV-3) will have to be skipped: the flag does not exist yet.
- Partial failure: record per-item results, retry with backoff, re-apply is idempotent. Status shows last successful sync.

## Acceptance
Plan shows the exact create/update/delete set against a project's GitLab variables (mock), apply converges it, a second plan is empty, a manual change in GitLab shows up as drift, and no value appears in plans, runs, logs or audit.

## Risks / human gates
First apply to a real GitLab project; any `prune` semantics change.
