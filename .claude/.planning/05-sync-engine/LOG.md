# 05 Sync Engine - Log

## 2026-10-17 SYNC-1
- New package `packages/sync` (`@orch/sync`, no dependencies, D10 layout): `SyncAdapter<Config> { type; capabilities; validate(config); connect(config): Remote }` and `Remote { read(); create(item); update(item); delete(ref) }`. An item is `{ key, scope, value, secret }`; `value` is `null` when the target hides it (`canReadValues: false`), scope `*` (`ALL_SCOPES`) when the target has none. `read` is ordered by key, then scope, by code unit. `SyncError` kinds: `invalid_config`, `invalid`, `unsupported`, `not_found`, `exists`, `unmaskable`, `failed`; a message may name key and scope, never a value, a credential or the config. A call that can never work (`invalid`, `unsupported`, `unmaskable`) fails as that before existence is asked, so `not_found`/`exists` always mean the item. ## 2026-10-17 SYNC-2
- `packages/sync/src/plan.ts`: pure `plan(desired: ItemInput[], actual: RemoteItem[], { unmanaged = "ignore", lastApplied?, capabilities? }): PlanItem[]`. A `PlanItem` is `{ key, scope, action: create|update|delete|noop|adopt, changed: ("value"|"secret")[] }`, ordered by key then scope (UTF-16 code unit, whatever order the inputs came in). Values are compared in memory and never leave it: the type has no value field, nor a fingerprint.
- Wanted items: absent from the target -> `create`; value or secret flag differs -> `update` (`changed` names what); same -> `noop`. Values compare exactly (case, spaces, lines, empty). Unmanaged items (the target has them, nothing wanted in that key and scope): `ignore` leaves them out, `adopt` lists them as `adopt` and changes nothing, `prune` lists `delete`. What is said of a wanted item never depends on the policy. Scopes are separate items: wanting `X@prod` keeps nothing of `X@*` under `prune`.
- Hidden values (`value: null` on the item): compared with `lastApplied.get(ref)` against `lastApplied.fingerprint(want.value)` (the caller supplies the HMAC, so the package keeps no dependency and no key); no record or no `lastApplied` at all -> `update value`, as the value cannot be known to be right. A readable value is always compared as it is, a record never hides drift. The record is asked about `{ key, scope }`, never given the value.
- With `capabilities`, a wanted secret for a target that cannot mask, or a scope other than `*` for one without scopes, fails the plan as `SyncError("unsupported")` (names key and scope, no value) instead of an `update` that never settles; without them nothing is checked. Duplicates fail loudly: an item wanted twice is `invalid`, one the target lists twice is `failed`.
- SPEC deviation: the "Design" lines for the plan and the unmanaged policy now say `adopt` is an action (report only: the SPEC's four actions had no way to show an adopted item) and `plan`'s options. Tasks unchanged. `ref.ts` holds the shared `refId`/`byKeyThenScope` (the fake uses them too); only `byKeyThenScope` is exported, for adapters that have to order a read.
- Tests: 321 in `plan.test.ts` (21 table tests on each action, each policy, hidden values, exact comparison, order incl. surrogate pairs and locale-vs-code-unit, duplicates, capabilities, key/scope collisions, canary leak and the plan type's own field list, plus a seeded property test over 300 random targets: same plan in any input order, one sorted line per item, the right items per policy, policy never changes a wanted item, only prune deletes, no value in the output, and applying the plan converges).
- Mutations: 48 checked on `plan.ts` and `ref.ts` (each action and branch, policy defaults and policy per action, sort, hidden-value comparison incl. no-record, record asked with the value or at `*`, exact comparison, error kinds and messages with values, `changed` order, item fields, id collisions, comparator, capability checks). 1 survived at first (scope compared by locale: no test had two scopes where locale and code unit order disagree): now tested; none left.
- `/code-review` (medium) found 7. **Fixed:** secret/scope the target cannot hold now fails the plan (option `capabilities`); the hidden-drift limit has a `shortcut:` comment; only the comparator is exported; flat comparator; `adopt` documented as report-only. **Dismissed:** no record means `update` on every plan until an apply records one - by design, SYNC-6 stores the fingerprint after an apply so it settles; a duplicate in the target's read fails the plan even when unmanaged - the contract allows one item per key and scope, so a duplicate is a broken read and guessing which is right is worse (the conformance suite holds adapters to it).
- Inline security review: no I/O, no secret handling beyond comparing values already in memory; no value, fingerprint or credential in a plan or an error (canary tests on both); `prune` only on an exact key and scope that nothing wants and only when asked for.
- **Limits / follow-ups:** a hidden value edited by hand on the target cannot be seen (only what was last applied is known), so it shows as `noop` until a value changes; `changed: ["value"]` cannot say "differs" from "could not be checked"; a plan does not know the target's own value rules (GitLab masking format): SYNC-3/SYNC-5 must fail the plan for those (`unmaskable`); apply order (e.g. deletes before creates) is SYNC-6's; plans of thousands of items are not benchmarked (O(n log n), maps and one sort).
- Gate: `bun run check` green, 1407 pass + 1 skip. New dependency: none.

## 2026-10-17 SYNC-3
- `packages/sync/src/gitlab-variables.ts`: `gitlabVariablesAdapter(gitlab: Pick<Gitlab, "variables">)`, type `gitlab-variables`, all four capabilities true. Config (zod, strict): `{ project: id|path, protected? }` or `{ group: id|path, protected? }`; anything else, a `token` included, is `invalid_config` with one fixed message and no echo. `check`: key must be 1-255 letters/digits/`_` (`invalid`), scope not empty (`invalid`), value at most 10,000 characters (`invalid`), a secret GitLab cannot mask (`canMask(value, { raw: true })`: 8+ characters, one line, no spaces) is `unmaskable` and is never written plain; `create`/`update` run it first, `delete` checks the key and scope.
- Writes: `{ value, type: file ? "file" : "env_var", masked: secret, raw: true, protected: config.protected, scope }`. Raw because the platform has already resolved references; masked, never hidden, so the value stays readable and drift shows; `description` is never sent, so one set by hand stays; `protected` is sent only when the config says so, so an update keeps what is there. `read` lists every variable of every scope (paginated by the client), a hidden one as `value: null`, sorted by key then scope. Exact scope: the client's own pre-check keeps GitLab's fall-back to a same-named variable of another scope from being written or deleted; an absent scope is `not_found` and nothing changes (tested with `A@*` present).
- Errors: GitLab answers a taken key as a plain refused body, so a refused create asks for the variable: there -> `exists`, absent -> `invalid`, cannot tell -> `failed`. Every other failure is `failed` with fixed words ("<key> (<scope>): GitLab answered <kind>", "reading the variables: ...", "the request could not be made"); GitLab's text, URLs and tokens never pass, tested with a client that returns them and with an error carrying a canary value.
- Contract change (done here because the adapter is the first thing that needs it): `Capabilities.supportsFiles`, `file` on `ItemInput`/`RemoteItem` (plan `changed` can now say `file`), and `SyncAdapter.check(item)`. This replaces the `capabilities` option SYNC-2 put on `plan()`: a plan does not know a target's value rules, an adapter does, so `plan()` lost the option (and its tests, which `check` covers in the conformance suite) and **SYNC-5 must call `adapter.check` for every wanted item before `plan()`**. The conformance suite has two more tests (a file is kept and can be made plain, a target without files refuses one; `check` says what a write would say, and what it accepts can be written) and an option `refused` for what a kind of target refuses beyond its capabilities. Fake variants: everything, hidden values, no scopes, no masking, no files, bare. `packages/gitlab` exports `isVariableKey`; `packages/sync` depends on `@orch/gitlab` and `zod` (both already in the workspace; no new package).
- Tests: `gitlab-variables.test.ts` (63 with the conformance runs against a project and a group on the mock): config accepted/refused, what is written (masked, raw, never hidden, file, scope, description kept, protected), what is read (all scopes, hidden null, order, pagination at 2 per page), scope isolation, unmaskable secrets (check/create/update, nothing written, no value in the message, symbols allowed), the 10,000 limit, injected 401/403/404/429/500, a misbehaving client, plan -> apply -> second plan empty with prune.
- Mutations: 44 checked (adapter checks and limits, config strictness, every written field, every read field, order, hidden values, create/update/delete error mapping, message content, owner choice, the fake's new `check`/`file` code, the plan's file comparison). 1 survived at first (masking as if references were expanded: no test had a secret with `$` or punctuation): now tested; none left.
- `/code-review` (medium) found 6. **Fixed:** `check`'s doc said "a plan calls it" (it does not; the caller does) and is now explicit; a failed read was named like an item (`"variables" (*)`), now "reading the variables". **Recorded as limits:** `raw`, `protected` and `hidden` of an existing variable are not read, so drift in them is not seen (a variable with `raw=false` and the right text is `noop` and still expands `$`); the extra GET after a refused create can fail or race; a Free-tier group's ignored scope is only found out after the write. **Dismissed:** a bad key is echoed (cut to 64) in the message - keys are not secret, they are in plans and audit; `check` runs again in `create`/`update` - the contract says a write fails like `check`, and it is a few comparisons.
- Inline security review: no credential in the adapter or its config (the client belongs to the connection; `validate` refuses `token`, `baseUrl` and any other key); a secret is written masked or refused, never plain, never hidden; no value, GitLab text, URL or token in an error (tested); only `@orch/gitlab` is used (invariant 2); `protected` is opt-in, so by default a secret is available to pipelines on every branch.
- **Limits / follow-ups:** a Free-tier group ignores `environment_scope`: the create is reported `failed` (the client notices) but the variable exists at `*`; a wrong project/group makes update/delete `not_found` (ambiguous with an absent item, the engine reads first); empty values and trailing newlines are unverified on a real GitLab; `protected` drift undetected; hidden variables are never created (GitLab cannot show them, drift cannot be seen); a masked secret is readable by GitLab maintainers; the 10,000 limit counts UTF-16 units; a `failed` after a POST timeout is an unknown outcome (re-read); mock fidelity against a real instance is unverified (GL-5 real run never executed); GitLab's rule that a masked value must not equal another variable's name is not checked here (GitLab refuses: `invalid`).

## 2026-10-17 SYNC-5
- **REVIEW (authz model):** new actions `sync.plan` (project maintainer) and `sync.run.read` (project reporter). Reason: planning opens every secret of the project and the connection token and compares them with the target, which is an equality oracle (`changed: ["value"]` says whether a guess is right), so it takes the people who may reveal secrets; a stored plan holds keys, scopes and actions only, so a reporter may read it. Tables in `core/authz.test.ts`, `api/authz.test.ts` (guard map, 401 count 73) updated; `docs/openapi.json` regenerated.
- **REVIEW (delete semantics):** `sync_targets` -> `sync_runs` -> `sync_run_items` all CASCADE: a plan's history goes with its target (and so with its project). Composite FK `sync_runs_target_fk (target_id, organization_id, project_id)` keeps a run in its target's org and project (needs the new unique `sync_targets_id_scope_key`, additive).
- **REVIEW (migration 0014, additive):** `sync_runs` (status `planned|applying|applied|failed`, `expires_at`, `desired_digest`, `counts`, `skipped`), `sync_run_items` (PK `(run_id, position)`, action check incl. `adopt`, timestamps because an apply records a result per line in SYNC-6), unique on `sync_targets`, `updated_at` triggers. drizzle-kit put the unique after the FK that needs it: hand-reordered.
- `apps/api/src/sync-plan.ts` `desiredState(db, keys, target)`: the project chain (org + project levels) resolved with `resolveVariables` goes to `*` (`secret` = kind secret, `file` = kind file); for each mapped environment (sorted) only its overrides go to the mapped scope: a key the base lacks, or whose value or kind differs. A mapped slug with no environment is nothing to sync: reported in `skipped.missingEnvironments` and its scope on the target is left out of the plan (never pruned). A key that does not resolve is in `skipped.unresolved` with a code, is not wanted where it fails, and is left out of the target's list too, so a broken reference never reads as `delete`/`adopt`. A base issue is not reported when some mapped environment resolves the key. `digest` = sha256 of type, connection, config, mapping, policy and `[id, key, kind, version]` per variable of each chain: no value goes in, and it is not exposed in the API.
- `apps/api/src/routes/sync-runs.ts`: `POST .../sync-targets/:targetId/plan` (201, audit `sync_run.plan` with target, name and counts) and `GET .../runs/:runId` (all lines, unpaginated). Order: master keys (503) -> target (404) -> connection opened and config validated (so a target that cannot be planned never opens a secret) -> `desiredState` in one read-only REPEATABLE READ transaction (variables, lines and digest are of one moment) -> `adapter.check` of every wanted item (all refusals in one 422 `plan_invalid` naming up to 10 and counting the rest; an unmaskable secret, a value over GitLab's 10,000, a bad key) -> read the target without the untouchable refs -> `plan()` with the target's unmanaged policy -> run, lines and audit row in one transaction, expiry now + 15 min. A target that cannot be read is 502 `target_failed` (fixed words); a stored config the type refuses is 422.
- `packages/db`: `sync-runs.ts` (create with lines inserted in chunks of 1000 because a statement binds at most 65,535 values, get by org + project + target + id, list lines in plan order). `openChain` now also returns each variable's `version` (for the digest).
