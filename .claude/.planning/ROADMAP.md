# Stacktide - Roadmap

A control plane to **set up CI/CD for GitLab projects in minutes, manage variables/secrets in one place, and sync them where they need to go** - later extended to IaC stack orchestration. Inspiration and what we borrow: [REFERENCES.md](REFERENCES.md). How we build: `.claude/skills/software-factory/SKILL.md`.

## Architecture in one breath
Bun + TS monorepo. API + worker (same codebase, two entrypoints) over Postgres. **GitLab is the runner**: the platform generates pipeline config, opens MRs, triggers pipelines, receives webhooks, stores desired state (variables, stacks) and records runs. Secrets are envelope-encrypted at rest. Humans sign in with GitLab; CI jobs authenticate with GitLab OIDC `id_tokens`. Clients: CLI (`orch`) and web UI share one typed API client.

| D2 | Runtime | Bun, TypeScript strict | Given |

| D10 | Layout | `apps/{api,cli,web}`, `packages/{core,db,crypto,gitlab,sync,pipelines,iac}`; create packages lazily | |
| D11 | UI | React via Bun HTML imports, no Next.js | Revisit in UI-1 |
| D12 | Lint/format | Biome | |
| D13 | DNS | DNS is applied runner-side with DNSControl (`tool: dnscontrol` stack); the platform holds no DNS credential and makes no DNS call; zone claims are a guard, the token scope is the boundary; deletes need `dns.prune: true`. | D14 | Deployments | Deployments are recorded as GitLab reports them (hook and refresh, ordered by `observed_at`, no user or commit text kept); GitLab's environment name equals the platform slug; the deploy step is the repository's own script; a promotion or rollback is a pipeline the platform starts on the default branch with three variables; the platform's guard is the gate; protected environments wait for change-request approvals. **ADR-0020, proposed 2026-10-21, not yet accepted** | Alt: read GitLab each view; retry GitLab's old deploy job; shipped Helm/SSH templates; an explicit mapping column |
| D15 | Variable folders | A variable's identity is `(level owner, folder, key)`; a folder is a project-level namespace shared by every environment (a row, soft delete, empty-only delete); `${KEY}` reads the holder's folder and `${/path/KEY}` an absolute address, with no fallback to the root; a sync target, `orch run` and an export read exactly one folder; folders inherit the project's roles; organization-level variables stay at the root. **ADR-0021, proposed 2026-10-21, not yet accepted** | Alt: a path prefix in the key; one tree per environment; recursive reads with flattened names; per-folder roles |
| D16 | More than one forge | A `packages/forge` seam with capability flags: a GitLab adapter over `@orch/gitlab` (unchanged) and a GitHub.com adapter; D1, D6, D8, D9 and invariant 2 are reworded for GitHub (not edited until accepted); a project belongs to one connection; a CI token is verified against its connection's issuer; **no generated pipeline on GitHub** (a static workflow reads its plan as data); **the platform observes GitHub approvals and never makes them**; the first cut refuses DNS, cost gates, scanning from artifacts, deployments, rotation and pools on GitHub. **ADR-0019, proposed 2026-10-22, not yet accepted** (the SPEC called it D14; D14 and D15 were taken first) | Alt: a GitHub-only fork; a webhook-only integration; GitHub through GitLab mirroring; the platform approving as the connection's user; a GitHub App from the start |
| D19 | Resource blueprints | A resource is a managed cloud service described by a blueprint `(kind, cloud)` (`network`, `service`, `postgres`, `bucket` on `gcp` and `aws`); shipped Terraform, vendored once per repository, with a closed input schema as the only way a value reaches HCL; creation is a merge or pull request through the forge seam, never a cloud call; state is `gitlab`/`orch` with `backend "http" {}`; wiring by deterministic secret names; safe defaults; public outputs are an allowlist; D1 and invariant 3 unchanged. **ADR-0024, proposed 2026-10-23, not yet accepted** (D17 and D18 are reserved for ADR-0022 and ADR-0023) | Alt: modules by Git URL; the platform calls the clouds; install Coolify or Dokploy beside it; wiring by remote state |

### Milestones
- **M0 Foundation** - green empty monorepo, ADRs confirmed.
- **M1 Variables to GitLab (API only)** - connect GitLab, import projects, manage variables per environment, plan/apply sync to GitLab CI variables. First real value.
- **M2 Pipelines, CLI, UI** - one-click pipeline setup via MR, `orch pull|run|push`, dashboard. The "super easy" milestone. Containerise (OPS-1, OPS-2) here.
- **M3 IaC** - stacks, change detection, plan on MR, apply on merge/command.
- **M4 Governance** - approvals, audit export, drift, policy, hardening.
- **M5 Expansion** - AWS SSM / Secrets Manager / Kubernetes / Vault targets.

## Suggested order for features 33-37
**35 -> 36 -> 34 -> 37**, with 33 beside them. 35 (what you can create) comes first because 36, 34 (ODE-20) and 37 all use it. 36 follows because a created service needs a way to receive an app. 34 adds whole environments and destroy. 37 is last because it only reads what the others record, and its design (RSH-2, also 34's picker) can be made at any time and is the one thing worth doing early. 33 is independent and can run at any time.
