# 09 iac-stacks-and-runs - LOG

## 2026-10-17 IAC-1
- **New package `@orch/iac`** (`packages/iac`): `stack.ts` (the `stack.yml` schema and `parseManifest`), `scan.ts` (`scanStacks`, `backendOf`, the `RepoSource` port), `gitlab-source.ts` (`gitlabSource(gitlab, project, ref)`: the tree and file reads go through `packages/gitlab`, nothing else touches GitLab).
- **`stack.yml`:** a strict zod object, so a misspelt key (`depend_on`) is an error and not a stack with no dependencies. `name` (slug, 1-63), `tool` (`terraform|tofu|terragrunt`), optional `version` (`1.9.8` or `1.9.8-rc1`, no `v`, no range), `tags` (max 20), `depends_on` (names, max 50), `watch` (relative paths or globs, max 50, no `..`, no absolute path, no backslash, no control characters), `apply_on` (`merge|command`, default **`command`**: nothing is applied unless the file asks). YAML is parsed with aliases refused (a small file must not expand into a large one) and a 64 KiB limit; a refusal names the key and the rule, never the value.
- **Scanner:** a stack is a directory holding a `stack.yml`; stacks may nest. Per-stack problems never hide the others: `invalid-manifest`, `unreadable`, `too-large`, `unsafe-path` (errors, the stack is left out), `duplicate-name` (neither claimant is returned), `missing-backend` and an unreadable `.tf` file (warnings, the stack stays), `too-many` (only the first 500 markers are read). `missing-backend` is the task's "reports stacks missing `backend "http" {}`", split into `none` (local state, which a CI job loses) and `other`. A Terragrunt stack's backend is generated by its own config, so it is `unchecked` and its files are not read. Output is sorted (stacks by path, problems by path, kind, message), so any file order gives one answer. The result also says `complete`: true only when no problem is an error.
- **The stack's directory ends up in shell commands and job names of generated pipelines**, so it is a closed character set (`A-Za-z0-9._@+=` and `-` inside a segment, no `.`/`..` segment) checked in the scanner **and** by a `CHECK` on `stacks.path`, so a writer other than the scanner cannot widen it. A refused directory is not read, and its message is fixed text (it does not carry the repository's characters back out).
- **Table `stacks`** (migration `0022_stacks.sql`, additive, with the `updated_at` trigger): one row per (project, name); the stack's manifest fields plus the scanned `path` and `backend`; composite FK to the project's organization, `ON DELETE CASCADE` (a project's stacks are read from its repository and go with it); CHECKs on name, path, tool, apply_on and backend. `syncStacks(db, org, project, stacks, {prune})` upserts by name in one transaction with the project row locked (two scans of a project take turns), keeps a stack's id, writes only a stack that changed (so `updated_at` means "last changed"), and **deletes a missing stack only with `prune: true`**: a scan that left a stack out because it failed to read is not the repository saying it is gone, so a caller prunes only when `complete`. Returns the names added and removed (for the audit event the route will write). `listStacks` is by directory.
- Tests: 75 in `packages/iac` (13 schema; 57 scanner and `backendOf`, incl. 19 unsafe directories, `complete`, the tf cap, the marker cap, bounded concurrency, order independence, comment markers inside strings; 5 against the mock GitLab incl. a paged tree) and 16 in `packages/db` (every field changing and changing back keeping the id, a repeated scan writing nothing, swapped directories, prune on and off, a bad row rolling everything back, two scans at once, other project and other organization untouched, every CHECK, FK and unique). 
- Mutations: 54 over the scanner, schema, db helper and migration (`run75`). Survivor: `S15` (errors of a dropped stack) was a dead clause, since a marker that produces a stack never carries an error: removed, and the rule is now one line. All others killed.
- `/code-review` (medium) found 10. **Fixed:** `replaceStacks` deleted a stack the scan could not read (now `syncStacks` with an explicit `prune`, and the scan reports `complete`); the `set: s` upsert dropped `undefined` keys (one statement now, explicit `excluded.*`, a required `NewStack`); `backendOf` stripped comments before reading strings, so an ARN glob such as `"bucket/*"` could swallow a real backend (one left-to-right pass that consumes strings and comments whole); a comparator that never returned 0; the quadratic `.tf` grouping; warnings of a dropped duplicate stayed (one rule now); `stacks.path` had no CHECK. **Rejected:** unknown, self and cyclic `depends_on` (IAC-2 builds the graph and owns cycle detection with a readable path; the table stores what the file says); bare `Error`s from `syncStacks` (both are caller bugs, not user conditions: the route finds the project first and the scanner never yields a duplicate); `.tf.json`, heredocs and the 50-file cap (recorded as a `shortcut:` comment).
- Inline security review: the repository is untrusted input. Every field that reaches a job name, shell command or image tag is a closed set or a restricted path (schema, scanner and database); aliases and size are bounded; errors and problems carry keys and fixed text only (a test plants a token-shaped value and a failing read whose error names one, and neither appears). The `path` of a problem is the repository's own path: a UI or MR comment that shows it must escape it (IAC-7). No credential is handled; the scan reads the default branch through the platform's GitLab client with the organization's own connection.
- **REVIEW (design gates, not decided by me):** (1) `apply_on` defaults to `command`, so nothing applies on merge unless a stack asks; (2) `version` is optional (the platform's default tool version, from IAC-5, would fill it); (3) nested stacks are allowed; which stack owns a changed file is IAC-3's rule; (4) the `stacks` table mirrors the default branch, and a stack that left the repository is deleted on a complete scan (a delete semantics choice, opt-in per call); (5) a Terragrunt stack's backend is not checked; (6) stacks are scanned from the repository's tree only: no `stack.yml` is created for you (IAC-5 scaffolds one).
- **Limits (shortcuts):** the first 500 stack markers and the first 50 `.tf` files per stack; `.tf.json` is not read; a heredoc that looks like a backend block fools `backendOf`; a repository with any marker that fails to read is never pruned until it is fixed; the scan reads every `.tf` file whole (no size cap on those).
- Gate: `bun run check` green: 2479 pass + 1 skip (root), 239 pass (web). New dependencies: `yaml` 2.8.1 and `zod` 4.6.7 (already used by `@orch/pipelines`, same versions) in the new package; no other.

## 2026-10-17 IAC-2
- **`packages/iac/src/graph.ts`** (pure, no I/O): `buildGraph(nodes)` takes `{name, dependsOn}` (a `Stack` fits) and returns `{ok: true, graph}` or `{ok: false, errors}`. Errors, all reported together: `duplicate-name`, `unknown-dependency`, `self-dependency` and `cycle`. A cycle error carries the path as a closed list (`a -> b -> a`, each stack depends on the next); there is **one cycle per group of stacks that depend on each other in a circle**, the shortest through the group's smallest name, so a tangle of five stacks is one message and not five. Nothing is built from a graph with errors.
- **The graph:** `names`, `dependencies(name)`, `waves(subset?)` and `affected(changed)`. A wave is a set of stacks that may run together; every stack comes after everything it depends on, as early as that allows. `waves(subset)` keeps the order through stacks that are not in the subset (c depends on b depends on a: `waves(["a","c"])` is `[["a"],["c"]]`), which is what a change-only run needs. `affected` is the change plus everything that depends on it, directly or not. Results are sorted and fresh arrays (a caller cannot change the graph).
- Tests: 38 in `graph.test.ts`: tables for waves, subsets, affected, every error kind and the snapshot rule, then seeded properties over 300 random graphs each (replayable from the seed in the message): on random DAGs, waves partition the stacks, every dependency is in an earlier wave and a stack is exactly one past its latest dependency; subset waves equal an independent oracle built from a transitive closure; `affected` equals the closure oracle and is closed under itself; on random graphs with cycles, a graph is refused exactly when a cycle exists, each tangle is reported once, and every reported path is simple, closed and follows real dependencies; adding a dependency back along an existing path always yields a cycle through both. The generator is asserted to really produce cycles (more than 50 of 300).
- Mutations: 26 in `run76` (waves counting every stack, not carrying order through left-out stacks, shortest instead of longest chain, unsorted output, affected only direct or without the change, unknown names accepted, dependencies not deduped or sorted, each error kind off, every stack of a tangle reported or only half the group marked, cycle path open or reversed, errors not stopping the build, handing out internal arrays...). All killed. Two were equivalent and were not kept: the duplicate-name `continue` (an error is returned either way) and the re-expansion guard in `affected` (only costs time).
- `/code-review` (medium) found 7. **Fixed:** marking a cycle group walked the graph once per member (now one forward and one backward walk); the duplicate-name check scanned the error list (a Set); the doc claimed "everything" while a duplicated name's second stack is not looked at further (now says so). **Rejected:** `affected`/`waves`/`dependencies` throwing on an unknown name (deliberate: IAC-3 takes names from the graph itself, so an unknown one is a caller bug that should be loud, not a quiet empty answer); the 15 s test limit (below); completion doc per task (the factory writes one per feature).
- **Unrelated flake fixed in the web tests:** two tests in `projects.test.tsx` wait up to 5 s inside a test whose own limit is also 5 s, and failed in 2 of 3 full web runs while the machine's load average was about 10 (the note beside the first already says the organizations answer can take 1.5 s). Each now has a 15 s test limit; no assertion or wait was changed. A real hang still fails at the 5 s wait.
- **REVIEW (design gates, not decided by me):** (1) wave layering is longest-path (a stack waits for its deepest chain), not the smallest number of waves; (2) the scanner already drops duplicate names whole, so `duplicate-name` here guards other callers; (3) a dependency on a stack that failed to scan is an `unknown-dependency`, not a quiet gap: IAC-3/IAC-4 decide what to do with a graph that has errors (the safe default is to refuse to generate a pipeline).
- Gate: `bun run check` green: 2517 pass + 1 skip (root), 239 pass (web). No new dependencies.

## 2026-10-17 IAC-3
- **`changes.ts`** (pure): `changedStacks(stacks, files)` says which stacks a list of changed files touches directly; the caller adds dependents with `graph.affected` (IAC-2). **`detectChanges(gitlab, project, from, to, stacks)`** in `gitlab-source.ts` is the one GitLab call (`repository.compare`, through `packages/gitlab`): `from` is the target branch or its commit, `to` the merge request's head, and GitLab diffs from their common ancestor, so only what the merge request adds counts. `stacks` must be the scan of `to`, so a stack the MR adds is there; one it removes is not.
- **Rules:** a file belongs to the stack with the closest directory above it (nested stacks: the inner one only; a root stack `.` owns whatever no other stack owns); a `watch` pattern, taken relative to the repository root, touches a stack when any changed file matches it, and a pattern that names a directory covers every file under it (`modules/shared` is `modules/shared/**` too, but does not reach `modules/shared-old`). A renamed file counts at both ends, so moving a file from one stack to another touches both; an added or deleted file is its one path. Matching is `Bun.Glob` (native, no regex backtracking); each distinct pattern is tried once however many stacks share it.
- **Fail safe:** when GitLab says it gave up on the diff (`compare_timeout`), or the list is 1000 files long (a guess at where a diff listing is cut: **not checked against GitLab**), `detectChanges` returns every stack as changed and `incomplete: true`. A plan only reads, so too many is safe and too few is not. Errors from GitLab (an unknown ref) are thrown, never read as "nothing changed".
- **`watch` is stricter now (IAC-1's schema):** a pattern that could never match is refused when `stack.yml` is read, because a watch that fires on nothing fails silently: a leading `!` (exclusions are not supported), a leading `./`, a trailing `/` or an empty segment, an unclosed `[` or `{`, and an empty class (`[]`, `[!]`). Nothing in a repository uses the earlier, looser form yet.
- Tests: 44 in `changes.test.ts` (tables for directory ownership, renames, watch patterns, nesting and the root stack; order independence and untouched inputs; seeded properties over 300 random trees: each file touches exactly the closest stack by an independent oracle, more changes never touch fewer stacks, a rename equals its two ends), 8 more in `gitlab-source.test.ts` against the mock GitLab (edit, add, delete, a watched module, a branch with nothing new, a ref against itself, an unknown ref, and told renames, a diff GitLab gave up on and the 999/1000 boundary) and 3 in `stack.test.ts`.
- Mutations: 36 (`run77`, `run78`) over the matcher, the wrapper and the pattern check; one survived at first because the mock compares by branch name in both directions (compare reversed): now the call's argument order is pinned with a recording stub; another because an empty class after a closed one was untested (a case added). All killed. Two were equivalent and not kept (the watch memo, and skipping a watch for an already-touched stack: only cost).
- `/code-review` (medium) found 8. **Fixed:** the docs now say `stacks` is the scan of the head and paths are repository-relative without `./`; an empty class was accepted by the pattern check; the sort in `changes.ts` was a second hand-written comparator (the default string sort now, as in `detectChanges`). **Rejected:** the 1000-file figure being a guess (it is flagged as a `shortcut:` and a REVIEW item; the real answer needs a real GitLab); `ChangedFile` could drift from GitLab's type (the call in `detectChanges` is type-checked); the schema is stricter than before (nothing uses it yet); a root or parent stack not being touched by a nested stack's `stack.yml` (dependents come from the graph of the head, and ownership by the closest directory is the rule below).
- **REVIEW (design gates, not decided by me):** (1) nested stacks: a file belongs to the closest stack only, so a parent stack is not touched by a change under a child unless it lists the path in `watch` or depends on the child; (2) a directory-named `watch` entry covers everything under it; (3) an incomplete comparison plans everything; (4) a stack removed by the MR is not planned (no destroy is implied by deleting a directory); (5) the 1000-file cut-off is unverified; (6) `watch` is relative to the repository root, not to the stack.
- Gate: `bun run check` green: 2570 pass + 1 skip (root), 239 pass (web). No new dependencies (`Bun.Glob` is the runtime's).
