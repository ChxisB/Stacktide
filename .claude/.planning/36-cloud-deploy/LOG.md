- **Findings that change the tasks (edited into `TASKS.md`):**
  1. A GitHub `sub` has three forms (ref, environment, and the immutable form with ids for repositories created after 2026-07-15). CLD-3 and CLD-4 pin the numeric id claim as well as the `sub`, and build the `sub` in the form the repository uses.
  2. GitLab's `sub` does not carry the environment: a GitLab identity trusts project, ref and the numeric ids.
  3. A GCP provider for GitHub or GitLab SaaS without an attribute condition is open to every repository: the condition is mandatory, with a test.

  5. The ECR repository is `IMMUTABLE`: a re-run for the same commit must check the tag before it pushes. CLD-6.
  6. A Cloud Run service cannot pull from a forge registry (only through an Artifact Registry remote repository, which needs a stored credential): ADR-0025 decision 6 stands.
- Gate: no code. Not checked: anything on a real cloud or forge; the fetch summarises pages, so a quoted fact is the read's wording, not a copy.

## 2026-10-27 - CLD-5/6 scripts, CLD-7/8/9 templates and workflows
- **What was built.**
  - `packages/pipelines/scripts/deploy-cloud-run.sh` and `deploy-ecs.sh`: POSIX `sh`, `shellcheck` clean, one `eval` each (the required-names loop), a private `umask 077` work directory that is removed on exit, the gcloud, docker and AWS state kept inside it. ## 2026-10-27 - CLD-3/4 the `deploy-identity` blueprint kind, GCP and AWS
- **What was built.** A fifth blueprint kind, `deploy-identity`, in `BlueprintSchema` (`packages/core/src/blueprints.ts`) and two modules, `packages/iac/blueprints/{gcp,aws}/deploy-identity/` (pinned v1 in `BLUEPRINT_MODULES`). Also: the `argsOf` case in the renderer, migration **0069** (`resources_check` lists the new kind; a relaxing change, forward-only), `orch resource add deploy-identity` with seven flags (`--forge`, `--repository`, `--repository-id`, `--owner-id`, `--branch`, `--immutable-subject`, `--existing-oidc-provider`), four render fixtures (GCP and AWS, GitHub and GitLab), `docs/openapi.json` regenerated.
- **Decisions of mine, not in the SPEC** (change any of them):
  - **One identity per service.** `uses` must hold exactly one `service:<name>` of the same cloud, region and project; nothing may `uses` an identity. The module derives the service's names from that name, with the service module's own formulas, and a test fails if either side is renamed.
  - **Inputs:** `forge`, `repository`, numeric `repositoryId` and `ownerId` (required: the platform does not look them up, it holds no forge call for it here), `branch` (GitLab only, required there), `immutableSubject` (GitHub only), `existingOidcProvider` (AWS only).
  - **The subject is exact and built in the form the repository uses.** GitHub: `repo:<o>/<r>:environment:<env>` (our deploy job names its environment), or the id form with `immutableSubject`. GitLab: `project_path:<path>:ref_type:branch:ref:<branch>`. No pattern anywhere: tests refuse `*`, `StringLike`, `startsWith`, `||` and `matches(`.
  - **GCP:** the provider's attribute condition is the exact `sub` **and** the numeric ids (`repository_id` and `repository_owner_id`, or `project_id` and `namespace_id`). The audience is Google's default, so `allowed_audiences` is never set (it is what the `cloud-run` template asks for). **Four roles, each on one thing:** `workloadIdentityUser` on the service account (to one `principal://` subject), `run.developer` on the one service, `iam.serviceAccountUser` on its runtime account, `artifactregistry.writer` on its repository. A test refuses any project, folder or organization grant, `owner`, `editor`, `admin` and token-creator.
  - **AWS:** a role named `<env>-<name>-deploy`, one-hour sessions, `StringEquals` only on `aud` and `sub`, plus `project_id` and `namespace_id` on GitLab. Five policy statements. **No action has a star;** two statements name `*` as the resource because AWS gives those calls nothing narrower (the registry login and the two task definition calls). A test pins exactly that list. `iam:PassRole` is on the service's `-exec` and `-task` roles and only to `ecs-tasks.amazonaws.com`.
  - **`existingOidcProvider`:** an account has one OIDC provider per issuer. The first identity makes it, the others look it up. Destroying the first one removes it for the rest (README says so).
- **Spike correction.** The existing-tag check in `deploy-ecs.sh` uses `ecr:DescribeImages`; the spike's reading said `BatchGetImage`. The policy follows the script.
- **Limit I could not close.** AWS documents only `aud` and `sub` as condition keys for GitHub's provider, so on **GitHub the numeric ids are pinned only through the immutable `sub`**. A repository whose subject has no ids, deleted and recreated with the same name, matches. GitLab's provider on gitlab.com does take the ids. The README and the schema say so.
- **The first apply is a human step.** An identity cannot create itself. Both READMEs say who applies it and with which rights.
- **Gate.** Core 40 and the module tests (96) green; iac 731 pass; the CLI resource tests (31) and the API propose tests (a new GitHub and GitLab case) green. `ORCH_E2E_TERRAFORM=1` run filtered to deploy-identity: 6 pass, 0 fail (`fmt` and `validate` on both modules and the four rendered stacks; 72 s, with the provider download).
