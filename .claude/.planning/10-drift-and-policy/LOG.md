# 10 drift-and-policy - LOG

## 2026-10-18 POL-1
- **Marker:** `stack.yml` gets `drift_every` (`6h`, `1d`: whole hours or days, 1-999, regex `^[1-9]\d{0,2}[hd]$`), read into `Stack.driftEverySeconds`. No `drift_every`, no check.
- **Migration `0026_stack_drift.sql`** (additive; trigger appended by hand as for the other tables): table `stack_drift` (PK project + stack; `status` unknown/drifted/clean, `since` = start of the episode, `requested_at` = what the cadence counts from, `checked_at`, plan counts; CHECKs make `status` and its counts agree, and the composite FK keeps a row in its project's organization, cascading with the project); `runs.kind` (`plan` default, `drift`) with `runs_kind_check` and `runs_drift_check` (a drift run has no merge request).
- **Worker:** a schedule `stack.drift` (every `STACK_DRIFT_CHECK_SECONDS`, default 3600, 0 = off, minimum 60) queues one `stack.drift` job per linked project tagged terraform/terragrunt (`queueStackDriftChecks`, `enqueueOnce` by project so a backlog does not grow; ids only in the payload). The check job (`stackDriftCheckHandler`) finds a connection that reaches the project, scans the default branch head, takes the stacks with a cadence that are due (period up since asked, less 5 min, or never asked; the ones that waited longest first; at most 100), dry-runs the pipeline generator, marks them asked for and, in a savepoint, creates a run `kind=drift` on the default branch, audits `run.create` as the job and starts the same plan child pipeline as a merge request plan (`planRequest`/`triggerPlan` were pulled out of `mr-plan.ts` to share it). GitLab refusing the pipeline leaves no run and is tried again after a period; any other failure fails the job, rolls everything back and the queue retries. Checks of one project take turns (`FOR NO KEY UPDATE` on the project row).
- **Finding:** when the plan summary of a `drift` run is stored (the existing summary route and its binding to the recorded summary job), `recordStackDrift` sets drifted/clean. An episode is one `stack.drift` audit event at its start (`drifted`) and one at its end (`clean`), counts only, `resourceType: stack`, `resourceId` the stack name; repeated drifted plans change the counts. `since` stays the start of the episode. A report whose run was asked for before the latest taken one changes nothing (a late run cannot undo a newer finding). The route's audit now declares `run.summary` and `stack.drift`.
- **Never applied:** `applyRun` refuses a drift run (`409 drift_run`) before it reads anything of GitLab; the DB check already keeps a drift run from having a merge request, which every apply path needs. `POST /runs` cannot create one (`kind` is not in the body; a body that has it is 422). `kind` is in the run API (`docs/openapi.json` regenerated).
- Docs: "Drift" section in `docs/iac.md`; `STACK_DRIFT_CHECK_SECONDS` in `.env.example`.

- `/code-review` (medium) found 10. **Fixed:** the project lock was `FOR UPDATE` and held across the GitLab call, which would have blocked inserts of rows pointing at the project (now `NO KEY UPDATE`); a late older run could overwrite a newer finding, and the route used app-server time (now the run's `createdAt`, ignored when older); when more were due than a run holds, name order starved the later names if the cadence equals the tick (now longest-waiting first). **Rejected:** duplicated IAC tag list (there is one constant, `IAC_TAGS`); `|| 3600` on a disabled schedule (it is written disabled, and a handler-less queue is simply not claimed); queueing cost and the GitLab scan per tick (known shortcut, below). **Logged as REVIEW:** the rest (below).
- Inline security review: the job payload is ids; the repository is untrusted and goes through the scanner's closed sets (names, paths) and the cadence regex before it reaches a pipeline; the audit and `stack_drift` rows hold the stack name, a status and counts, never a resource address or a value (the summary route already receives resources and keeps them out of the audit trail: unchanged); recording a finding happens only after the existing binding of the caller to the recorded summary job, and a refused or late summary records nothing (tested); drift runs hold no cloud credentials in the control plane (the plan job is the IAC-11 one); `Refused` log lines carry at most 200 characters of GitLab's message; a drift run cannot be applied. No new route; route guard 94, OpenAPI operations 92 unchanged.
- **REVIEW (design gates, not decided by me):**
  1. The marker gains `drift_every` (whole hours/days).
  2. **The connection is chosen by trial** (the platform records no project-to-connection link): the first 20 `gitlab` connections of the organization, in id order, until one can fetch the project's default branch by its numeric id. **If two GitLab instances in one organization have a project with the same numeric id, a check can land on the wrong one** and plan the wrong repository. The upgrade is to record the connection at import.
  3. Every tick reads every linked project and, for each IaC project, scans its default branch over GitLab even when nothing is due (cache by head sha, or skip when no row is due and nothing changed, is the upgrade).
  4. The cadence is rounded to the tick, with 5 minutes of slack, counted from when a check was *asked for*; no guard against an earlier drift run still running (a long plan can overlap the next).
  5. Drift is a normal plan of the default branch, not `-refresh-only`: a plan that wants to change something because the code moved ahead of the apply is reported as drift too.
  6. The audit event `stack.drift` is the hook for POL-2 (episode start and end only).
  7. No route reads drift status yet (follow-up for the UI/API).
  8. A protected `environment` works only because the default branch is protected.
  9. The default branch's `.gitlab-ci.yml` must include the parent snippet; a project without it is retried once per period and only the worker log says so (nothing visible to the user).
  10. **The `stacks` table is not filled in production** (`syncStacks` has no caller outside tests), which is why drift scans the repository itself; `POST /runs` therefore always answers 422 `unknown_stack` for a real project (MR planning is unaffected). Also noted in the feature 09 completion doc.
  11. A stack that leaves the repository or loses its `drift_every`, or whose drift plans all fail, keeps its last status and `since` forever (no `resolved` event). Subscribers must treat an open episode as open until told otherwise; POL-2 decides whether to expire.
  12. The run records the sha of the head it scanned, but the pipeline runs on the branch: a commit between the two is planned and recorded under the older sha.
  13. An orphan GitLab pipeline is possible if the commit fails after GitLab started the pipeline (the same shortcut as IAC-8); the retry then starts a second plan.
  14. A pipeline GitLab refuses marks the stacks as asked for (retried once per period); a failure of any other kind retries at the queue's pace.
  15. The schedule is disabled when the merge request plan settings are missing (`ORCH_API_URL`, `ORCH_CI_AUDIENCE`, `ORCH_HELPER_IMAGE`).
  16. A project must be tagged terraform/terragrunt at import to be checked.
  17. Last report wins within the ordering above (the run's *request* time, not when it finished).
- Gate: `bun run check` green: 2980 pass + 1 skip (the opt-in real-GitLab run) + 0 fail (root), 239 pass (web). No new dependencies.

## 2026-10-18 POL-2
- **What:** organizations get notification sinks (`webhook`: any public https address, HMAC-signed; `slack`: a `hooks.slack.com/services/` incoming webhook), and a project says per sink which events it hears (`stack.drift` only, for now). When the plan-summary route finds the start or end of a drift episode it queues one `notify.deliver` job per subscribed sink in the same transaction as the `stack.drift` audit event (`notifyStackDrift`); the worker's `notifyDeliverHandler` opens the sink, checks the address again, signs and posts.
- **Migration `0027_notifications.sql`** (additive, trigger block by hand as for the other tables): `notification_sinks` (org RESTRICT, unique name per org, kind check, `host` readable, `secret_enc` + `dek_key_id` + `dek_wrapped` = the sealed address and a webhook's signing secret, as a connection's token is) and `notification_subscriptions` (PK sink + project + event, composite FKs to the sink and the project through the organization, both CASCADE).
- **API** (`routes/notifications.ts`): `GET|POST /organizations/:orgId/notification-sinks`, `DELETE .../:sinkId`; `GET /organizations/:orgId/projects/:projectId/notifications`, `PUT|DELETE .../:sinkId`. Audit actions `notification.sink.create|delete`, `notification.subscription.update|delete` (the address is never in one; metadata is kind, name, host / events). A webhook's `whsec_…` secret is in the create answer once, with `cache-control: no-store`. The answer schema is an allow-list: a field added to the handler's answer by mistake is dropped (mutation R2 survived for this reason).
- **Delivery** (`notify.ts`): `x-orch-signature: v1=hmac-sha256("<timestamp>.<body>")`, `x-orch-delivery` = job id (the same for every try), fresh `x-orch-timestamp`; Slack gets `{text}` with `& < >` escaped. Redirects are not followed, 10 s timeout, errors are fixed sentences (`sink answered 500`, `sink could not be reached`, `sink address is not allowed`, `sink is not readable`), so `last_error` and logs never hold the address or secret. 10 attempts, 1 s doubling (about 8.5 min), then `dead`. A sink deleted in the meantime resolves quietly.
- **SSRF:** https only, no credentials, no `localhost`/`.local`/`.internal`/dotless names, IP literals and everything the name resolves to must be public (IPv4 private/loopback/link-local/shared/documentation/reserved/relay; IPv6 only inside 2000::/3 minus 6to4, 2001::/23, 2001:db8::/32, 3fff::/20). Checked when the sink is made and again at each delivery.
- Docs: "Notifications" under Drift in `docs/iac.md` (kinds, headers, payload, receiver verification snippet, retry schedule, ordering caveat). `docs/openapi.json` regenerated (6 operations). No new settings.
- Tests: 17 in `packages/db/src/notifications.test.ts` (sealing, bindings tested one at a time, org isolation, paging, cascades, fan-out, rollback, concurrent set), 133 in `apps/api/src/notify.test.ts` (URL and address tables, signature against an independent HMAC, retry/backoff/dead through the real worker, leaks across job row, body, headers, logs, errors, SSRF cases, tampered stored addresses), 17 route tests (`notifications.test.ts`), 3 drift integration tests in `plan-summary.test.ts`; route/operation counts (100 / 98), audit registry and the worker queue list updated (the expected list gained `notify.deliver`: an addition, not a loosening).
- Mutations: 66 over signature, timestamp, delivery id, redirects, resolved-address and literal checks, the delivery-time URL recheck, timeout, status handling, error scrubbing, Slack escaping, the IP ranges, https/credentials/Slack host/internal names, secret size, gone sinks, unsigned webhooks, audit and answer contents, guards (route and rule level), strict bodies, org scoping, dedupe, delivery attempts, AAD and key-context bindings, the hook, the clock and the worker registration. Four survived at first and got tests (delivery-time recheck for non-literal addresses, unsigned webhook, each crypto binding alone); four are equivalent by design: the route's sink/project existence checks (the composite FKs answer the same 404 through `mapDbError`), the delete's second step (only differs in a race), and the answer containing the address (stripped by the response schema).
- `/code-review` (medium) found 6. **Fixed:** two concurrent PUTs for one sink could collide on the primary key (500): now delete-what-is-gone plus insert-on-conflict-do-nothing, with a concurrency test; `publicAddress` lacked 192.88.99.0/24, 2001::/23 and 3fff::/20 (added with cases); the secret answer lacked `cache-control: no-store` (added; found by my own review against the webhook-secret route). **Documented, not fixed:** DNS rebinding (below); deliveries are not ordered (a retried `drifted` can arrive after the `clean` that followed it: the webhook has `at`, Slack has no ordering; stated in the docs); Slack mrkdwn characters in names (`*`, `_`) can break the bold markers (cosmetic; `@here` is not live as only `& < >` markup is interpreted by incoming webhooks without `link_names`); no cap on sinks per org; `host` includes the port.
- Inline security review: no secret or address in a log, error, audit row, list, job payload or `last_error` (leak tests on each); the address is sealed with a per-sink key bound to org and sink id both ways; all five new actions are org-admin or project-reporter by rule, deny by default, and every mutation has an audit row inside its transaction; the delivery is the only new outbound request and it is constrained as above.
- **REVIEW (design gates, not decided by me):**
  1. **Crypto:** new envelope contexts (`aad("notification_sink", org, id)`, key context `notification_sink:<id>`), sealed JSON `{url, secret?}`. The master-key **rewrap job** is still unbuilt for connections, variable keys and now sinks.
  2. **Authz:** sinks are read, created and deleted by org admins; the project's subscription list is readable by project reporters (name, kind and host of the sink, which can say something: `abc123.ngrok.io`), changed by org admins only (no project-level admin may subscribe); DELETE of a subscription reuses `notification.subscription.update`.
  3. **Migration 0027** (additive; sinks RESTRICT the organization, so an organization with sinks cannot be deleted; the message says "projects or connections" and was not updated).
  4. **DNS rebinding** is open: the address is resolved and checked, then `fetch` resolves it again. Closing it needs the connection pinned to the checked address (a custom agent/proxy), or an egress policy on the worker. Anyone with org admin can point a sink at a name they control, so it is reachable by admins only, but it is the one SSRF gap.
  5. No test-send route, no secret rotation (delete and add again), no delivery log or UI: the only trace of a failure is `last_error` on a dead job and the worker log.
  6. A permanent failure (a 4xx) is retried like a transient one until the attempts run out; no `Retry-After`; no per-sink rate limit; a sink the project removed leaves queued jobs that still deliver (they resolve quietly only when the sink itself is gone).
  7. `events` is only `stack.drift` (both `drifted` and `clean` notify; the counts are in the body). The payload carries the project and stack names.
  8. Deliveries are not ordered (above); no cap on sinks or subscriptions.
  9. The webhook body is `{id, event, at, organizationId, project, stack, status, plan}`; the signature scheme `v1=` leaves room for another.
- Gate: `bun run check` green: 3155 pass + 1 skip (the opt-in real-GitLab run) + 0 fail (root), 239 pass (web). No new dependencies.
