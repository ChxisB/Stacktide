## 2026-10-18 POL-3
- **What:** organizations get **policy sets** (`name`, `source` = a GitLab project path, `ref`, `path`, `tag`; at most 50). A stack whose `stack.yml` carries `tag` has its plan judged: the generated summary job (image `ORCH_POLICY_IMAGE`) downloads each set's archive with the job token, runs `conftest test --output json --all-namespaces` on `plan.json`, reduces the answer with a jq filter to **rule names only** and posts `{stack, evaluated, denied[], warned[]}` to `POST …/runs/:runId/policy-verdict`. The verdict (`pass | warn | deny`) is stored on the run's stack; **a crashed, missing or unreadable evaluator posts `evaluated:false`, which is a deny** (`evaluator-failed`), and a missing verdict for a stack a set reaches is `policy_pending`.
- **Apply preconditions** (after `plan_expired`, before `dependency_not_applied`): `policy_denied` (409, with rule names) and `policy_pending` (409). The MR note has a *Policy* section (verdict plus up to three rule names per stack).
- **Migration `0028_policy_sets.sql`** (additive, trigger block by hand): `policy_sets` (org CASCADE, unique name per org, text-shape checks) and four nullable columns on `run_stacks` (`policy_verdict/denied/warned/at`) with `run_stacks_policy_check` (all four or none; verdict in the set; arrays of at most 50).

Creating a set takes the org row `FOR NO KEY UPDATE` so the cap of 50 holds under concurrency (child inserts take a key share, which it does not block). Operation count 98 → 102, route count 100 → 104; `docs/iac.md` has a *Policy* section; `docs/ci.md` names the second use of the summary scope.

  1. **The tag opt-out:** which stacks a set reaches is decided by `tags` in `stack.yml` of the merge request's own commit. An author can drop the tag in the MR; the stack is then not judged and not `policy_pending`.   7. Drift runs are not judged; there is no UI; `warn` shows only in the MR note.
  8. A failed post leaves no verdict, so apply is refused as pending; a retried plan job drops the verdict (apply waits for a replan, the summary job is not rerun for you). `warn` rule names beyond three are counted in the note, not listed.
  9. No `ORCH_POLICY_IMAGE` means tagged stacks are not planned at all (the generator error is in the MR note).
  10. The whole archive of the policy project is downloaded per set per stack per plan, sequentially; a 50-set organization is slow. Moving refs and the archive size are not limited.
  11. Migration 0028 is additive; deleting an organization cascades its sets (configuration, no secret).

- **REVIEW (design gates, not decided by me):**
  1. **Instance-wide settings.** One env setting for every organization: no per-organization config, no UI, no audit of the setting, no authz. Upgrade when two organizations need different ones.
  2. **A drift check of a target that breaks a guardrail is not recorded:** it logs "drift not checked" and keeps the last status. Real drift of such a target goes unseen and un-notified until it is protected or the rule is off. Auto-sync behaves the same ("not planned"); nothing is written.
  3. **"Production" is a name:** `production` and `prod` (or `ORCH_PRODUCTION_SCOPES`), matched as GitLab scope patterns. A target that calls its production `live` is not guarded until the setting says so. Names are literal, case-sensitive.
  4. **Behaviour change on upgrade:** a target that already syncs to a production scope without `protected: true` now fails plan, auto-sync and drift checks until it is protected or the rule is off. Existing data is not migrated.
  5. **Bare `*` is not production.** A variable in the all-scopes scope reaches production jobs too, but if it counted, every default-scope variable would break the rule. A secret at `*` on an unprotected target is **not** refused. Decide if it should be (it would make `protected: true` mandatory for almost every target).
  6. **A stored plan is not re-checked at apply.** Its digest covers the target's config, so flipping `protected` makes the plan stale; changing `ORCH_PRODUCTION_SCOPES` or `ORCH_GUARDRAILS_OFF` after planning does not.
  7. **`protected` can only be set through the API** (`PATCH` the target's `config`); the web app and the CLI cannot edit a target's config. The refusal names it anyway.
  8. **One target type.** The check reads `protected` from the GitLab-variables config; a second type needs the adapter to say (`shortcut:` in `sync-plan.ts`).
  9. **The pipeline rule cannot tell a secret from a variable,** so it applies `production-variable-protected` only, and it refuses (it does not just describe the exposure in the MR); switching that one rule off lets it through. It also reads the GitLab-variables targets of the project, not those of other projects that sync to the same GitLab project.
  10. **The entry points are not tested:** `worker-main.ts` and `index.ts` pass the parsed setting to the handlers and the app; the handlers and the app are tested with a setting, the passing is not.
- Gate: `bun run check` green: 3283 pass + 1 skip (the opt-in real-GitLab run) + 0 fail (root), 240 pass (web). No new dependencies.
