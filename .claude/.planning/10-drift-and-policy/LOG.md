## 2026-10-18 POL-1
- **Marker:** `stack.yml` gets `drift_every` (`6h`, `1d`: whole hours or days, 1-999, regex `^[1-9]\d{0,2}[hd]$`), read into `Stack.driftEverySeconds`. No `drift_every`, no check.
- **Migration `0026_stack_drift.sql`** (additive; trigger appended by hand as for the other tables): table `stack_drift` (PK project + stack; `status` unknown/drifted/clean, `since` = start of the episode, `requested_at` = what the cadence counts from, `checked_at`, plan counts; CHECKs make `status` and its counts agree, and the composite FK keeps a row in its project's organization, cascading with the project); `runs.kind` (`plan` default, `drift`) with `runs_kind_check` and `runs_drift_check` (a drift run has no merge request).
- **Worker:** a schedule `stack.drift` (every `STACK_DRIFT_CHECK_SECONDS`, default 3600, 0 = off, minimum 60) queues one `stack.drift` job per linked project tagged terraform/terragrunt (`queueStackDriftChecks`, `enqueueOnce` by project so a backlog does not grow; ids only in the payload). The check job (`stackDriftCheckHandler`) finds a connection that reaches the project, scans the default branch head, takes the stacks with a cadence that are due (period up since asked, less 5 min, or never asked; the ones that waited longest first; at most 100), dry-runs the pipeline generator, marks them asked for and, in a savepoint, creates a run `kind=drift` on the default branch, audits `run.create` as the job and starts the same plan child pipeline as a merge request plan (`planRequest`/`triggerPlan` were pulled out of `mr-plan.ts` to share it). GitLab refusing the pipeline leaves no run and is tried again after a period; any other failure fails the job, rolls everything back and the queue retries. Checks of one project take turns (`FOR NO KEY UPDATE` on the project row).
- **Finding:** when the plan summary of a `drift` run is stored (the existing summary route and its binding to the recorded summary job), `recordStackDrift` sets drifted/clean. An episode is one `stack.drift` audit event at its start (`drifted`) and one at its end (`clean`), counts only, `resourceType: stack`, `resourceId` the stack name; repeated drifted plans change the counts. `since` stays the start of the episode. A report whose run was asked for before the latest taken one changes nothing (a late run cannot undo a newer finding). The route's audit now declares `run.summary` and `stack.drift`.
- **Never applied:** `applyRun` refuses a drift run (`409 drift_run`) before it reads anything of GitLab; the DB check already keeps a drift run from having a merge request, which every apply path needs. `POST /runs` cannot create one (`kind` is not in the body; a body that has it is 422). `kind` is in the run API (`docs/openapi.json` regenerated).

- **REVIEW (design gates, not decided by me):**
  1. The marker gains `drift_every` (whole hours/days).
  2. **The connection is chosen by trial** (the platform records no project-to-connection link): the first 20 `gitlab` connections of the organization, in id order, until one can fetch the project's default branch by its numeric id. **If two GitLab instances in one organization have a project with the same numeric id, a check can land on the wrong one** and plan the wrong repository. The upgrade is to record the connection at import.
  3. Every tick reads every linked project and, for each IaC project, scans its default branch over GitLab even when nothing is due (cache by head sha, or skip when no row is due and nothing changed, is the upgrade).
  4. The cadence is rounded to the tick, with 5 minutes of slack, counted from when a check was *asked for*; no guard against an earlier drift run still running (a long plan can overlap the next).
  5. Drift is a normal plan of the default branch, not `-refresh-only`: a plan that wants to change something because the code moved ahead of the apply is reported as drift too.
  6. The audit event `stack.drift` is the hook for POL-2 (episode start and end only).
  7. No route reads drift status yet (follow-up for the UI/API).
  8. A protected `environment` works only because the default branch is protected.
  9. The default branch's `.gitlab-ci.yml` must include the parent snippet; a project without it is retried once per period and only the worker log says so (nothing visible to the user).
  10. **The `stacks` table is not filled in production** (`syncStacks` has no caller outside tests), which is why drift scans the repository itself; `POST /runs` therefore always answers 422 `unknown_stack` for a real project (MR planning is unaffected). Also noted in the feature 09 completion doc.
  11. A stack that leaves the repository or loses its `drift_every`, or whose drift plans all fail, keeps its last status and `since` forever (no `resolved` event). Subscribers must treat an open episode as open until told otherwise; POL-2 decides whether to expire.
  12. The run records the sha of the head it scanned, but the pipeline runs on the branch: a commit between the two is planned and recorded under the older sha.
  13. An orphan GitLab pipeline is possible if the commit fails after GitLab started the pipeline (the same shortcut as IAC-8); the retry then starts a second plan.
  14. A pipeline GitLab refuses marks the stacks as asked for (retried once per period); a failure of any other kind retries at the queue's pace.
  15. The schedule is disabled when the merge request plan settings are missing (`ORCH_API_URL`, `ORCH_CI_AUDIENCE`, `ORCH_HELPER_IMAGE`).
  16. A project must be tagged terraform/terragrunt at import to be checked.
  17. Last report wins within the ordering above (the run's *request* time, not when it finished).
