# 04 Secrets and Variables - Log

## 2026-10-17 VAR-1 - REVIEW (crypto and key handling were built to the approved SPEC and ADR-0007 unattended; a human should read this entry and `packages/crypto/src`)
- New package `@orch/crypto`, no dependencies (`node:crypto`). AES-256-GCM, 96-bit random nonces, 16-byte tag, blob = `[version 1][nonce][ciphertext][tag]`.
- API: `generateDek()`, `encrypt(dek, text, aad)` / `decrypt(dek, blob, aad)`, `wrapDek` / `unwrapDek` / `rewrapDek(provider, ..., context)`, `aad(...parts)`, `envKeyProvider(env)`, `KeyProvider { currentKeyId, wrap, unwrap }` (async, so a KMS provider fits), `CryptoError` with a `code`.
- **Opaque keys.** `Dek` is an empty class whose bytes sit in a module-private `WeakMap`: it prints as `Dek {}`, JSON/spread/inspect show nothing, and nothing else type-checks as one. The bytes are copied in, so a provider reusing its buffer cannot change a key.
- **Context binding.** `Aad` is a branded string only `aad(...parts)` can make (JSON array: unambiguous, lone surrogates escaped). Callers lead with the record kind: `aad("variable", projectId, variableId)`. The DEK wrap binds `aad("orch:dek", context)` plus the master key id, so a wrap opens only for the same owner and the same key id.
- **Master keys (env provider).** `ORCH_MASTER_KEYS="k2:<b64>,k1:<b64>"`, 32 bytes each, canonical base64 only; the first entry wraps, the rest only unwrap. Rotation = add a new first entry, `rewrapDek` every row whose `keyId != currentKeyId`, drop the old entry. `rewrapDek` on a row already on the current key returns it unchanged (so the job writes nothing for it). Values are never re-encrypted. Config errors name the entry's position, never its text. `.env.example` documents the variable commented out and with no default: a real key goes in `.env`.
- Errors are fixed strings with a code (`decrypt_failed` covers wrong key, wrong AAD and any altered byte; `bad_format`, `unknown_key`, `bad_config`, `invalid_input`); never a key, plaintext or AAD.
- Tests (19): round-trip of empty, unicode, 1 MB and 200 random value/AAD pairs; ciphertext differs per call and hides the value; 10,000 distinct nonces; every single byte flipped fails (byte 0 as `bad_format`, the rest `decrypt_failed`); wrong AAD, wrong key, truncation; a fixed vector built independently with `node:crypto`; wrap/unwrap, wrong owner, wrong master key, tampered wrap, key-id swap (same key under two ids), `unknown_key`, rotation with the old key dropped; env parsing rejects bad entries without echoing them; no key material in JSON/inspect/String of a `Dek` or provider; error text free of value and AAD. Mutations checked, each fails tests: no AAD, fixed nonce, no key-id binding, no tag check, wrap ignoring its context, no canonical-base64 check, no well-formed check, rewrap always rewriting.
- `/code-review` (medium) found 9, plus the inline crypto review it covers (nonce, AAD, key-id binding, leakage): fixed key-size check in `seal`/`open`, blob type check, copy of key bytes, canonical base64, lone surrogates (rejected for values, escaped in AAD), branded `Aad`, test strictness, fixed vector, no-op rewrap. Not done: the version byte is not in the AAD (only version 1 exists and the check is strict); `unknown_key` vs `decrypt_failed` stays distinct on purpose (the key id comes from our own row, and operators need to see a dropped master key); no wiping of key bytes (not possible in JS); no cap or counter on random-nonce use (a per-project DEK makes 2^32 unreachable; a DEK-replacement job is not built).
- **Not done / for the human gate:** `/security-review` is unusable here (no remote), so the review above is the only one. The master key sits in the process environment (ADR-0007 accepts this for local and early use). Losing every master key loses every secret: OPS-4 must cover backup. Nothing uses the package yet; VAR-2 adds the tables and wires it in.
- Gate: `bun run check` green, 202 pass + 1 skip. New dependency: none. New workspace package: `packages/crypto` (`bun.lock` updated).

## 2026-10-17 VAR-2 - REVIEW (key handling and delete semantics were built to the approved SPEC unattended; read `packages/db/src/variables.ts` and `packages/db/drizzle/0012_variables.sql`)
- Tables (migration `0012_variables`, additive; the only change to an existing table is a new `UNIQUE (id, project_id)` on `environments`, the target of a composite FK):
  - `variable_keys`: the wrapped data key of one owner, **one per project and one per organization** (for org-level variables; partial unique indexes on `project_id IS NULL` / `NOT NULL`). Made on the first `createVariable` (insert `ON CONFLICT DO NOTHING`, loser re-reads the winner's: tested with 6 concurrent creates). Wrap context `variables:project:<id>` / `variables:org:<id>`.
  - `variables`: org / project / project+environment level (CHECK: an environment needs a project; composite FKs keep the project in the org and the environment in the project), `kind` and key-format CHECKs (`^[A-Za-z_][A-Za-z0-9_]{0,254}$`), unique key per level **among live rows** (`deleted_at IS NULL`). SPEC's `current_version_id` is a plain `current_version` number: a rollback (VAR-5) makes a new version, so the latest is always the live one, and it avoids a circular FK.
  - `variable_versions`: append-only (`value_enc`, `version`, actor kind/id, `reason`, `created_at`; no `updated_at`, added to the conventions test's append-only list). A trigger refuses UPDATE, TRUNCATE and any DELETE **whose variable still exists**; a cascade passes because the variable is already gone.
- Every value is sealed, `plain` too (kind can change later, and a raw `SELECT` must show no plaintext): AES-256-GCM with the owner's DEK, AAD `aad("variable", orgId, projectId|"", variableId, version)`.
- Repo (`packages/db/src/variables.ts`, exported): `createVariable`, `setVariable` (value = next version, description-only = no version, concurrent writers get a version each: the UPDATE is the lock), `deleteVariable` (soft), `getVariable`, `listVariables` (exactly one level, keyset by id), `listVersions` (newest first), `revealVariable` (current or an older version: the one way to a secret for a person), `openChain` (every live variable that applies to an environment, all opened: the input to the VAR-3 resolver). `plain` values come back with the variable; `secret`/`file` values are `null` in `Variable` and appear only through `revealVariable` and `openChain`. No view holds `value_enc` or the `dek_*` columns. Every query repeats org (and project) so a path id finds nothing under the wrong parent. Errors thrown: `CryptoError`; a lost key is `Error("variable key missing")`.
- **Delete semantics (REVIEW):** project and environment removal CASCADE to their variables, versions and keys (the delete is already an explicit, guarded action). Organization removal also cascades to org-level variables and keys, but is still blocked by projects and connections (RESTRICT). Rejected: RESTRICT on org-level variables, because soft-deleted rows would then block org removal for ever. A variable deleted through the API is soft (history kept, key free for reuse).
- Tests (`variables.test.ts`, 26): raw `SELECT *` of the three tables holds no plaintext for every kind; plain returned, secret/file never in list/get; reveal current/older/missing version; one key per owner under a race; ciphertext moved to another variable or version, a value sealed for another project and a key wrapped for another project all fail with `CryptoError` (hand-planted rows, with a control that opens); wrong master key; unique-key rules per level and the same key allowed across levels, environments, projects, orgs and letter case; key/kind/scope checks; cross-org and cross-project FKs; id scoping on every function; versions order/paging/actor/reason/concurrency; a version number once per variable; UPDATE/DELETE/TRUNCATE refused; soft delete frees the key at all three levels and keeps history; cascades from environment, project and organization; chain contents (sibling project, other env, other org, deleted, shadowed); lost data key is an error for write and read and makes no new key; empty patch changes nothing.
- Mutations: 46 checked (AAD parts, key context, secret decryption in lists, key lookup, race handling, soft-delete/scoping predicates, paging, chain predicates and levels, trigger and FK/CHECK/unique definitions), all killed. First run left three survivors (AAD without variable id, owner, and a constant key context): killed by adding same-version swap and hand-planted-row tests.
- `/code-review` (medium) found 8. Fixed: append-only guard keyed on "variable already gone" instead of trigger depth (a nested trigger could have deleted versions); `setVariable`/reads no longer make a new data key when the old one is lost (it would have orphaned earlier versions); empty patch no longer touches the row; indexes added for the cascade lookups (`variables(organization_id, project_id)`, `variables(environment_id)`). Not changed, by design: no rewrap job (below); `openChain` opens the whole chain, shadowed values too, with no limit (precedence belongs to the VAR-3 resolver; revisit if an environment has thousands of variables); the AAD does not bind environment, key name or kind (row metadata is not authenticated: someone with DB **write** access can rename or re-point a variable or roll `current_version` back, only ciphertext moved between rows is detected; ADR-0007 protects against a DB read); no purge of deleted variables' ciphertext (history is what VAR-5 restores from; an erasure path needs a deliberate trigger exception and a decision).
- Inline security review: no value in any error, log or audit path (repo throws only fixed strings or `CryptoError`); Postgres error detail for the tables holds ids, key names and ciphertext only, never plaintext; no plaintext leaves `openChain`/`revealVariable`; the repo writes no audit rows (VAR-4's routes must: `variable.create|update|delete|reveal`, metadata ids and key names only).

## 2026-10-17 VAR-3
- `packages/core/src/variables.ts` (exported from the core index): `resolveVariables(inputs): { variables, issues }`, pure, no I/O, no dependency. Input is the chain for one environment as one list (`VariableInput` = `ChainEntry` from `@orch/db`, now the same type); the caller picks the chain (org + project + environment, or org + project for a project-wide view).
- Small design decisions inside the task (SPEC says only "`${KEY}` resolves within the same environment's resolved set; a value that references any secret is itself a secret"):
  - Most specific level wins each key (environment > project > organization). A reference reads the **winner**, so a self reference is a cycle even when it overrides a lower level.
  - Syntax is literal unless exact: `${KEY}` with `KEY` a valid variable key is a reference; `$${` writes a literal `${`; `$KEY`, `${KEY:-x}`, `${}` and an unclosed `${` stay as written. Text that came out of a substitution is never read again.
  - `file` variables are not interpolated (their content is taken as written, `$${` included) but can be referenced.
  - Taint: a `plain` value that reads a `secret` or `file` result (any depth) gets `kind: "secret"` and `tainted: true`; a declared `secret`/`file` keeps its kind. Only winners count, so a shadowed secret taints nothing.
  - A key with a problem is left out and explained, the rest still resolves. Issues: `missing {key, ref}`, `cycle {key, path}` (path from the smallest key of the ring, closed), `unresolved {key, ref}` (reads a key that has no result), `duplicate {key, level}` (several at the most specific level that has the key; the repository's unique index makes this impossible, the resolver is total anyway), `too_large {key}`. Issues carry key names only, never a value (tested with a marker).
  - Resolved values are capped at `MAX_RESOLVED_LENGTH` (1 MiB, UTF-16 units), checked while assembling, so a chain that doubles at every step stops after 20 levels instead of exhausting memory. VAR-4 must still cap what is written.
  - Depth-first with an explicit stack: a 20,000-long chain and a 20,000-long ring resolve without overflowing the call stack. Output is sorted by key and independent of input order.
  - `VARIABLE_KINDS`/`VariableKind` moved to core (the db schema re-exports them); `KEY_PATTERN` is exported for VAR-4's validation and shares one source with the reference regex (the database `variables_key_check` is a separate copy: change both together).
- Tests (`variables.test.ts`, 88): tables for precedence/override/provenance, reference syntax (valid, near-miss, escape, 255-char limit), nesting, files, taint, missing, cycles (self, 2, ring, tail, ring entered from outside, override breaking a cycle, diamond), duplicates, size, scale; 1500 seeded random chains (mulberry32, no dependency) against an independent regex-substitution oracle, plus order independence, taint invariants and "every key resolved xor named by an issue".
- Mutations: 35 checked (precedence, duplicate handling, escape, reference bounds, file/secret interpolation, each taint rule, issue reporting, cycle marking/rotation/closing, size limit and its boundary, sorting, provenance, text before/after a reference); all killed except one equivalent (checking the size after the loop instead of during it gives the same results; the early exit only saves work). First run left four survivors (cycle rotation, ring path start, sorted output, size timing): the first three killed by new tests.
- `/code-review` (medium) found 5. Fixed: reference regex built from the same key source as `KEY_PATTERN`; `ChainEntry`/`ChainLevel` are aliases of core's types; `file` + `$${` documented; candidate loop simplified. Declined: the db schema's runtime import of `@orch/core` (checked: `drizzle-kit generate` still loads the schema and reports no changes; the db package already depends on core).
- Inline security review: pure function over values, no logging, no error carries a value, no `eval`/dynamic code; regexes are linear (no nested quantifiers) so crafted values cannot cause catastrophic backtracking; keys named `__proto__`/`constructor` are plain `Map` keys (tested).
- **Limits / follow-ups:** a cycle is reported once per back edge found, so a node that merely belongs to a second ring through an already-finished node shows as `unresolved` rather than `cycle` (it is still left out); the size cap counts UTF-16 units, not bytes; nothing here checks who may see a result (VAR-4 must strip `value` from every non-`plain` result it returns, and from `plain` results that came from a tainted resolve).
- Gate: `bun run check` green, 851 pass + 1 skip. New dependency: none.

## 2026-10-17 VAR-4
- `apps/api/src/routes/variables.ts` (`variableRoutes`, wired in `app.ts`): the same seven routes at each level (list, get, create, patch, delete, `versions`, `value`) under `/organizations/:orgId/variables`, `/organizations/:orgId/projects/:projectId/variables` and `.../environments/:envId/variables`, plus `GET .../environments/:envId/resolved-variables`. 47 routes in all (guard table, spec and audit-coverage tests updated; `docs/openapi.json` regenerated).
- Authz (`packages/core/src/authz.ts`, **REVIEW**: new rules, model unchanged): project and environment level `variable.read` = project reporter, `variable.create|update|delete` and `secret.reveal` = project maintainer; organization level `variable.org.read` = org viewer, `variable.org.create|update|delete` and `secret.reveal.org` = org admin. Environment-tied CI subjects keep the existing env rule.
- Shapes: create takes `{key, kind, value, description?}`, patch `{value?, description?, reason?}`, both strict objects (unknown keys, `kind` and `key` changes are 422; a change must change something; a `reason` without a `value` is 422, it belongs to a version). Value 1 to 65,536 characters, well-formed Unicode. Responses carry `value` only for `plain`; `secret` and `file` give `null`. List, get, create and patch never contain a secret; `GET .../:varId/value[?version=]` is the only way to one: same transaction as its audit row (`variable.reveal`, ids, key name and version only), `cache-control: no-store`.
- Audit: `variable.create|update|delete|reveal`, metadata ids, key, kind, level, changed field names and version. No value, no reason.
- Resolved endpoint: the chain of the environment through VAR-3's `resolveVariables`; `value` only for results that are `plain` and not tainted, `issues` carry key names. Every secret in the chain is opened in the process to compute taint and references, but none is returned or logged. Any project reporter sees organization-level **plain** values there, as their pipelines receive them (**review finding 1, accepted**; secrets and file values stay hidden).
- Errors: unique key 409 `key_taken`, missing parent 404, unreadable stored secret a fixed 500 (names no value, logged with request id), no master keys 503 for everything that opens a value (create, patch, list, get, value, resolved). Delete and `versions` need no keys (tested).
- **Repo change (REVIEW):** lookups are now level-exact. `live(scope, id)` pins the organization, project **and** environment (or their absence), so an id found under the wrong level finds nothing. New `describeVariable`. The `variable_keys` unique index is on `project_id` alone: a project that already has a data key and is named with another organization makes the insert a silent no-op and then fails with a plain `Error`; the routes check the parent first (create and list), the repo contract says so. A migration would fix it at the root; not done (additive-only, no gate for it yet).
