# 31 Deployments - Tasks

Gate for every task, from the repo root: `bunx biome format --write <touched folders>`, `bunx biome check .`, `bun run typecheck`, then the suites of the folders touched (`bun test --env-file=.env.example packages apps/api apps/cli`, `cd apps/web && bun test --env-file=../../.env.example`). Tests need Postgres on `localhost:5433` (`bun run dev:db`). Web tasks also run `bun run e2e`. Nothing here touches a real GitLab or cloud account (the mock GitLab only).

**Rule for every task: every existing test passes unchanged.** A test that has to change (an exact key list gaining a field) is a finding, written in LOG.md, not an edit made quietly. Every new CSS class gets a rule in `apps/web/src/styles.test.ts`. Every task that returns or stores a deployment adds a leak test: no GitLab user, commit text, variable value or secret.

**Cuts.** A (DEP-1 to DEP-8) see it. B (DEP-9, DEP-10) the deploy template. C (DEP-11 to DEP-15) promote and roll back. D (DEP-16 to DEP-18) protected environments: **waits for its own go** (it uses the change-request approvals, an auth-model change). E (DEP-19 to DEP-21) the notification and the numbers. F (DEP-22, DEP-23) demo and delivery. A, B and C answer the question "can we manage the deployment life cycle"; D and E can wait.

Names used throughout: GitLab's environment **name** is the platform environment's **slug**; the three variables of a promotion are `ORCH_DEPLOY_ENV`, `ORCH_DEPLOY_SHA`, `ORCH_PREVIOUS_SHA`; the template is `docker-deploy`.
