## 2026-10-19 ROT-1
- Built: a new package `packages/rotation` (`@orch/rotation`; D10 says packages are created lazily, and a provider list will grow beyond what `packages/sync` should carry). `Rotator<Config>` is `type`, `validate(config)`, `rotate({config, key}) -> {value, handle, config?}` and an idempotent `revoke(config, handle)`. `handle` names what was minted (an id, never a credential; stored in the open) so the engine can revoke the *new* credential if the write fails and the *old* one after the grace; `config?` lets a provider hand back the config for the next rotation when it changed (a token id). `RotationError` kinds: `invalid_config`, `not_found`, `denied`, `failed`; messages never carry a value, credential or config. `fakeRotator()` records mint/revoke in order and tracks `live`; `runRotatorConformance` (exported from `@orch/rotation/testing`) is run for the fake and `random`. `random`: length 8-256 (default 32), alphabets `alphanumeric|hex|base64url|numeric`, bytes from `crypto.getRandomValues` with rejection sampling so no character is favoured (a test counts 62 000 draws within +-25%); unknown settings are refused without naming them.
- Decision: `random` has no `grace` meaning (there is no old credential to keep valid; the old value is just no longer the live one). The doc (ROT-5) says so.
- Tests: 15 (conformance x2 providers, random: defaults/alphabets/bias/two differ/14 bad configs with a canary, fake: order, `live`, a failure names its kind and not a minted value).

## 2026-10-19 ROT-3
- Built: `apps/api/src/rotate.ts` (beside the sync engine: adapters in packages, orchestration in the app). `rotateVariable(deps, claimed, {now})`: the provider mints, then one transaction holds the new variable version (`setVariable`, so history, rollback, auto-sync apply), the `variable.rotate` audit event (provider, key name, version or change request id; actor `rotation:<id>`) and `completeRotation` (new handle, the replaced credential and when to revoke it, next due). If any of them fails the transaction rolls back, the minted credential is revoked and the old value stays live; a revoke that fails is logged by handle only. Results: `rotated`, `waiting` (protected), `skipped` (`variable_gone`, `claim_lost`, `protection_changed`); a provider failure throws its `RotationError` with nothing changed. `revokePrevious` revokes the replaced credential and forgets it (the sweep in ROT-4 calls it); a rotation also runs it first, so a replaced credential still waiting is never overwritten and lost. New repo functions: `rotationSubject`, `clearRevoked`, `openRequestBy`.
- Decision (protected environments): the new value is sealed in a change request authored by the rotation (`rotation:<id>`), the old one stays live, a person approves it as for any edit, and at most one such request is open per rotation (a later cycle that finds it open mints nothing). Only a provider that is not `external` can do this, so I added `external` to the `Rotator` contract (true when a rotation mints or ends a credential at the provider; conformance requires it to agree with `handle`). A rejected request would strand a minted credential, and GitLab's rotate endpoint ends the old token at once (to verify in ROT-6), so an external provider on a protected environment is refused (`denied`). This narrows the recommended "wait for approval" to providers that can wait; `random` does, `gitlab-token` will not.
- Decision: the engine takes the environment's `share` lock inside the write and re-reads `protected`, as `writable()` in the variable routes does, so protection cannot be switched on between check and write. `protection-coverage.test.ts` lists writers of variables; `rotate.ts` is added to it on purpose, with the reason.
- Tests: 18 (rotated version and audit, grace and revoke, earlier credential revoked first, provider failure, unknown provider not echoed, variable gone, deleted/claim taken/protection switched during mint each revoke the minted credential and keep nothing, failing revoke logged by handle not value, protected: request opened and approval makes it the version, second cycle no second request, rejected then asked again, external refused with nothing minted, project-level variable not held, canary: value absent from audit rows, logs, change request, rotation row and errors, and from the sealed bytes).
- Gate: `bun run check` green: 4372 pass + 2 skip, 246 web. New dependency: `@orch/rotation` workspace link in apps/api.
- Review: self-reviewed against the invariants; `/security-review` is run once over the whole feature (decided for this batch), not per task.
- Follow-ups: ROT-5 refuses an external provider on a protected environment when the rotation is set (the engine still checks, since an environment can be protected later), and refuses a provider change while `previous_handle` is waiting (its handle belongs to the old provider). `pending_approval` stays as the last status after approval until the next cycle. If the commit of the write transaction fails after it ran, the compensation revokes a credential that may be live (shortcut: no way to ask the database whether it committed). The retry delay and the "after N failures" notification are ROT-4.

## 2026-10-19 ROT-4

## 2026-10-19 ROT-6
- **Verified answer (docs.gitlab.com/api/project_access_tokens):** `POST /projects/:id/access_tokens/:token_id/rotate` "immediately revokes the previous token and creates a new token". So **the old token does not stay valid**: there is no overlap and no grace. `token_id` is an id or `self`; `expires_at` (`YYYY-MM-DD`) is optional and defaults to a week when an expiry is required; the answer (200) carries the new token's `id`, `name`, `scopes`, `access_level`, `expires_at` and `token`; errors are 400 (not rotated), 401, 403, 404, 405. The new token keeps the old one's scopes. Rotating another token needs a personal access token with `api` scope. Rotating a revoked token is refused (400) and GitLab treats a replayed one as a leak and revokes the token family.

## 2026-10-19 ROT-10
- Built: the lease engine under ADR-0014. `packages/core/src/leases.ts` (limits as constants); migration `0039_secret_leases` + `schema/secret-leases.ts` (no column can hold a value: a test lists them); `packages/db/src/leases.ts` (`startLease` under an advisory lock on the principal, `recordHandle`, `forgetLease`, `endLease`, `dueLeases`, `getLease`, `listLeases`); `packages/rotation/src/gitlab-lease.ts` (`Leaser` contract in `types.ts`; `gitlabFailure` exported from `gitlab-token.ts`); `apps/api/src/lease.ts` (`issueLease`, `revokeLease`, `sweepLeases`); `builtInLeasers` in `rotators.ts` (which now shares `openGitlab` with `builtInRotators`); the sweep runs first in `rotation.tick` when the worker passes `leasers`.
- Decisions: the row first, then the credential, then handle and audit together (a token never exists that no row can name); provider revoke before the row ends, so a failing provider leaves a lease that says it is live and the next tick retries; the sweep is a no-claim idempotent pass like the replaced-credential sweep (`endLease` ends once, so a person and the sweeper racing end it once). The GitLab date is `date(expiresAt + 24h)`: GitLab expires at 00:00 UTC *starting* that date (from its docs), so never early, at most a day late.

## 2026-10-19 Feature 14 code review (batched over ROT-3..ROT-11)
- Twelve findings. Ten fixed with a test first, two accepted as limits. Running it once over the whole feature, not per task.
  - **F1** a rotation whose write is lost after the provider minted: `keepMinted` (`rotate.ts`). A provider that ended the replaced credential (`gitlab-token`) keeps the new one (`advanceRotation` moves the row's handle and config on, idempotent against an ambiguous commit), the next attempt rotates it. A write of unknown outcome keeps the credential when the row names it; if even that cannot be read it is kept and logged (revoking a live credential is an outage, an unrevoked one nobody holds is not).
  - **F3** a CI job's lease ended after its own token: the lease's TTL is cut to the token's remaining life (`CiJob.expiresAt`), `409 ci_token_ending` under the 60-second minimum.
  - **F4** the lease sweep ran inside `rotation.tick`, so `ROTATION_CHECK_SECONDS=0` stopped lease revocation and one sweep failure aborted rotations: now its own `lease.sweep` queue and schedule (60 s, needs keys, always on).
  - **F5** `completeRotation` wrote `previous_handle`/`revoke_at` even when the rotation had none to record, clearing a pending revoke: written only when the provider says.
  - **F6** `recordFailure` did the count, the audit event and the notification in one transaction, so a failing alert undid the count and the backoff: the count is its own write; the alert is a second transaction, logged if it fails (limit: that alert is not sent later).
  - **F7** `issueLease`'s compensation lost the handle when the revoke failed too: the row now keeps it for the sweeper.
  - **F8** a CI job with no `job_id` gets no lease scopes (the cap has no job to count against); a CI holder is `ci:<project id>:job-<job id>` (job ids are unique per GitLab, and the cap counts across organizations).
  - **F9** changing a failing rotation's provider or config now clears the failures and tries at once; re-enabling one that was off counts from now (jsonb compared in JS, see the driver quirk).
  - **F10** deleting a variable left its current credential and an orphaned row: the current handle goes to the sweep as a replaced one, and `clearRevoked` deletes the row when nothing is left and the variable is gone (shortcut, commented: a row holding both a current and a replaced credential keeps the current one until the replaced is revoked).
  - **F12** `gitlab-token` expiry was the date `expiresInDays` on, which GitLab ends at 00:00 UTC: a day later now; a provider can state `lifetimeDays(config)` and the PUT refuses an interval that is not shorter (`422 interval_exceeds_lifetime`).
  - **Accepted:** **F2** "rotate now" can take over a claim a worker holds (the claim is the fence, not an exclusive lock; the F1 fix means a lost claim leaves the new credential and config kept, and the next attempt rotates it); **F11** two claims in the same millisecond share a fence value (a real fix is a claim-token column, a schema change).
