## What this changes in the plan

1. **The `sub` is not one string.** On GitHub a job that names an `environment:` (our deploy workflow does) has the **environment form** of `sub`; a job without one has the **ref form**; a repository created after 2026-07-15 has the **immutable form with ids**. A condition built from the project path alone would fail closed on a new repository. CLD-3 and CLD-4 take the repository's numeric id (and owner id) and pin **both**, the `sub` and the id claim (`repository_id`, `namespace_id`, `project_id`), and build the `sub` in the form the repository uses. The cybersquatting warning in the GCP page is the reason for the ids.
2. **GitLab's trust is per project and ref, not per environment** (the environment is not in the default `sub`). A GitLab identity trusts `project_path:…:ref_type:branch:ref:main` and the numeric ids. The environment's own protection (who may deploy) stays GitLab's.
3. **A GitHub provider on GCP without a condition is open to every repository on GitHub.** The condition is mandatory in the blueprint, not an option, and a test fails on a provider without one.
4. **The AWS service module must stop reverting a deploy.** `aws_ecs_service.this` takes `task_definition = aws_ecs_task_definition.this.arn` with no `lifecycle`, so the next apply after a deploy would put the placeholder task definition back. The GCP module already has `ignore_changes` on the image. CLD-6 adds `ignore_changes = [task_definition]` to the AWS module, with a plain test (this edits a Feature 35 module and the vendored copy).
5. **The AWS ECR repository is `IMMUTABLE`.** A second push of the same tag fails, so a re-run of a deploy for the same commit must check the tag first (`ecr:BatchGetImage` is in the push policy) and skip the push. CLD-6 does and tests it.
6. **No `*` is allowed except the one the cloud forces**, in a named list a test reads: `ecr:GetAuthorizationToken` (verified) and, until CLD-15 shows otherwise, the two ECS actions above. ADR-0025's decision 3 is read that way.
7. **GitHub already records deployments** for a job with `environment:`; CLD-10 reads them and the `deployment_status` webhook (not fired for `inactive`, so a poll or the next list covers it). The workflow does not create deployments by hand.
8. **Cloud Run cannot pull from a forge registry**, which settles the registry question of ADR-0025 (decision 6).
