# ADR-0019: More than one forge

## Context
The platform is GitLab-shaped on purpose (D1, D6, D8, D9). Teams that keep code on GitHub.com, on GitLab.com or on several self-managed GitLab instances cannot use it fully, and the audit ([forge-seam.md](../forge-seam.md)) found two different problems:

1. **Another GitLab is a small change with deep roots.** Connections already hold a `baseUrl` each, but sign-in, project roles and the CI token read one deployment-wide `GITLAB_URL`, a project does not know which connection it came from, and a user's GitLab id is unique across the deployment.
2. **GitHub is a second forge, and one thing does not map at all.** The platform starts a GitLab pipeline with a *generated* child pipeline passed as a file variable. GitHub has no such thing: a workflow is a file in the repository and a dispatch takes a few declared inputs. Approvals also differ: they are an environment with required reviewers that a reviewer's own account must approve, and on private repositories that needs GitHub Enterprise.

## Decision
1. **A forge is a seam, `packages/forge`.** It holds the operations the callers need (shaped by what they read, not by GitLab's endpoints) and **capability flags** for what a forge lacks. A GitLab adapter wraps `@orch/gitlab` unchanged; a GitHub adapter wraps a new `packages/github`. A feature the forge lacks is refused with a message by its flag, never a button that half works.
2. **The wording of the earlier decisions.** D1: the forge's own CI is the runner (GitLab CI or GitHub Actions); no runner fleet is built. D6: gains the GitHub connection credential (a fine-grained token, ADR-0013's class) and Actions OIDC for CI jobs; "Sign in with GitHub" is optional. D8: on GitHub the pipeline is an inline workflow delivered by a pull request. D9: the default is the forge's managed state **for GitLab** and `state: orch` (ADR-0017) for GitHub. **Invariant 2** reads: all forge traffic goes through `packages/gitlab` or `packages/github`, reached through `packages/forge`. Unchanged: no cloud credentials in the control plane, plan then apply, nothing pushed to a default branch, tests never touch a real forge. The rows D1, D6, D8, D9 and the skill's invariant 2 are **not edited** until you accept this.
3. **A project belongs to one connection** (FRG-28), a nullable `connection_id` where null means the organization's only connection of its type. That is what lets two GitLab instances, or a GitLab and a GitHub, each hold "project 42".
4. **GitLab on any instance (Phase A).** A CI identity token is verified against the issuer and keys of the connection that owns the project (the deployment's `GITLAB_URL` stays the fallback); a second instance signs people in through feature 20's SSO (GitLab is an OIDC provider), so no new auth method and no change to `users.gitlab_id`; a private CA is tried through `NODE_EXTRA_CA_CERTS` first.
5. **No generated pipeline on GitHub.** The stack workflow is a static file committed by a pull request. It takes the platform's `run_id`, fetches the run's plan **as data** with the exchanged OIDC token, and runs the stacks as a matrix per dependency level. The platform starts it with a workflow dispatch and finds the run by its name. GitLab keeps its generated child pipeline untouched.
6. **The platform observes approvals on GitHub and never makes them.** The approve call needs a required reviewer's own identity; if the platform made it, every approval would be the connection's one account and GitHub's "prevent self-review" would no longer separate duties. The platform shows "waiting for approval in GitHub" and learns of the decision from the webhook. It also reads the environment's protection rules and **refuses to deliver an apply it cannot gate**.
7. **The GitHub credential is a fine-grained token per connection first** (the smallest, the same shape as a GitLab connection). A GitHub App (short-lived tokens, not tied to a person) is a follow-up. A webhook secret is stored **sealed**, because GitHub signs the body with an HMAC and a hash of the secret cannot check it.
8. **The first cut refuses, by flag, on GitHub:** DNS stacks and cost gates, secret scanning from job artifacts, deployments (feature 31), token rotation and leases, runner pools, GitLab-managed state, and `ci.lint`. GitHub.com only; `baseUrl` stays configurable so Enterprise Server is a follow-up.
9. **Secrets sync as GitHub allows:** secrets are write-only and sealed to the scope's public key (`crypto_box_seal`), so drift on a secret is names and `updated_at` only; variables are readable and compared by value; a `file` variable is refused.

## Why this, and what was left out
- **A GitHub-only fork** was rejected: two products to keep, and the web, the CLI, sync, rotation and the variables model are forge-neutral already.
- **A generic webhook-only integration** (the platform only listens) was rejected: it cannot open a pull request, sync a secret or start a run, which is the product.
- **GitHub through GitLab's repository mirroring** was rejected: it needs a GitLab the team may not have, and pipelines would run on a copy.
- **The platform approving on GitHub** was rejected for the reason in 6.
- **A GitHub App from the start** was rejected for the first cut: more setup (an installation per organization, key handling) for a credential that fits the existing connection model less well.
- **Bitbucket, Gitea, Azure DevOps** and **several forges specially designed inside one organization** are not built. It is allowed (a project has one connection); nothing special is designed for it.

## Consequences
- **Three auth-model changes**, each with a `/security-review` and a flag in the final report: CI token verification per connection (FRG-5), Actions OIDC (FRG-23), Sign in with GitHub (FRG-25).
- **One new dependency** is likely: a sealed-box implementation for FRG-19, justified in the LOG (a human gate).
- **Migrations are additive** (FRG-28's connection id, the sealed webhook secret); FRG-28 re-creates the project's unique index to include the connection, flagged as 0059 was.
- **Nothing here ran against a real GitHub or a second GitLab**; FRG-8 and FRG-27 are human gates. The sealed-box result, whether a protected-ref claim exists in an Actions token, the dispatch response and PKCE for a GitHub OAuth app are unconfirmed ([forge-seam.md](../forge-seam.md) section 8).
- **On a private repository without GitHub Enterprise** the apply gate cannot exist, so a GitHub stack there plans but is refused an apply. That is a limit of GitHub's plans, not of this design, and it will surprise teams on small paid plans.
- The `ci_tokens` columns keep their GitLab names (`gitlab_project_id`, `gitlab_job_id`, `ref_protected`) and hold the forge's ids; renaming costs a migration for no gain.
