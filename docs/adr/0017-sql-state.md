# ADR-0017: Platform-hosted Terraform state (opt-in per stack)
Status: Accepted (the recommended decisions, taken on your instruction to make them; amend or reverse them here) · Roadmap: STATE-1, D9 · Amends: ADR-0009

## Context
ADR-0009 (D9) says stacks keep their state in GitLab-managed Terraform state and that a database-hosted state backend is backlog. A team that wants the state in one place with the rest of its platform data, versioned, sealed, locked and queryable by what is in it, cannot have that. This ADR changes a confirmed decision, so it is a human gate; the choices below are the recommended ones. **Nothing here makes GitLab-managed state go away or stops being the default.**

## Decision
1. **Opt-in per stack.** `stack.yml` gets `state: gitlab | orch`, default `gitlab`. A stack without the key is generated exactly as before. `orch` points the stack's `http` backend at this API instead of GitLab. The switch is a change to the repository (a merge request), never something the platform does by itself.
2. **What is stored.** One immutable row per write in `state_versions` (stack, serial, lineage, size, who wrote it, the state sealed with a data key made for that row and wrapped by a master key, ADR-0007). One row per stack in `state_locks`. One row per resource instance of the **current** version in `state_resources`: address, type, provider, module, mode and the `count`/`for_each` key, **never an attribute**. Nothing is read from the sealed state except by the backend routes; the index is written in the same transaction as the version it describes, so it can never disagree with it.
3. **The protocol is Terraform's `http` backend.** `GET`, `POST` (with `?ID=<lock id>`) and `DELETE` on the state; lock and unlock as `POST` and `DELETE` on `.../lock` (what the generated jobs use) and as the backend's default `LOCK` and `UNLOCK` verbs on the state itself. A write whose serial is lower than the newest version's, or whose lineage differs from it, is refused; the same serial with the same content is accepted again (a retry), the same serial with other content is refused. A file that is not Terraform state version 4 is refused and nothing is written.
4. **Retention and size.** The newest 20 versions of a stack are kept; older ones are deleted in the write that makes the 21st. The largest state is the API's request body cap (`ORCH_MAX_BODY_BYTES`, 2 MiB by default; the repository refuses more than 16 MiB whatever the cap): a bigger state is refused with 413 and the cap has to be raised first.
5. **Who may reach the state's content: CI jobs, and only they.** The backend sends HTTP Basic credentials, so the state routes (and only they) accept `Authorization: Basic` with the platform's CI token as the password. The token carries `state.read` and, **only for a job on a protected ref with a job id**, `state.write` (which covers writing, deleting, locking and unlocking), and only when the job asks for them (`orch ci login --state`). A job on a branch that anyone can push to may therefore read state (GitLab-managed state lets developers read too) but never write or lock it, so its plan runs with `-lock=false`. A person, with a session or a token, gets no state content at all (403): the API, the CLI and the page show versions and the resource index only. The token names a project; the stack in the path must be one of that project's.
6. **A state token lives as long as the job.** An ordinary CI token lasts 15 minutes at most and never past the job's `id_token`, which GitLab ends after 5 minutes unless the job sets `timeout:`. A job that cannot write its state at the end of an `apply` loses what it created, so the generated jobs of a stack on `orch` set `timeout: 1h` and ask for a token of up to an hour (`MAX_CI_TTL_MS`). An `apply` longer than that cannot write its state; this is a limit of v1, written in the runbook.
7. **Locks.** The owner of a lock is the job (`gitlab_job_id`) that took it; the lock ends when the job's token would (`CiJob.expiresAt`), so a crashed job's lock expires by itself. A second request is answered `423` with the holder's lock info in the body, which is what Terraform prints. Only the owner's job releases it, and only with the lock's id. **Force-unlock is an org admin's, from the API, and is audited.** There are no locks on a part of a state in v1.
8. **Sealed, and in the key lists.** `state_versions` is the fifth table with a wrapped data key: it is in `KEY_TABLES`, re-wrapped by `bun run keys:rotate`, and in the backup test. Audit rows hold stack id, serial, size and lock id, never content; no response, log or error carries state.
9. **Import is a separate step.** `orch state import <stack>` asks the API to read the stack's GitLab-managed state through `packages/gitlab` (with the organization's GitLab connection) and write it as version 1, refusing when the stack already has state here. It never switches the stack. The first real import is a human gate.
10. **Out of scope.** Running Terraform in the control plane (D1 stands). Resource-level locks and scoped plans: dropped, with the reasons in [state-resource-locks.md](../state-resource-locks.md) (STATE-9). Downloading, editing or rolling back state through the API, CLI or page. Opt-in is **not** checked on the server: any CI token of the project may use the backend for any stack of the project, as with GitLab-managed state.

## Consequences
- **The control plane now holds your infrastructure's state.** State holds cloud identifiers and often secrets an output or a provider wrote there, so a database and backup breach is worse than before. The control plane still holds no cloud credentials by design; sealing, the key re-wrap, retention and backups must be treated as strictly as the master keys (`docs/runbook-keys-and-backup.md`). Losing the database loses state: **GitLab-managed state stays the default until backups are proven (OPS-4)**, and the first real state write and import are human gates.
- A CI token for state is long-lived (up to an hour) compared with the others, and travels in `TF_HTTP_PASSWORD`, which the tool and anything it runs can read: the same exposure as `CI_JOB_TOKEN` has. It is limited to one project and to the stack routes.
- Plans from an unprotected ref work (read, no lock). Two plans can then run beside an apply; a saved plan applied against changed state is refused by Terraform itself.
- Reversing this: nothing copies state back to GitLab. A team that leaves `orch` runs `terraform state pull` in a protected job, repoints the backend and pushes. The tables stay until a later migration drops them; the migration that makes them is additive.
- Not covered: the graph and resource-level lock parts of the Stategraph idea; more than the newest 20 versions; encryption of the state in transit beyond TLS; a state larger than the body cap.
