# ADR-0020: Deployments are recorded as GitLab reports them, and a promotion is a pipeline the platform starts

## Context
The platform sets up CI, manages variables and secrets, and orchestrates infrastructure stacks. It does not know an application's deployments: no table holds one, `packages/gitlab` has no call for them, and the three templates end at build or `docker push`. Feature 31 adds the application half of the life cycle: see what is where, deploy, promote a good build, roll back, and know a deploy failed. Invariant 3 says the control plane holds no cloud or infrastructure credentials and the CI runner does; invariant 6 says nothing is pushed to a default branch.

## Decision
1. **GitLab stays the runner and the credential holder** (D1). The platform never connects to a deploy target. Credentials for a deploy are CI variables scoped to the environment, or the repository's own tooling; the platform stores none.
2. **A deployment is recorded as GitLab answered when asked.** A `Deployment Hook` (allow-listed fields only) queues a job; the worker asks GitLab for the deployment and stores the answer, ordered by `observed_at` the way a pipeline run is (PIPE-8): an earlier read never replaces a later one. `POST .../deployments/refresh` fills a project whose webhook predates the feature. The row keeps GitLab's ids, environment name, sha, ref, status, job and pipeline ids and times. It keeps no GitLab user, no commit text and nothing free-form.
3. **Environment names match by slug.** GitLab's environment name equals the platform environment's slug. Nothing is configured; a GitLab name with no platform environment is listed by name only.
4. **The deploy step is the repository's own script.** The `docker-deploy` template builds and publishes the image, then runs `deployScript` (default `deploy.sh`) with the image and the environment in its environment. The platform ships no Helm, SSH or compose logic.
5. **A promotion is a new pipeline on the default branch,** started with `gitlab.pipelines.trigger` and exactly three variables: `ORCH_DEPLOY_ENV` (a slug), `ORCH_DEPLOY_SHA` (40 hex characters) and `ORCH_PREVIOUS_SHA` (the environment's current build, when there is one). Both values are checked by the platform before they are sent and again by the template's script before it uses them. A rollback is a promotion of the newest earlier good build to the same environment, one code path. Only a build that finished `success` somewhere in the project may be promoted. This is the path IaC applies already use, and starts no job that retries an old one (an old job needs its artifacts and may be hidden by "prevent outdated deployment jobs").
6. **The platform's guard is the gate.** The pipeline is started with the organization's connection token, not the person, so GitLab's own protected-environment rules apply to the token's user. Promote and roll back are maintainer actions (`deployment.promote`, `deployment.rollback`), as `run.apply` is; reading is reporter; refreshing is maintainer because it spends GitLab calls. Every promotion and rollback writes one audit event naming the environment, the sha, the previous sha and the pipeline.
7. **Protected environments wait for approvals.** A promotion or rollback into an environment whose `protected` flag is set starts only with an approved change request of the `deploy` kind for that environment and commit: the approvals that already guard syncs and IaC applies (one approval, one use, the author may not approve). The start takes it in the transaction that starts the pipeline and writes the audit row, so a refused start leaves it unspent; without one the answer is `409 approval_required`. No second approval system is built.
8. **Numbers come from deployments alone** (cut E): frequency, failure rate and median time from a failure to the next success. No lead time (it needs commit times, which are not stored).

## Why this, and what was left out
- **Reading GitLab on every page view** (no table) was rejected: it needs GitLab up, loses what GitLab prunes, and cannot give the numbers.
- **Retrying GitLab's earlier deploy job** as the rollback was rejected: it runs the old pipeline definition and needs the old artifacts.
- **Templates that ship Helm or SSH logic** were rejected: more to keep right, and each fits fewer projects than a script the team owns.
- **An explicit mapping column** between GitLab and platform environments was rejected for now: a naming rule is nothing to configure, and a mismatch is visible (it is listed as unmatched).
- **Kargo, Argo Rollouts and Flagger** need Kubernetes and a controller; their ideas are kept (stages in order, verify after a deploy, step back), their machinery is not.
- **Auto-promotion** when a deployment verifies would need a CI token that may promote, which is an authorization decision of its own.

## Consequences
- The first real promotion writes to a real GitLab (a pipeline on a real project), and the template has only met the mock's lint: `environment: name: $VAR`, `resource_group` with a variable and the `rules` are GitLab behaviours the mock cannot prove. Both are human gates, as the first real apply of feature 09 was.
- A maintainer may promote to every unprotected environment of the project; the token's own rights are not the person's. Protected environments are the answer, and until they exist they are refused.
- Two promotions to one environment within seconds both pass the platform's check (the table only knows what GitLab has reported); the template's `resource_group` makes the second wait and deploy the same sha again, which a script must tolerate. The code says so in a `shortcut:` comment.
- GitLab may restrict who can set pipeline variables on a project; the trigger would then be refused (`gitlab_refused`). The IaC plan pipelines depend on the same setting.
- A rollback restores the application, not its data: a migration that ran stays run. The confirm and the doc say it.
- An existing project's webhook must also send **Deployment events**; until it does, only Refresh fills the table.
