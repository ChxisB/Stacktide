# DNSControl spike (DNS-2)

What DNSControl really does, checked on 2026-10-20 before anything in feature 21 depends on it. Everything here ran on one machine against DNSControl's local `BIND` provider writing zone files to a directory: no network, no real zone, no credential. The captured outputs are the fixtures in `packages/iac/src/fixtures/dnscontrol/` (kept byte for byte; Biome ignores that folder).

**How it ran.** Docker was not answering on the machine, so this was not run in a container. The release binary `v5.5.0` (published 2026-10-15) was downloaded from the project's GitHub release, checked against the release's `checksums.txt`, and run from an empty directory. The image was **not pulled or run**: finding 12 comes from the project's `Dockerfile` and release config and from Docker Hub's tag list. Re-run the spike in the image once Docker works; the behaviour does not depend on how the binary is started.

## Findings

| # | Question | Answer | Consequence |
|---|---|---|---|
| 1 | Exit codes of `preview` | `0` whether or not there are changes. `--expect-no-changes` makes it exit `1` when there are. A bad config exits `1` (`check`, `preview`). | The plan job reads the report, not the exit code, to decide what changed. Use `--expect-no-changes` where "empty" must be a hard test (drift, the second plan). |
| 2 | A machine-readable preview | `preview --report <file>` writes a JSON array: one entry per domain and provider (and one per registrar) with `corrections` (a count) and `correction_details` (strings, one per change). `report-changes.json`. | Parse the report, never the console text. |
| 3 | The text of a change | `+ CREATE <fqdn> <TYPE> <rdata> ttl=<n>`, `- DELETE <fqdn> <TYPE> <rdata> ttl=<n>`, `± MODIFY <fqdn> <TYPE> (<old>) -> (<new>)`. The apex is the bare zone name. A zone that is new is `Ensuring zone "<zone>" exists in "<provider>"`. | The summary keeps `verb`, `fqdn` and `TYPE` of each line and drops everything after the type. A line that does not match becomes one change of `<zone>` (`update`, or `create` for "Ensuring zone"). |
| 4 | Grouping | BIND puts all record changes in one numbered correction (`#1:` with several lines). The report lists each line separately. Other providers number one correction per record. | Read lines from `correction_details`, not the `#n` numbering. |
| 5 | Values in the output | Present in the console text, in `correction_details` and in `push`. **Errors echo values too** (`not a valid IPv4 address: not-an-ip`). | Nothing the tool prints may reach a summary, MR note, audit row or error. Only the parsed verb, name and type do; every message the platform shows is fixed wording. |
| 6 | A zone that does not exist yet | `preview` shows only `Ensuring zone ... exists`, no record changes. The first `push` creates the zone and writes all records in the same run (`report-new-zone.json`). | The first plan of a new zone is one create of the zone. The import job (DNS-9) is how an existing zone gets a first empty plan. |
| 7 | Purge default | Confirmed: a record at the provider that the config does not list is **deleted** (`- DELETE _canary...`). `NO_PURGE` on the domain keeps unknown records (`report-no-purge.json`: 0 corrections). | `dns.prune` defaults to false, so the scaffold writes `NO_PURGE`; a delete in a plan is the gate (DNS-7). |
| 8 | `print-ir` and the keep flag | `print-ir` prints JSON: `domains[].records[]` with `type`, `ttl`, `name`, `comparablev3` and `rdata`, plus `filepos`. `"keepunknown": true` is on the domain only when `NO_PURGE` is set; it is absent otherwise (`print-ir.json`, `print-ir-no-purge.json`). | The lint's `keep-unknown` rule is `keepunknown` absent while `prune` is false. Record values are in the IR: the lint runs in the runner and emits no value. |
| 9 | `dnscontrol check` | Offline; exits `0` with `No errors.` or `1` with a message. It does **not** reject two SPF `TXT` records at one name (`two-spf.js`, exit `0`). | The `spf-single` lint rule is needed on top of `check`. |
| 10 | `$ENV` in `creds.json` | Confirmed: `"directory": "$ZONE_DIR"` took the value of `ZONE_DIR` (`creds.env.json`). **An unset variable did not fail**: the BIND provider fell back to its default directory. Unset behaviour for token providers was not tested (no network). | The plan job checks that every `$NAME` in `creds.json` is a set, non-empty variable and stops with a fixed message naming it, rather than letting the tool run with an empty token. |
| 11 | `get-zones` | `get-zones <credkey> <zone>` prints a zone as `--format` `zone`, `js`, `djs`, `tsv` or `nameonly`, to stdout or `--out`. The `js` output is "a decent first draft": it sets `{no_ns: "true"}`, declares the provider with an empty second argument and comments the SOA out. Planned against the same zone it gives **0 corrections**. | The import job's artifact is the `js` draft. The scaffold adds `NO_PURGE` (the draft does not have it), and fixes the provider call. |
| 12 | The official image | `dnscontrol/dnscontrol` on Docker Hub, mirrored as `ghcr.io/dnscontrol/dnscontrol`. Tags are the version **without** a `v` (`5.5.0`, `5.4.0`, ...) and `latest`; `amd64` and `arm64`. Alpine based, `ENTRYPOINT ["/usr/local/bin/dnscontrol"]`, `WORKDIR /dns`, no `orch`. | The stack's `version` is the tag (`5.5.0`). A job needs `entrypoint: [""]` and an image that also holds `orch`: build `FROM dnscontrol/dnscontrol:<version>` and add the `orch` binary, as for Terraform stacks with an environment. |
| 13 | Handing the tool its credentials | `orch run` with no `--prefix` sets each variable of the environment under its own name. | `orch run -- dnscontrol preview` is enough: `creds.json` names `$CF_API_TOKEN`, the stack's environment has `CF_API_TOKEN`. No prefix. |
| 14 | `--allow-fetch` | Off by default: "Enable JS fetch(), dangerous on untrusted code". | The generated jobs never pass it. |
| 15 | Reproducible BIND output | `--bindserial N` pins the SOA serial. | Used in tests only. |
| 16 | The `NO_PURGE` note in the report (found by the end-to-end run, DNS-13) | With `NO_PURGE` and at least one other change, `correction_details` starts with the note `N records not being deleted because of NO_PURGE:` and then one line per record it keeps, as `TYPE("name.", value),` (`report-no-purge-changes.json`: 6 lines for 1 create). The console counts that as part of one correction; the report's `corrections` counts the lines. With no other change the report has 0 corrections (finding 7). | The summary filter drops the note and its record lines: they are not changes. Before this, each line was one update of the zone, so a plan of one create read as 1 add and 5 changes, and a zone with many kept records passed the list's limit and was denied as truncated. The apply's change-set digest still holds the note, so a kept record that changes between plan and apply makes the apply refuse and ask for a new plan. |

## What changed in the plan
- The plan job writes `preview --report` JSON and the text as the artifact (`access: developer`); the summary job reads the JSON. (SPEC, DNS-4.)
- The apply job's change-set digest is taken over the sorted `correction_details` of the re-run, values included, inside the runner. Only the digest is compared; nothing is posted. (DNS-5.)
- DNS-13 (finding 16): the summary leaves out the `NO_PURGE` note. Seen with BIND only; whether a network provider words it the same is not verified.
- DNS-4 adds the unset-variable check (finding 10). DNS-8 and DNS-9 add `NO_PURGE` to what they write (findings 7 and 11).
- Not verified here, and said so: how a provider that talks to a network (Cloudflare, Route 53) words its corrections beyond the grammar above, an unset `$VAR` for such a provider, and the image running on a CI runner. The first run against a real provider stays a human gate.
