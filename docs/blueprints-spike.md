## Findings that change the SPEC
1. **A rendered stack must not set `environment:` on GitHub, and does not need it anywhere.** The key makes the plan job read a platform environment's variables as `TF_VAR_*` and needs an image with `orch`; `stack-workflow.ts` refuses it ("a GitHub job has an environment only by deploying to it, which is not built yet"). Blueprints take no variables from the platform, so **`stack.yml` carries no `environment:`**. The environment is in the `resources` row and in the stack's name.
2. **The stack name is the state key and must be unique in the project.** A rendered stack is named `<environment>-<name>-<kind>` (at most 63 characters, so the three parts are limited together in BLP-3). `uses: postgres:main` in environment `staging` resolves to the stack `staging-main-postgres`.
3. **The `stacks` table has no environment column.** A stack is tied to an environment only through the optional `environment:` key at plan time, and nothing stores it. Feature 34 derives "an environment's state from its stacks" (ODE-4) and so needs a stored link; **ODE-2 must settle how** (a column filled by `scan`, or the name prefix this feature uses). For this feature the link is the `resources` row.
4. **A stack's state lives per run, not on the stack.** `run_stacks.status` (`queued … applied … failed`) is the per-stack state; a resource's state (BLP-14) is derived from its stack's newest `run_stacks` row.
5. **The database password cannot be kept out of Terraform state with Terraform 1.5.** `password` is stored in state; write-only arguments need 1.11. The password is generated by `random_password` and written to the secret manager as part of a connection URL; **the state is sealed by the platform (ADR-0017)** and the module's README says so. For RDS, `manage_master_user_password` would put the secret under a name RDS chooses and holding a different shape (no URL), so it is not used; the uniform name `<environment>-<name>-database-url` is.
